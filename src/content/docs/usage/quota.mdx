O Turbo Notify mede **duas quotas independentes** por número vinculado (`main` ou
alias extra): mensagens outbound e contatos distintos contactados. Desde a ADR
2026-07-02 ambas as quotas são **por número** — cada número tem sua própria
franquia, e uma organization com N números tem N× a franquia do tier.

Apenas o que trafega **via Turbo Notify** (`origin: "tn"`) consome quota;
mensagens enviadas direto do telefone físico (`origin: "native"`) não contam.

## Ciclo avaliado — quando a quota reseta

A janela de medição das duas quotas é o **ciclo de faturamento avaliado** da
organization (`cycle_start` até `cycle_end` — o mesmo período `current_period_*`
da assinatura), não mais uma janela rolling de 30 dias. `resets_at` sempre
coincide com `cycle_end`: a quota reseta na virada do ciclo, não em uma janela
móvel que decai dia a dia.

- **`used`**/**`quota`** são sempre medidos contra o ciclo atualmente aberto.
- Ao fechar o ciclo (renovação da assinatura), os contadores zeram e uma nova
  janela `[cycle_start, cycle_end)` começa.
- O `cycle_start`/`cycle_end` é o **mesmo para todos os números** da
  organization (o ciclo é da assinatura, não do número) — só `used`/`quota`
  variam por número.

## Tabela de tiers (por número, por ciclo)

| Tier       | Mensagens/ciclo | Contatos distintos/ciclo | Números extras (máx.) |
| ---------- | --------------: | -----------------------: | ---------------------:|
| `FREE`     | 1.000           | 100                       | 0                      |
| `SOLO`     | 10.000          | 1.000                     | 0                      |
| `BUSINESS` | 50.000          | 5.000                     | 300                    |
| `CUSTOM`   | 500.000+        | 50.000+                   | 1.000                  |

A razão 10:1 (mensagens/contato) reflete o uso médio de ~10 mensagens por
contato por ciclo. Overrides de organization (`messages_quota_override` /
`contacts_quota_override`) substituem o teto do tier quando definidos — aplicados
**por número**, do mesmo jeito que o teto do tier.

O campo `tier` nas respostas abaixo é sempre um dos 4 valores acima, em
**maiúsculas** (`"FREE"`, `"SOLO"`, `"BUSINESS"`, `"CUSTOM"`).

## Grupos e mensagens inbound

- Um envio para **grupo** consome **1 unidade da quota de mensagens** e **zero**
  da quota de contatos — um grupo não é um contato.
- Mensagens **inbound** (recebidas) não consomem nenhuma das duas quotas.
- Apenas envios **outbound** com `origin: "tn"` consomem a quota de mensagens;
  apenas contatos contactados **via Turbo Notify** consomem a quota de contatos.

## Envio para grupos exige plano BUSINESS ou superior

Enviar mensagem ou indicador de digitação para um `group_id` requer a feature
`groups:messages`, disponível a partir do tier `BUSINESS`. Em `FREE`/`SOLO` você
ainda pode **receber** mensagens de grupo, listar grupos e consultar detalhes —
apenas o **envio** outbound para grupo é bloqueado:

<ApiResponse
  status={402}
  body={{
    error: 'feature_not_available',
  }}
/>

Veja [Grupos — Visão geral](/groups/overview/) e [Limitações de grupos](/groups/limitations/).

## Endpoint: uso agregado da conta

```http
GET /v1/usage
```

**Scope:** qualquer API key autenticada (sem scope específico).

**Cache:** `Cache-Control: max-age=60` (Redis L1 com TTL 60s).

`GET /v1/usage` é o **roll-up da conta**: `messages`/`contacts` no nível raiz
somam o uso de **todos os números** da organization — `quota` é a **soma das
franquias de cada número** (uma organization com 2 números em um tier de
100/ciclo reporta `quota: 200`). `resets_at` é o `cycle_end` avaliado da
organization (o mesmo para todo número). A resposta também traz `numbers[]`:
uma entrada por número **vivo** (main + extras), com o detalhamento
`used`/`quota`/`remaining` de cada família — sem `resets_at`/`tier` por entrada
(ambos já são uniformes no nível raiz).

<ApiResponse
  status={200}
  body={{
    messages: {
      used: 1234,
      quota: 10000,
      remaining: 8766,
      resets_at: '2026-07-01T00:00:00Z',
      tier: 'SOLO',
    },
    contacts: {
      used: 87,
      quota: 1000,
      remaining: 913,
      resets_at: '2026-07-01T00:00:00Z',
      tier: 'SOLO',
    },
    numbers: [
      {
        alias: 'main',
        messages: { used: 600, quota: 5000, remaining: 4400 },
        contacts: { used: 40, quota: 500, remaining: 460 },
      },
    ],
  }}
/>

### `GET /v1/usage/messages`

Mesmo roll-up de conta, apenas a família de mensagens — mas também carrega seu
próprio `numbers[]` (entradas só com `messages`), para quem consulta apenas essa
quota sem pagar o custo do roll-up de contatos:

<ApiResponse
  status={200}
  body={{
    messages: {
      used: 1234,
      quota: 10000,
      remaining: 8766,
      resets_at: '2026-07-01T00:00:00Z',
      tier: 'SOLO',
    },
    numbers: [
      { alias: 'main', messages: { used: 600, quota: 5000, remaining: 4400 } },
    ],
  }}
/>

## Endpoints por número

- `GET /v1/numbers/{alias}/messages/quota` — quota de **mensagens** do número
  (rota plana para o principal: `GET /v1/messages/quota`, equivalente a
  `GET /v1/numbers/main/messages/quota`).
- `GET /v1/numbers/{alias}/contacts/quota` — quota de **contatos** do número
  (rota plana para o principal: `GET /v1/contacts/quota`).

Ambos retornam o mesmo shape — o snapshot do ciclo avaliado **daquele número**:

<ApiResponse
  status={200}
  body={{
    used: 1234,
    quota: 10000,
    remaining: 8766,
    cycle_start: '2026-06-01T00:00:00Z',
    cycle_end: '2026-07-01T00:00:00Z',
    resets_at: '2026-07-01T00:00:00Z',
    tier: 'SOLO',
  }}
/>

`resets_at` sempre repete `cycle_end` — mantido por conveniência para clientes
que só olham um campo. Estes dois endpoints (diferente de `GET /v1/usage`)
expõem `cycle_start`/`cycle_end` explicitamente porque são o snapshot de **um**
número, não um roll-up de vários.

## Janela de leitura por retenção (read-window)

Além da quota, cada tier define por quantos dias uma mensagem **permanece
consultável** pela API — mensagens mais antigas que essa janela deixam de
existir para leitura:

| Tier       | Janela de leitura |
| ---------- | -----------------:|
| `FREE`     | 7 dias            |
| `SOLO`     | 30 dias           |
| `BUSINESS` | 90 dias           |
| `CUSTOM`   | 365 dias          |

- `GET /v1/numbers/{alias}/messages/{id}` de uma mensagem mais antiga que a
  janela do tier retorna **404** (indistinguível de "nunca existiu").
- `GET /v1/numbers/{alias}/messages` (lista por cursor) **filtra** mensagens
  fora da janela — elas simplesmente não aparecem na página.
- Esta janela é sobre **visibilidade via API**; o armazenamento físico segue a
  retenção de partição fixa (12 meses) independentemente do tier — ver
  [Retenção das mensagens](/messages/retention/) para o ciclo de vida completo
  do conteúdo e dos metadados.

## Erros

### 402 — assinatura inativa

Retornado pelo pipeline de envio quando a assinatura da organization não
permite o uso de features (`ACTIVE` e `TRIALING` dentro do período de trial são
os únicos estados que passam sem restrição):

<ApiResponse
  status={402}
  body={{
    error: 'subscription_inactive',
    message: 'Subscription is not active',
    details: { status: 'trial_expired' },
  }}
/>

`details.status` é um destes valores: `trialing` (permitido, não gera este
erro), `trial_expired` (trial encerrado sem plano pago), `past_due` ou
`canceled` (após o fim do período já pago) — ou `missing` (organization sem
nenhuma assinatura; cobre também os status internos `pending`/`terminated`,
que são filtrados na camada de repositório e colapsam para `missing`, nunca
aparecendo verbatim neste campo).

### 402 — feature indisponível no plano

<ApiResponse
  status={402}
  body={{
    error: 'feature_not_available',
  }}
/>

Hoje os gates públicos desta família são: reações (`reactions`, SOLO+); indicador
de digitação (`typing_indicator`, SOLO+ — o gate base, toda chamada); envio de
mensagem ou indicador de digitação para grupo (`groups:messages`, BUSINESS+ — veja
[acima](#envio-para-grupos-exige-plano-business-ou-superior)); histórico
detalhado de recibos (`read_receipts`, BUSINESS+ — veja
[Recibos](/messages/receipts/)); e criação de números extras (`extra_numbers`,
indisponível em FREE/SOLO — veja [Números extras](/numbers/add/)).

### 402 — limite de números extras atingido

Retornado por `POST /v1/numbers` quando a organization já tem
`max_extra_numbers` números extras vivos para o tier (BUSINESS 300 / CUSTOM
1.000; FREE/SOLO não têm acesso a números extras):

<ApiResponse
  status={402}
  body={{
    error: 'extra_numbers_limit_reached',
    message: 'Extra numbers limit reached for the current plan (300/300).',
    details: { limit: 300, current: 300 },
  }}
/>

`details.limit` é o teto `max_extra_numbers` do tier; `details.current` é a
contagem atual de números extras vivos da organization.

### 402 — quota de contatos excedida

<ApiResponse
  status={402}
  body={{
    error: 'contact_quota_exceeded',
    message: 'Distinct-contacts quota exceeded for tier BUSINESS (100/100 this cycle)',
    details: { quota: 100, used: 100, resets_at: '2026-07-01T00:00:00Z', tier: 'BUSINESS' },
  }}
/>

### 429 — quota de mensagens excedida

<ApiResponse
  status={429}
  headers={{ 'Retry-After': '1' }}
  body={{
    error: 'messages_quota_exceeded',
  }}
/>

Diferente do 402 de contatos, este 429 **não** carrega `details` com
`used`/`quota`/`resets_at` no corpo — consulte
`GET /v1/numbers/{alias}/messages/quota` (ou `GET /v1/usage/messages`) para o
snapshot completo e o `resets_at` real. O cabeçalho `Retry-After` aqui é um
valor técnico curto (não representa "quanto falta para a quota renovar" — a
quota só renova em `resets_at`, que pode estar a dias de distância).

### 402 vs 429 — quando aparecem

| | 402 (contatos) | 429 (mensagens) |
| - | ------------- | ------------- |
| Sinal | Fazer upgrade de plano | Quota do ciclo esgotada |
| Cabeçalho `Retry-After` | Ausente | Presente (não confiável para saber quando a quota renova) |
| Corpo com `used`/`quota`/`resets_at` | Sim (`details`) | Não — consulte o endpoint de quota |
| Reseta em | `resets_at` (fim do ciclo avaliado) ou upgrade | `resets_at` (fim do ciclo avaliado) |

## Webhooks de quota

- `contact.quota.warning` em 80/90/95% (basis points).
- `contact.quota.exceeded` no estouro.
- `message.quota.warning` em 80/90/95%.
- `message.quota.exceeded` no estouro.

Ambas as famílias carregam `cycle_start`/`cycle_end` no `data` (substituindo o
antigo `window_days`). Veja [Eventos de quota de mensagem](/webhooks/message-quota-events/),
[Eventos de contato](/webhooks/contact-events/) e [Limites de Mensagens](/messages/rate-limits/).
