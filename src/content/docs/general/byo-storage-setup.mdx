**BYO Object Storage** (Bring Your Own) permite que o Turbo Notify armazene mídias recebidas e fotos de perfil de contatos diretamente no seu próprio bucket, sob seu controle total. Sem essa configuração, mídias inbound não ficam disponíveis para download.

## O que é BYO Object Storage

Quando um contato envia uma imagem, vídeo, áudio, documento ou figurinha para o seu número WhatsApp, o Turbo Notify:

1. Recebe a mídia da rede WhatsApp.
2. Faz upload do arquivo para o seu bucket (via S3 API).
3. Retorna uma URL pré-assinada diretamente no objeto de mídia (`image.url`, `video.url`, …) ao consultar `GET /v1/numbers/{alias}/messages/{id}`.
4. Envia o webhook `message.received` com os campos de mídia disponíveis.

Sem BYO Storage configurado, o campo `kind` retorna `"unavailable"` com `reason: "no_storage"` — os bytes da mídia não são persistidos.

## Provedores suportados

O Turbo Notify usa a S3 HTTP API como protocolo de transporte — o mesmo protocolo suportado pelos três provedores:

| Provedor | Free tier | Notas |
|----------|:---------:|-------|
| **Cloudflare R2** | Sim | Sem custo de egress; excelente para alta frequência de downloads. Consulte o site do provedor para limites atuais. |
| **Supabase Storage** | Sim | Ideal se você já usa Supabase na sua stack. Consulte o site do provedor para limites atuais. |
| **AWS S3** | Sim (Free Tier 12 meses) | Maior ecossistema de ferramentas; há custo de egress. Consulte o site da AWS para detalhes. |

:::note[Preços]
Não citamos valores específicos pois os planos dos provedores mudam. Acesse o site de cada provedor para verificar os limites e preços atuais antes de escolher.
:::

## Como configurar

### 1. Crie um bucket no provedor escolhido

O bucket deve ser **privado** (sem acesso público). O Turbo Notify acessa o conteúdo via credenciais IAM/API, não por URLs públicas.

### 2. Crie credenciais com permissões mínimas

As permissões necessárias são:

```
s3:PutObject
s3:GetObject
s3:DeleteObject
s3:ListBucket
```

Crie um usuário IAM (AWS), API token (Cloudflare R2) ou service role (Supabase) com escopo restrito ao bucket do Turbo Notify.

### 3. Configure no dashboard

Acesse <DashboardLink path="/storage">Armazenamento</DashboardLink> e preencha:

| Campo | Valor |
|-------|-------|
| **Provedor** | AWS S3, Cloudflare R2 ou Supabase Storage |
| **Bucket** | Nome do bucket criado |
| **Região** | Região do bucket (ex: `us-east-1`, `auto` para R2) |
| **Access Key ID** | Chave de acesso IAM / R2 / Supabase |
| **Secret Access Key** | Chave secreta correspondente |
| **Cloudflare Account ID** / **Supabase Project Ref** | Apenas para R2 e Supabase, respectivamente — o endpoint S3-compatible é gerado automaticamente a partir desse valor |

### 4. Valide a conexão

Após salvar, clique em **Testar conexão**. O Turbo Notify verifica o bucket (`HEAD`), grava um objeto temporário (`PUT`), lê-o de volta (`GET`) e o remove (`DELETE`) para validar as 4 permissões necessárias (`ListBucket`/`PutObject`/`GetObject`/`DeleteObject`). O resultado aparece como:

- **Conectado** — integração ativa, mídias passam a ser armazenadas imediatamente.
- **Falha** — verifique credenciais, nome do bucket e permissões.

## Comportamento após configuração

### Mídias recebidas

Toda mídia recebida após a ativação é automaticamente copiada para o seu bucket. Os campos de mídia em `GET /v1/numbers/{alias}/messages/{id}` passam a retornar `kind: "available"`, por exemplo:

```json
{
  "kind": "available",
  "url": "https://<bucket>.r2.cloudflarestorage.com/...?X-Amz-...",
  "expires_at": "2026-04-21T11:00:00Z",
  "mime_type": "image/jpeg",
  "size_bytes": 184320
}
```

O acesso à mídia expira conforme o `expires_at`. Para obter uma nova URL, consulte a mensagem novamente.

### Fotos de perfil de contatos

Com BYO Storage ativo, fotos de perfil são armazenadas no bucket e retornadas via `GET /v1/numbers/{alias}/contacts/{id}/profile-picture` como redirect 302 para a URL pré-assinada.

### Mídias anteriores à configuração

Mídias recebidas **antes** da ativação do BYO Storage permanecem com `kind: "unavailable"` — não há backfill retroativo. Apenas novas mídias são armazenadas.

## Solução de problemas

### `kind: "unavailable"` com `reason: "upload_failed"`

O upload falhou após retentativas. Possíveis causas:

- Credenciais expiradas ou com permissões insuficientes.
- Bucket deletado ou com política de acesso alterada.
- Quota do bucket atingida (verifique no console do provedor).

Acesse <DashboardLink path="/storage">Armazenamento</DashboardLink> e clique em **Testar conexão** para diagnosticar.

### `kind: "unavailable"` com `reason: "storage_circuit_open"`

O circuit breaker de storage foi ativado por falhas consecutivas. O Turbo Notify retentará automaticamente. Quando a conexão for restabelecida, você receberá o webhook `storage.recovered`.

### `kind: "pending"`

O upload está em andamento. Aguarde alguns segundos e consulte `GET /v1/numbers/{alias}/messages/{id}` novamente. Esse estado só é visível durante o processamento — o webhook `message.received` só é emitido após resolução (disponível ou indisponível).

## Segurança

- Credenciais são armazenadas encriptadas (AES-256-GCM) — nunca em texto claro.
- O Turbo Notify nunca expõe credenciais em logs ou respostas.
- URLs pré-assinadas têm validade configurável (padrão: 15 minutos; configurável até 1 hora).
- Recomendamos política de acesso **least-privilege** — escopo restrito ao bucket do Turbo Notify.
