Eventos relacionados con la **cuota de mensajes por número**, medida contra el
**ciclo de facturación evaluado** de la organización (`cycle_start`/`cycle_end`
— ya no una ventana rolling de 30 días). Límites por tier: `FREE`=300,
`SOLO`=1.8k, `BUSINESS`=50k, `CUSTOM`=500k **por número, por ciclo**.

Desde la ADR 2026-07-02 la cuota de mensajes es **por número** — reflejando la
cuota de contactos: cada número vinculado (`main` o el alias de un número
extra) tiene su propia franquicia, así que una organización con N números
obtiene N× la franquicia del tier. Estos eventos identifican el número
afectado vía **`number_alias` en el envelope** (no en `data`). Solo los
mensajes enviados **vía Turbo Notify** (`origin: "tn"`) consumen la cuota.

> **Nota (2026-05-15):** el enforcement de esta cuota se activó el 2026-05-15.
> Los límites ya estaban documentados — desde esa fecha el código los aplica
> efectivamente. Ver [Per-Tier Message Quota Activation](/es/changelog/2026-05-15-message-quota-activation/)
> y la [auditoría de límites](/es/messages/rate-limits/).

## Eventos

| Evento | Cuándo |
| ------ | ------ |
| `message.quota.warning` | Cruzó el threshold 80/90/95% de la cuota de mensajes del número |
| `message.quota.exceeded` | Un envío fue rechazado por agotamiento (HTTP 429) |

## `number_alias` en el envelope

Ambos eventos llevan, justo debajo de `organization_id`, el campo
`number_alias`: el handle del número TN ("inbox") cuya cuota de mensajes se
alcanzó — `"main"` para el número principal o el alias de un número extra. El
`data` del evento lleva los campos de cuota `threshold_bps` (solo en
`warning`), `used`, `quota`, `cycle_start`, `cycle_end`, `resets_at`, `tier`,
`channel`, `origin` — `number_alias` va en el **envelope**, nunca en `data`.

> **Ciclo evaluado (2026-07-04):** el antiguo campo `window_days` fue
> **retirado** — `used`/`quota` ahora se miden contra el ciclo de facturación
> evaluado de la organización, representado por `cycle_start`/`cycle_end` (ISO
> 8601 UTC). `resets_at` sigue siendo igual a `cycle_end`.

> Entre los eventos de cuenta, `number_alias` se omite **solo** en
> `storage.*`. Toda familia `*.quota.*` (contactos y mensajes) ahora lo lleva.

## Ejemplo: `message.quota.warning`

```json
{
  "id": "evt_...",
  "type": "message.quota.warning",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:00Z",
  "data": {
    "threshold_bps": 80,
    "used": 240,
    "quota": 300,
    "cycle_start": "2026-06-01T00:00:00Z",
    "cycle_end": "2026-07-01T00:00:00Z",
    "resets_at": "2026-07-01T00:00:00Z",
    "tier": "FREE",
    "channel": "whatsapp",
    "origin": "tn"
  }
}
```

## Ejemplo: `message.quota.exceeded`

```json
{
  "id": "evt_...",
  "type": "message.quota.exceeded",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:00Z",
  "data": {
    "quota": 300,
    "used": 300,
    "cycle_start": "2026-06-01T00:00:00Z",
    "cycle_end": "2026-07-01T00:00:00Z",
    "resets_at": "2026-07-01T00:00:00Z",
    "tier": "FREE",
    "channel": "whatsapp",
    "origin": "tn"
  }
}
```

## Timestamps y correlación

- Estos son eventos **sintéticos** de Turbo Notify (no reflejan una acción en
  WhatsApp): desde 2026-06-02 **no** llevan `at` en `data` — solo el
  `created_at` del envelope (momento en que TN emitió el evento).
- `cycle_start`/`cycle_end` son el ciclo de facturación evaluado contra el que
  se midieron `used`/`quota`. `resets_at` es un timestamp de **valor de
  negocio** (cuándo resetea el ciclo de cuota), mantenido con su nombre
  semántico — igual a `cycle_end` en la emisión, no es el momento de la
  ocurrencia.
- No hay `phone` en el payload de estos eventos. Para correlacionar con la
  solicitud que disparó el rechazo, usa `GET /v1/events?request_id=req_...`.
