**Data:** 2026-06-22
**Status:** Aplicado

:::note[Atualização 2026-06-25]
As rotas planas mencionadas como "404" nesta entrada foram **reintroduzidas**
três dias depois como um tier de acesso direto válido ao número principal —
veja [Rotas flat para o número principal](/changelog/2026-06-25-flat-main-routes/).
Hoje `/v1/messages`, `/v1/contacts` e `/v1/groups` (+ sub-rotas) **nunca
retornam 404** por serem flat: funcionam como equivalentes de
`/v1/numbers/main/…`, com resposta idêntica. O 404 descrito abaixo foi real
apenas na janela entre 2026-06-22 e 2026-06-25.
:::

:::caution[Mudança de rota — quebra de compatibilidade em 2026-06-22]
Esta foi uma **mudança de rota** que quebrou a compatibilidade. Toda chamada a
mensagens, contatos e grupos precisou migrar para o caminho aninhado abaixo do
número (`/v1/numbers/{alias}/…`). Entre 2026-06-22 e 2026-06-25, as rotas
planas antigas (`/v1/messages`, `/v1/contacts`, `/v1/groups` e suas
sub-rotas) retornavam **404** — desde 2026-06-25 elas voltaram a funcionar
como forma curta para o número principal (veja a nota acima).
:::

## O que mudou

### Mensagens, contatos e grupos sempre abaixo do número

Mensagens, contatos e grupos passam a estar **sempre associados a um número** da
sua organização. Isso é expresso de forma **estrutural** na API: as rotas
residem abaixo da rota do número, identificado pelo `{alias}` (`main` para o
número principal ou o alias de um número extra).

| Antes (rota plana, aninhamento obrigatório em 2026-06-22) | Agora (aninhado por número) |
| ------------------------- | --------------------------- |
| `POST /v1/messages` | `POST /v1/numbers/{alias}/messages` |
| — (não havia lista pública) | `GET /v1/numbers/{alias}/messages` (lista por cursor — **novo**) |
| `GET /v1/messages/{id}` | `GET /v1/numbers/{alias}/messages/{id}` |
| `GET /v1/messages/{id}/status` | `GET /v1/numbers/{alias}/messages/{id}/status` |
| `GET /v1/messages/{id}/reactions` | `GET /v1/numbers/{alias}/messages/{id}/reactions` |
| `GET /v1/messages/{id}/receipts` | `GET /v1/numbers/{alias}/messages/{id}/receipts` |
| `POST /v1/messages/{id}/reply` | `POST /v1/numbers/{alias}/messages/{id}/reply` |
| `POST /v1/messages/{id}/edit` | `POST /v1/numbers/{alias}/messages/{id}/edit` |
| `POST /v1/messages/{id}/delete` | `POST /v1/numbers/{alias}/messages/{id}/delete` |
| `POST /v1/messages/{id}/react` | `POST /v1/numbers/{alias}/messages/{id}/react` |
| `POST /v1/typing-indicator` | `POST /v1/numbers/{alias}/typing-indicator` |
| `GET /v1/contacts` | `GET /v1/numbers/{alias}/contacts` |
| `GET /v1/contacts/{id}` | `GET /v1/numbers/{alias}/contacts/{id}` |
| `GET /v1/contacts/{id}/profile-picture` | `GET /v1/numbers/{alias}/contacts/{id}/profile-picture` |
| `GET /v1/contacts/quota` | `GET /v1/numbers/{alias}/contacts/quota` |
| `POST /v1/contacts/{id}/refresh` | `POST /v1/numbers/{alias}/contacts/{id}/refresh` |
| `GET /v1/groups` | `GET /v1/numbers/{alias}/groups` |
| `GET /v1/groups/{id}` | `GET /v1/numbers/{alias}/groups/{id}` |
| `GET /v1/groups/{id}/picture` | `GET /v1/numbers/{alias}/groups/{id}/picture` |

### O envio não aceita mais `from` no body

Como o remetente agora é o número do path, o campo `from` no corpo de envio foi
**removido**. Para enviar a partir do número principal use
`POST /v1/numbers/main/messages`; para um número extra use o alias dele
(`POST /v1/numbers/{alias}/messages`). O campo `to` (destinatário) permanece
inalterado e continua aceitando `number`, `group_id` ou `contact_id`.

### Identificadores únicos, mas não endereçáveis sozinhos

Os ids públicos (`msg_…`, `ct_…`, `grp_…`) continuam globalmente únicos, mas
**não são mais endereçáveis sozinhos**: para ler ou agir sobre um recurso por id
você precisa do `number_alias` ao qual ele pertence. Esse handle está **sempre
presente no envelope** de todo webhook, item de `GET /v1/events` e resposta de
envio — leia-o de lá e use-o nas chamadas por id subsequentes. Tentar acessar um
id sob o alias errado retorna **404**.

### Chave de idempotência por alias

O escopo da chave de idempotência (`Idempotency-Key`) passa a ser
`(organização, number_alias, chave)`. A mesma chave em dois aliases diferentes
produz **dois envios independentes**.

### `contact.quota.*` agora por número

Os eventos `contact.quota.warning` e `contact.quota.exceeded` passam a carregar
o campo **`number_alias` no envelope** (logo abaixo de `organization_id`),
identificando o número cuja quota de contatos foi atingida. O `data` do evento
permanece inalterado. `number_alias` continua **omitido** apenas em `storage.*` e,
neste momento (2026-06-22), também nos eventos de quota de mensagem
(`message.quota.*`) — a cota de mensagem ainda era por organização.

:::note[Atualização 2026-07-02]
A [ADR 2026-07-02 — Per-Number Message Quota](/reference/decisions/2026-07-02-per-number-message-quota/)
tornou a cota de mensagem **por número** também. Desde então, `message.quota.warning`
e `message.quota.exceeded` **também carregam `number_alias`** no envelope — a regra
de omissão estreita para **somente `storage.*`**, igual à de `contact.quota.*`.
:::

### `GET /v1/events` aceita o filtro `number_alias`

A rota de polling `GET /v1/events` ganha um parâmetro opcional **`number_alias`**
que restringe a resposta aos eventos de um único número. As superfícies de conta
(`GET /v1/usage`, `GET /v1/usage/messages`, `GET /v1/events`, `storage.*`)
permanecem **no nível raiz** e não foram afetadas pela mudança de rota.

## Compatibilidade

Pré-produção: a mudança quebrou a compatibilidade sem camada de transição.
As rotas planas retornaram 404 imediatamente **entre 2026-06-22 e
2026-06-25** — desde então voltaram como forma curta válida para o número
principal ([detalhes](/changelog/2026-06-25-flat-main-routes/)). Migre
chamadas de números extras para o caminho aninhado (`/v1/numbers/{alias}/…`)
e passe a ler o `number_alias` do envelope para chamadas por id — isso vale
independentemente de qual tier de rota (plana ou aninhada) você usa.
