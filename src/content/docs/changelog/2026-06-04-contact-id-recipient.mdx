**Data:** 2026-06-04
**Status:** Aplicado

## O que mudou

> Nota: na data desta mudança a rota era a plana `POST /v1/messages`. Depois ela foi
> aninhada sob o número — hoje use `POST /v1/numbers/{alias}/messages`
> ([2026-06-22](/changelog/2026-06-22-number-scoped-routes/)).

O campo `to` em `POST /v1/messages` agora aceita três formas mutuamente exclusivas:

| Forma | Exemplo | Quando usar |
| ----- | ------- | ----------- |
| `number` | `{"number": "+5511999999999"}` | Você tem o telefone E.164 |
| `group_id` | `{"group_id": "grp_..."}` | Destinatário é um grupo WhatsApp |
| `contact_id` | `{"contact_id": "ct_..."}` | Você tem o ID do contato no Turbo Notify |

Nenhuma das formas anteriores foi alterada — a mudança é **aditiva**.

## Novo formato do campo `to`

```json
{
  "to": { "contact_id": "ct_a1b2c3d4e5f6789012345678901234ab" },
  "content": {
    "text": "Olá, sua solicitação foi processada."
  }
}
```

O Turbo Notify resolve o telefone a partir do registro do contato no momento do envio. O contato deve pertencer à mesma organização da chave de acesso usada.

## Novos códigos de erro

| Código | HTTP | Significado |
| ------ | ---- | ----------- |
| `contact_not_found` | 400 | O `contact_id` informado não existe para esta organização |
| `contacts_not_enabled` | 400 | O recurso Contatos não está provisionado para esta organização |

## Por que usar `contact_id`

Se o seu sistema já armazena o `ct_` dos contatos do Turbo Notify (por exemplo, a partir de webhooks `contact.created`), não é necessário manter um mapeamento separado de telefone. Você passa o `contact_id` diretamente e o Turbo Notify faz a resolução internamente.
