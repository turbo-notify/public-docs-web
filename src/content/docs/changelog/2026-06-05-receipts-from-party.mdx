**Data:** 2026-06-05
**Status:** Aplicado

## O que mudou

> Nota: na data desta mudança estas rotas eram as planas `GET /v1/messages/{id}/receipts`
> e `.../reactions`. Depois foram aninhadas sob o número — hoje use
> `GET /v1/numbers/{alias}/messages/{id}/receipts` e `.../reactions`
> ([2026-06-22](/changelog/2026-06-22-number-scoped-routes/)).

Cada item em `receipts[]` agora inclui um objeto `from` com a identidade da parte que confirmou a entrega ou leitura — alinhando o endpoint com o padrão já existente em `GET /v1/messages/{id}/reactions`.

| Campo | Tipo | Descrição |
| ----- | ---- | --------- |
| `from.number` | string | Número E.164 sem `+`. Omitido para recibos de dispositivo vinculado (LID). |
| `from.contact_id` | string | Identificador público do contato TN (`ct_{hex32}`). Omitido quando não disponível. |
| `from.name` | string | Nome de exibição WhatsApp (PII — propriedade do organization). Omitido quando não disponível. |

O objeto `from` inteiro é omitido em recibos legados (pré-2026-06) e quando nenhuma informação de identidade está disponível.

## Exemplo de resposta

```json
{
  "message_id": "msg_0198d3c5a1b24d3e9f01a2b3c4d5e6f7",
  "receipts": [
    {
      "from": {
        "contact_id": "ct_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
        "name": "João Silva",
        "number": "5511999990000"
      },
      "status": "delivered",
      "at": "2025-07-16T10:00:05Z"
    },
    {
      "from": {
        "contact_id": "ct_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
        "name": "João Silva",
        "number": "5511999990000"
      },
      "status": "read",
      "at": "2025-07-16T10:01:12Z"
    }
  ]
}
```

## Compatibilidade

A mudança é **aditiva** — respostas anteriores sem o campo `from` permanecem válidas. Clientes que já ignoram campos desconhecidos não precisam de alteração.
