O Turbo Notify disponibiliza uma API de eventos que permite consultar o histórico de eventos da sua conta de forma paginada. Use o polling como alternativa ao webhook ou para reconciliar eventos que possam ter sido perdidos durante uma indisponibilidade do seu endpoint.

## Quando usar polling

O webhook é a forma principal de receber eventos em tempo real. O polling é recomendado em dois cenários:

- **Sem webhook configurado**: consulte eventos regularmente para processar mensagens recebidas, confirmações de envio e demais notificações.
- **Recuperação após falha**: após uma interrupção do seu endpoint de webhook, use o polling para buscar os eventos perdidos e reconciliar o estado do seu sistema.

## Endpoint

```
GET /v1/events
```

**Escopo obrigatório:** `events:read`

## Parâmetros de consulta

| Parâmetro | Tipo | Descrição |
| --------- | ---- | --------- |
| `types[]` | string[] | Filtrar por tipos de evento (OR). Ex: `types[]=message.received&types[]=message.sent` |
| `type` | string | Filtrar por um tipo de evento com suporte a wildcard. Ex: `type=message.*` |
| `request_id` | string | Filtrar pelos eventos gerados por uma única requisição assíncrona (`req_…`). Útil para correlacionar o resultado de um `POST` (envio, resposta, edição ou exclusão) usando o `X-Request-ID` retornado no header da resposta. **Reações não são correlacionáveis por aqui**: o header devolvido no `POST .../react` não é um `req_…` válido; use o `message_id` da mensagem-alvo (veja [Enviar reação](/other-features/reaction/)). Ex: `request_id=req_01993c5a1b24d3e9f01a2b3c4d5e6f70` |
| `number_alias` | string | Filtrar pelos eventos de um único número (`"main"` ou o alias de um número extra). Ausente = todos os números da organização. Apenas os eventos sem número único (`storage.*` **e** `media.unavailable`) são excluídos quando este filtro é informado; `message.quota.*` é por número e é filtrável. |
| `starting_after` | string | Cursor para paginação progressiva. Passe o `id` do último item da página anterior. |
| `ending_before` | string | Cursor para paginação retroativa. Passe o `id` do primeiro item da página atual. |
| `limit` | integer | Número de eventos por página. Intervalo: 1–100. Padrão: 25. |
| `created[gte]` | ISO-8601 | Retornar eventos criados a partir deste timestamp. |
| `created[lte]` | ISO-8601 | Retornar eventos criados até este timestamp. |

### Envelope da lista

| Campo | Tipo | Descrição |
| ----- | ---- | --------- |
| `object` | string | Sempre `"list"`. |
| `data` | array | Lista de eventos (no máximo `limit` itens). |
| `has_more` | boolean | `true` quando existem mais eventos além da página atual. |

### Envelope de cada evento

| Campo | Tipo | Descrição |
| ----- | ---- | --------- |
| `id` | string | Identificador único (`evt_…`). Use como chave de idempotência. |
| `type` | string | Tipo do evento (ex.: `message.received`). |
| `organization_id` | string | Identificador público da sua organização (`org_{hex32}`). |
| `number_alias` | string | Handle do número Turbo Notify ao qual o evento pertence: `"main"` para o número principal ou o alias de um número extra. É a **string do alias**, nunca um UUID. Presente em eventos ligados a um número específico: `message.*`, `number.*`, `group.*` e **todos** os `contact.*` (inclusive `contact.quota.*`) e `message.quota.*` (a quota de mensagens é por número). **Omitido** em `storage.*` **e** em `media.unavailable`: os eventos que não pertencem a um número único. |
| `created_at` | string | Momento de **emissão do evento pelo Turbo Notify** (quando o registro foi criado/publicado). ISO 8601 em UTC com sufixo `Z` e precisão de segundos (ex.: `2026-06-01T13:00:05Z`). Distinto de `data.at` (o momento da ação no WhatsApp), quando presente. |
| `data` | object | Payload específico do evento, **idêntico** ao entregue via webhook. Quando há uma ação real no WhatsApp, `data.at` traz esse momento (valor distinto de `created_at`), inclusive para eventos **outbound** (`message.sent`/`replied`/`edited`/`deleted` + `*.failed`) e os `number.*` de ação real, cujo `at` é o momento genuíno do WhatsApp, tipicamente anterior ao `created_at`. Eventos sintéticos não têm `at`. |

## Paginação por cursor

A paginação é baseada em cursor, o que garante páginas estáveis mesmo enquanto novos eventos chegam. O cursor é o `id` de um evento.

Os eventos vêm **do mais novo para o mais antigo**, e é isso que decide qual cursor usar:

| Você quer | Use | Direção |
|---|---|---|
| Acompanhar o que acabou de acontecer | `ending_before` | Eventos **mais novos** que o cursor |
| Percorrer o histórico | `starting_after` | Eventos **mais antigos** que o cursor |

:::caution[Para acompanhar mensagens novas, o cursor é `ending_before`]
`starting_after` avança para trás no tempo. Se você guardar o último evento processado e passá-lo em `starting_after` num laço, vai receber eventos cada vez mais antigos e **nunca** alcançar os novos. Guarde o `id` do **primeiro** evento da página (o mais recente) e passe-o em `ending_before`. Uma resposta vazia quer dizer que você está em dia.
:::

:::caution[Uma página cheia quer dizer que sobrou coisa de fora]
A resposta sempre traz os eventos **mais recentes** que cabem no `limit`, então se chegaram mais eventos do que o `limit` entre duas consultas, os que ficaram de fora são os **mais antigos** do lote. Se você guardar só o primeiro `id` da página e seguir em frente, esses eventos ficam para trás e não voltam mais.

A regra é simples: **página cheia significa que há mais**. Use `limit=100` e, sempre que a página vier cheia, continue lendo com `starting_after` a partir do último evento dela até reencontrar o cursor que você já tinha. Uma organização que envia 150 mensagens por minuto gera receipts junto: um lote de mais de 20 eventos entre duas consultas é rotina.
:::

**Acompanhar eventos novos**: peça o que chegou depois do último evento processado e, se a página vier cheia, desça até alcançá-lo.

    ```js title="acompanhar.js"
    const LIMITE = 100;
    let ultimoVisto = null;

    async function pagina(params) {
      const response = await fetch(
        `https://api.turbonotify.com/v1/events?${params}`,
        { headers: { 'Authorization': 'Bearer SUA_CHAVE' } }
      );
      return (await response.json()).data;
    }

    async function buscarNovidades() {
      const params = new URLSearchParams({ limit: String(LIMITE) });
      if (ultimoVisto) params.set('ending_before', ultimoVisto);

      let atual = await pagina(params);
      // Vazio: você está em dia.
      if (atual.length === 0) return [];

      const lote = [...atual];

      // Página cheia com um cursor conhecido: chegou mais do que coube, e o
      // que falta é mais antigo que o último desta página. Desça até
      // reencontrar o cursor anterior.
      while (ultimoVisto && atual.length === LIMITE) {
        atual = await pagina(new URLSearchParams({
          limit: String(LIMITE),
          starting_after: lote[lote.length - 1].id,
        }));
        for (const evento of atual) {
          if (evento.id === ultimoVisto) { atual = []; break; }
          lote.push(evento);
        }
      }

      // O primeiro do lote é o mais recente: é ele que vira o próximo cursor.
      ultimoVisto = lote[0].id;
      return lote;
    }
    ```

    ```python title="acompanhar.py"
    import requests

    LIMITE = 100
    ultimo_visto = None

    def pagina(**params):
        response = requests.get(
            "https://api.turbonotify.com/v1/events",
            headers={"Authorization": "Bearer SUA_CHAVE"},
            params={"limit": LIMITE, **params},
        )
        return response.json()["data"]

    def buscar_novidades():
        global ultimo_visto
        atual = pagina(ending_before=ultimo_visto) if ultimo_visto else pagina()

        # Vazio: você está em dia.
        if not atual:
            return []

        lote = list(atual)

        # Página cheia com um cursor conhecido: chegou mais do que coube, e o
        # que falta é mais antigo que o último desta página. Desça até
        # reencontrar o cursor anterior.
        while ultimo_visto and len(atual) == LIMITE:
            atual = pagina(starting_after=lote[-1]["id"])
            for evento in atual:
                if evento["id"] == ultimo_visto:
                    atual = []
                    break
                lote.append(evento)

        # O primeiro do lote é o mais recente: é ele que vira o próximo cursor.
        ultimo_visto = lote[0]["id"]
        return lote
    ```

    ```js title="polling.js"
      const todos = [];

      while (true) {
        const params = new URLSearchParams({ limit: '20' });
        if (startingAfter) params.set('starting_after', startingAfter);

        const response = await fetch(
    ```

    ```python title="polling.py"
      headers = {"Authorization": "Bearer SUA_CHAVE"}
      todos = []
      starting_after = None

          params = {"limit": 20}
          if starting_after:
              params["starting_after"] = starting_after
    ```

## Intervalo recomendado

O endpoint de polling não tem um limitador dedicado: ele compartilha o rate limit geral de ingresso da API, **1000 requisições/segundo por organização** (`api_requests_per_second`). Ultrapassar esse teto resulta em `429 Too Many Requests` (`rate_limit_exceeded`), mas na prática ele é bem mais permissivo do que um intervalo fixo entre chamadas de polling.

Para sistemas de alta demanda, prefira o uso de webhooks para receber eventos em tempo real e reserve o polling para reconciliação.

## Paridade com webhooks

O objeto `data` de cada evento retornado pela API é **byte-a-byte idêntico** ao `data` entregue via webhook para o mesmo evento. O envelope é o mesmo em ambos os canais:

| Campo | Webhook | Polling |
| ----- | ------- | ------- |
| `id` | presente | presente |
| `type` | presente | presente |
| `organization_id` | presente | presente |
| `number_alias` | presente (em eventos ligados a um número) | presente (em eventos ligados a um número) |
| `created_at` | presente | presente (mesmo valor) |
| `data` | **idêntico** | **idêntico** |

Isso permite:

- Sistemas que usam **apenas polling** processam os mesmos dados que sistemas baseados em webhook.
- Sistemas **híbridos** podem usar a API para reconciliar eventos perdidos reaproveitando o mesmo código de processamento.
- Catálogo completo de `type` e `data`: consulte a [referência de eventos no documento de webhook](/messages/webhook/#tipos-de-evento).
- Exemplos de payload por `content_type` (texto, mídia, localização, calendário): [Exemplos por content_type](/messages/webhook/#exemplos-por-content_type-inbound).

A paridade inclui o campo [`data.mentions`](/messages/webhook/#campos-da-mensagem):
quando uma mensagem menciona alguém, os eventos
`message.received`/`message.replied`/`message.sent`/`message.edited` retornados
pelo polling carregam exatamente a mesma lista `mentions` e o mesmo `preview`
(cada token de menção conta como 1 caractere), entregues via webhook,
byte-a-byte.

## Recuperação após falha de webhook

Para recuperar eventos perdidos durante uma indisponibilidade do seu endpoint:

1. Identifique o timestamp aproximado do início da falha.
2. Consulte `GET /v1/events?created[gte]=<timestamp_da_falha>` para buscar os eventos do período.
3. Processe apenas os eventos não vistos usando o `id` de cada evento como chave de idempotência.

## Retenção de eventos

`GET /v1/events` aplica a **janela de retenção de conteúdo do seu plano** (a mesma que governa `GET /v1/numbers/{alias}/messages/{id}`: veja [Retenção das mensagens](/messages/retention/)) como limite inferior de `created_at` da consulta. Eventos mais antigos que essa janela **não são retornados**, e isso vale para todas as famílias de evento, não apenas `message.*`. Numa organização no padrão de 3 dias, por exemplo, o polling enxerga os últimos 3 dias de eventos.

O registro do evento em si é descartado fisicamente após **30 dias**, um horizonte fixo da plataforma. O que você observa na prática é sempre o menor dos dois prazos.

## Erros possíveis

| Status | Código de erro | Descrição |
| :----: | -------------- | --------- |
| `400` | `invalid_event_id` | O cursor fornecido em `starting_after` ou `ending_before` não é um id de evento válido (`evt_` + 32 hex). Um cursor bem formado mas inexistente não gera erro. O filtro é simplesmente ignorado. |
| `400` | `invalid_request_id` | O `request_id` informado não é um id de requisição válido (`req_` + 32 hex). O `X-Request-ID` devolvido em respostas `GET` é um UUID de correlação, **não** um `req_…`. Só o header devolvido pelos `POST` assíncronos serve como filtro aqui. |
| `403` | `not_authorized` | A chave de acesso está inválida ou ausente. |
| `403` | `insufficient_scope` | A chave de acesso não possui o escopo `events:read` (resposta inclui `required_scope`). |
| `422` | `validation_error` | Um parâmetro de consulta não passou na validação (por exemplo `limit` fora do intervalo 1–100 ou `created[gte]`/`created[lte]` em formato não-ISO-8601). A resposta traz `details.errors` com os campos rejeitados. |
| `429` | `rate_limit_exceeded` | Limite de requisições ultrapassado. Aguarde antes de tentar novamente. |
| `500` | `internal_error` | Erro interno inesperado no servidor. |
