O Turbo Notify notifica seu sistema sobre eventos — envio confirmado, entrega, leitura, mensagem recebida, reação, falha — via webhook (HTTP POST). O objeto `data` de cada evento é **idêntico** ao retornado pelo endpoint [`GET /events`](/messages/polling/); a diferença entre os dois canais está apenas no envelope (campos `timestamp` vs `created_at` e a presença do tag `object: "event"` no polling).

## Recebimento dos eventos

Para começar a receber eventos, cadastre a URL do seu webhook no <DashboardLink path="/webhook">Dashboard</DashboardLink>. A URL deve ser pública, acessível via HTTPS e responder com status `2xx` dentro de 5 segundos.

:::tip[Inspecione e aprenda em tempo real]
Antes de plugar o webhook na sua aplicação, abra o <ExternalLink href="https://webhook.turbonotify.com">Webhook Inspector</ExternalLink> e cadastre a URL gerada. O Inspector recebe cada delivery em tempo real (via WebSocket), exibe headers/body completos, valida a assinatura HMAC interativamente e sugere a próxima chamada REST típica para cada tipo de evento (`message.received` → `GET /v1/messages/{id}`).
:::

## Privacidade

Recomendamos que sua URL de webhook não exponha informações sensíveis, como chaves de acesso ou identificadores internos. Use caminhos genéricos e valide a autenticidade da requisição pelo cabeçalho de assinatura.

## Segurança

Toda requisição de webhook enviada pelo Turbo Notify inclui os cabeçalhos abaixo. Utilize a assinatura para garantir que a requisição foi realmente enviada pelo Turbo Notify e não por terceiros.

| Header | Descrição |
|--------|-----------|
| `X-Webhook-Signature` | `sha256=<hex>` — HMAC-SHA256 de `{X-Webhook-Timestamp}.{raw_body}` com seu segredo. |
| `X-Webhook-Timestamp` | Unix epoch (segundos) — utilize para rejeitar deliveries com mais de ~5 minutos (proteção contra replay). |
| `X-Webhook-Attempt` | Número da tentativa atual (começa em 1, incrementa nos retries). |
| `X-Webhook-Max-Attempts` | Total de tentativas que o Turbo Notify fará antes de desistir. |
| `User-Agent` | `TurboNotify-Webhook/1.0` — útil para WAF allowlists. |

O segredo para validação está disponível no <DashboardLink path="/webhook">Dashboard</DashboardLink>, na mesma seção onde você cadastra a URL.

Exemplo de validação da assinatura:

```python title="validacao.py"
import hmac
import hashlib

def verificar_assinatura(payload: bytes, timestamp: str, assinatura: str, segredo: str) -> bool:
    dados_assinados = f"{timestamp}.".encode() + payload
    esperado = "sha256=" + hmac.new(
        segredo.encode(),
        dados_assinados,
        hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(esperado, assinatura)

# Uso:
# timestamp = request.headers["X-Webhook-Timestamp"]
# assinatura = request.headers["X-Webhook-Signature"]
# verificar_assinatura(request.body, timestamp, assinatura, segredo)
```

```js title="validacao.js"
const crypto = require('crypto');

function verificarAssinatura(payload, timestamp, assinatura, segredo) {
  const dadosAssinados = `${timestamp}.${payload}`;
  const esperado = 'sha256=' + crypto
    .createHmac('sha256', segredo)
    .update(dadosAssinados)
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(esperado),
    Buffer.from(assinatura)
  );
}

// Uso:
// const timestamp = req.headers['x-webhook-timestamp'];
// const assinatura = req.headers['x-webhook-signature'];
// verificarAssinatura(req.body, timestamp, assinatura, segredo);
```

## Estrutura do evento

Toda requisição de webhook segue a mesma estrutura base:

| Propriedade  | Tipo                | Descrição                                                                 |
| ------------ | ------------------- | ------------------------------------------------------------------------- |
| `id`         | `string`            | Identificador único do evento (`evt_…`). Use como chave de idempotência.  |
| `type`       | `string`            | Tipo do evento (ex.: `message.sent`).                                     |
| `timestamp`  | `string`            | Data e hora do evento em ISO 8601 UTC, com sufixo `Z`. O endpoint de polling expõe o mesmo instante sob o nome `created_at` — divergência mantida por compatibilidade. |
| `request_id` | `string \| null`    | ID de rastreamento da requisição que originou o evento. **Sempre presente** — `null` para eventos operacionais sem requisição original (ex.: `number.connected`). |
| `data`       | `object`            | Dados específicos do evento (veja a tabela em [Tipos de evento](#tipos-de-evento)). |

:::note[Receipts e direção]
Os eventos `message.delivered` e `message.read` representam **confirmações de leitura/entrega vindas do destinatário**. Por isso `direction` é sempre `"inbound"` (a confirmação chegou do peer), mas `from`/`to` carregam as partes da **mensagem outbound original** — `from` é o seu número (com `alias`), `to` é o número do destinatário. Não confunda com `message.received`, em que `direction="inbound"` reflete uma mensagem nova vinda do contato.
:::

### Exemplo — `message.sent` (outbound)

```json title="webhook-payload.json"
{
  "id": "evt_abc123def456789012345678",
  "type": "message.sent",
  "timestamp": "2026-04-22T10:00:05Z",
  "request_id": "req_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "data": {
    "message_id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "direction": "outbound",
    "from": { "number": "5511999990001", "alias": "main", "name": "Turbo Notify" },
    "to":   { "number": "5511999990002", "name": "João Silva" },
    "content_type": "text",
    "preview": "Sua mensagem...",
    "sent_at": "2026-04-22T10:00:05Z"
  }
}
```

`from.alias` é sempre preenchido. Use `"main"` para identificar o número principal ou o alias do número extra (ex.: `"vendas-sp"`).

`content_type` e `preview` espelham `message.received` — `text`,
`image`, `audio`, `video`, `document`, `sticker`, `location`,
`contact` ou `calendar`. Para o body completo (vCard, coordenadas,
descrição do evento, etc.), faça `GET /v1/messages/{message_id}`.

### Exemplo — `message.received` (inbound)

```json title="webhook-payload.json"
{
  "id": "evt_def789abc234567890123456",
  "type": "message.received",
  "timestamp": "2026-04-24T15:32:11Z",
  "data": {
    "message_id": "msg_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
    "direction": "inbound",
    "from": { "number": "5511777777777", "name": "João Silva" },
    "to":   { "number": "5511999990001", "alias": "main", "name": "Turbo Notify" },
    "content_type": "text",
    "preview": "Olá, gostaria de saber...",
    "received_at": "2026-04-24T15:32:11Z"
  }
}
```

`from.name` traz o nome de exibição que o contato configurou no WhatsApp (push name); o campo é omitido quando o contato não definiu nenhum. `to.alias` resolve para `"main"` quando a mensagem chegou no número principal ou para o alias do número extra que recebeu. `to.name` traz o nome de exibição do número Turbo Notify que recebeu a mensagem (capturado na conexão via WhatsApp); omitido se não disponível.

### Exemplo — `message.received` (grupo)

Disponível desde 2026-05-24. Quando uma mensagem chega de um **grupo WhatsApp**,
`to` carrega `group_id` + snapshot `name` em vez de `number`; e um campo
`member` top-level identifica a linha Turbo Notify que participa do grupo.
`from` continua sendo o participante que enviou — pessoas sempre falam, nunca grupos.
Para mensagens 1:1 (não-grupo) `to.group_id` e `member` são omitidos — payloads
pré-existentes permanecem byte-idênticos.

```json title="message.received (grupo)"
{
  "id": "evt_c00a44c3fc774698b0f130d40bb5f104",
  "type": "message.received",
  "timestamp": "2026-05-25T22:55:14Z",
  "data": {
    "message_id": "msg_e95500cc03c1492e81e46a77c1f0d420",
    "direction": "inbound",
    "from": {
      "number": "5571999258283",
      "name": "Cleverson",
      "contact_id": "ct_45f2ece8a66a4eeaa661aeb9b8e58c77"
    },
    "to": {
      "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a",
      "name": "TNT"
    },
    "member": {
      "number": "5511973117056",
      "alias": "main"
    },
    "content_type": "text",
    "preview": "Bom dia pessoal",
    "received_at": "2026-05-25T22:55:14Z"
  }
}
```

- `to.group_id` é o identificador público do grupo no formato `grp_{hex32}` — estável por tenant e referenciável em chamadas futuras. Nunca exponemos o JID bruto do WhatsApp.
- `to.name` é o nome atual do grupo (snapshot no momento do evento). Pode ser `null` quando o nome ainda não foi hidratado — uma chamada `GET /v1/messages/{id}` após alguns segundos costuma trazer o nome resolvido.
- `member` identifica a linha Turbo Notify que participa do grupo (`number` + `alias`). Essencial quando o tenant tem múltiplos números extras e precisa saber qual deles está no grupo.
- Para detectar mensagens de grupo o cliente verifica `"group_id" in data.to` — 1:1 nunca carrega esse campo.

### Exemplo — `message.replied` (inbound/outbound)

Disponível desde 2026-04-28. Replies (mensagens que citam outra) são entregues como evento dedicado em vez de `message.sent`/`message.received`. Carrega qualquer `content_type` (text/image/video/audio/document/sticker/location/contact/calendar) — o tipo real do conteúdo é preservado, e a discriminação como reply vem do campo `quoted_message_id` (sempre presente neste evento).


Para responder uma mensagem via API, envie `POST /v1/messages` com `quoted_message_id` apontando para a mensagem citada (qualquer mensagem do chat, inbound ou outbound). Veja [/messages/send/](/messages/send/).

`quoted_message_id` é sempre o id público (`msg_{hex32}`) da mensagem citada. Use `GET /v1/messages/{quoted_message_id}` para recuperar o conteúdo completo da mensagem original.

### Exemplo — `message.delivered` / `message.read` (receipt inbound)

Receipts são sempre **inbound** — o peer A confirma a entrega/leitura de uma mensagem que o seu número (B) enviou. O evento carrega `direction: "inbound"` (indicando que o recibo veio do peer) e as **parties da mensagem original** (seu número em `from`, o peer em `to`) com snapshot do conteúdo original (`content_type` + `preview`) para facilitar debug sem `GET /v1/messages/{id}` extra.

```json title="message.delivered"

    "message_id": "msg_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
    "direction": "inbound",
    "from": { "number": "5511999990001", "alias": "main", "name": "Turbo Notify" },
    "to":   { "number": "5511777777777", "name": "João Silva" },
    "content_type": "text",
    "preview": "Olá, gostaria de saber...",
    "delivered_at": "2026-04-28T10:00:30Z"
  }
}
```

```json title="message.read"
{
  "id": "evt_read_001",
  "type": "message.read",
  "timestamp": "2026-04-28T10:01:15Z",
  "data": {
    "message_id": "msg_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
    "direction": "inbound",
    "from": { "number": "5511999990001", "alias": "main", "name": "Turbo Notify" },
    "to":   { "number": "5511777777777", "name": "João Silva" },
```

### Exemplos por `content_type` (inbound)

O envelope do webhook é idêntico em estrutura para todos os tipos
inbound — apenas `data.content_type` e `data.preview` mudam. Os
trechos abaixo mostram só o objeto `data` para reduzir ruído visual.

Para obter o **body completo** (texto, vCard, coordenadas, descrição
do evento, link da mídia, etc.), faça `GET /v1/messages/{message_id}`.
Os exemplos de body abaixo refletem o `body` retornado por esse
endpoint dentro da janela de retenção.

```json title="data — message.received (text)"

  "direction": "inbound",
  "from": { "number": "5511777777777", "name": "João Silva" },
```

"storage_circuit_open"}`, a payload carrega `setup_hint` apontando para
o wizard de configuração no Dashboard. Veja
[Armazenamento e mídia](#armazenamento-e-mídia) e o guia
[BYO Object Storage](/general/byo-storage-setup/).

## Tipos de evento

O catálogo público é fechado — seu endpoint só recebe os 24 eventos listados aqui.

### Mensagens — ciclo de envio

| Tipo                      | Quando é emitido                                                   |
| ------------------------- | ------------------------------------------------------------------ |
| `message.sent`            | Mensagem enviada com sucesso ao WhatsApp (sem citação).            |
| `message.send.failed`     | Falha no envio de uma mensagem regular (sem citação).              |
| `message.delivered`       | Receipt inbound: peer entregou uma mensagem que você enviou.       |
| `message.read`            | Receipt inbound: peer leu uma mensagem que você enviou.            |

### Mensagens — replies (citações)

| Tipo                      | Quando é emitido                                                   |
| ------------------------- | ------------------------------------------------------------------ |
| `message.replied`         | Reply enviado/recebido (qualquer `content_type`, ambas direções).  |
| `message.reply.failed`    | Falha ao enviar um reply (mensagem com `quoted_message_id`).     |

### Mensagens — recebimento e operações

| Tipo                      | Quando é emitido                                                   |
| ------------------------- | ------------------------------------------------------------------ |
| `message.received`        | Mensagem recebida de um contato (texto, mídia — sem citação).      |
| `message.edited`          | Mensagem foi editada (sua ou do contato).                          |
| `message.edit.failed`     | Falha ao editar uma mensagem.                                      |
| `message.deleted`         | Mensagem foi deletada/revogada (sua ou do contato).                |
| `message.delete.failed`   | Falha ao deletar uma mensagem.                                     |
| `message.reacted`         | Uma reação foi adicionada ou removida.                             |
| `message.react.failed`    | Falha ao reagir a uma mensagem.                                    |

### Números — ciclo de vida

| Tipo                          | Quando é emitido                                                  |
| ----------------------------- | ----------------------------------------------------------------- |
| `number.created`              | Número extra provisionado.                                        |
| `number.connected`            | Número principal ou extra conectado ao WhatsApp.                  |
| `number.disconnected`         | Número desconectado temporariamente.                              |
| `number.connect.failed`       | Falha no pareamento/conexão.                                      |
| `number.revoked`              | Dispositivo desvinculado pelo WhatsApp.                           |
| `number.remove.scheduled`     | Exclusão de número extra agendada (período de carência).          |
| `number.remove.canceled`      | Exclusão agendada foi cancelada.                                  |
| `number.removed`              | Número extra foi removido.                                        |

Todos os eventos `number.*` carregam os campos comuns `alias` e `number` (quando disponível). O campo `name` — nome de exibição WhatsApp do número, capturado na conexão — é **opcional** em todos os eventos e **omitido quando nulo**. O `alias` `"main"` identifica o número principal; qualquer outro valor identifica um número extra.

```json title="number.connected (exemplo)"
{
  "id": "evt_num_conn_abc123",
  "type": "number.connected",
  "timestamp": "2026-05-08T10:00:00Z",
  "data": {
    "name": "Turbo Notify",
    "alias": "main",
    "number": "5511973117056",
    "connected_at": "2026-05-08T10:00:00Z"
  }
}
```

### Armazenamento e mídia

Eventos relacionados à integração BYO Object Storage (AWS S3, Cloudflare R2, Supabase Storage) e à disponibilidade de mídia recebida.

:::note
Estes eventos são **provider-agnostic**: o payload é o mesmo independentemente do vendor configurado (AWS S3, Cloudflare R2 ou Supabase Storage). O protocolo de transporte é sempre a S3 HTTP API.
:::

:::caution[Mensagens recebidas com mídia — entrega só após resolução]
Para mensagens **inbound com mídia** (imagem, vídeo, áudio, documento, sticker), o webhook `message.received` só é enviado depois que o estado de mídia chega a um *terminal* para o seu tenant:

- **Com [BYO Storage](/general/byo-storage-setup/) ativo**: bytes salvos no seu bucket (`media.kind = "available"`), ou falha permanente sinalizada por `media.unavailable`.
- **Sem BYO Storage**: payload sai com `media.kind = "unavailable"` e `reason = "no_storage"` + `setup_hint` envelope. O Turbo Notify **não baixa nem proxia** os bytes da CDN do WhatsApp — apenas os metadados (mime, tamanho, hash, legenda) são persistidos.

Em caso de falha transitória de upload (rede, 5xx do storage, etc.), Turbo Notify aguarda o circuit breaker fechar; quando aberto, novas mensagens saem como `media.kind = "unavailable"` com `reason = "storage_circuit_open"`. Mensagens recebidas durante a janela degradada **não são** recuperadas retroativamente.

Use o evento `media.unavailable` como sinal definitivo de que aquela mídia não pôde ser persistida no seu bucket.
:::

#### Saúde do storage

| Tipo                          | Quando é emitido                                                  |
| ----------------------------- | ----------------------------------------------------------------- |
| `storage.degraded`            | Falhas consecutivas na integração BYO Object Storage abriram o circuito. |
| `storage.recovered`           | Primeira operação bem-sucedida após o circuito ter sido aberto — operação normal restabelecida. |

## Eventos de falha

Os eventos de falha compartilham um envelope comum (`error_code`, `error_message`, `failed_at`, `direction: "outbound"`, `origin`) e diferem entre si pelo conjunto de campos extras.

### `message.send.failed` / `message.reply.failed`

Falhas de envio podem ocorrer **antes** da mensagem ser persistida (validação, timeout do gateway), por isso `message_id` está intencionalmente ausente. Use `request_id` no envelope para correlacionar com a chamada original. `message.reply.failed` adiciona `quoted_message_id` para identificar a mensagem citada.

```json title="message.send.failed"
{
  "id": "evt_send_fail_001",
  "type": "message.send.failed",
  "timestamp": "2026-05-05T10:00:00Z",
  "request_id": "req_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "data": {
    "direction": "outbound",
    "origin": "api",
    "error_code": "whatsapp_unavailable",
    "error_message": "WhatsApp session is not connected",
    "failed_at": "2026-05-05T10:00:00Z"
  }
}
```

### `message.edit.failed` / `message.delete.failed` / `message.react.failed`

Diferentemente de `message.send.failed`, essas operações falham **sobre uma mensagem que já existe** no Turbo Notify. O payload carrega `message_id` da mensagem-alvo, dispensando a manutenção de um mapeamento privado `request_id → message_id` no seu lado.

```json title="message.edit.failed"
{
  "id": "evt_edit_fail_001",
  "type": "message.edit.failed",
  "timestamp": "2026-05-05T10:05:00Z",
  "request_id": "req_b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5",
  "data": {
    "message_id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "direction": "outbound",
    "origin": "api",
    "error_code": "edit_window_expired",
    "error_message": "Cannot edit after 15 minutes",
    "failed_at": "2026-05-05T10:05:00Z"
  }
}
```

`message.delete.failed` e `message.react.failed` seguem a mesma forma — apenas o valor de `type` muda.

## Notificações inbound de edição/deleção

Quando o **contato** edita ou apaga uma mensagem, o WhatsApp pode entregar a notificação com um identificador de protocolo diferente da mensagem original. Esse identificador aparece como `wa_notification_id` em `message.edited` / `message.deleted` (apenas inbound) — ele **não é** o id da mensagem editada/deletada, é o id da notificação de protocolo. Use `message_id` para identificar a mensagem que sofreu a alteração; `wa_notification_id` é puramente diagnóstico (debug de duplicidade).

## Mapeamento de operações assíncronas

Operações da API que disparam processamento assíncrono retornam um `request_id`. O mesmo `request_id` aparece no webhook do evento resultante — use para correlacionar:

| Operação                   | Evento de sucesso             | Evento de falha                   |
| -------------------------- | ----------------------------- | --------------------------------- |
| Enviar mensagem            | `message.sent`                | `message.send.failed`             |
| Responder mensagem         | `message.replied`             | `message.reply.failed`            |
| Editar mensagem            | `message.edited`              | `message.edit.failed`             |
| Deletar mensagem           | `message.deleted`             | `message.delete.failed`           |
| Reagir a uma mensagem      | `message.reacted`             | `message.react.failed`            |
| Conectar número extra      | `number.connected`            | `number.connect.failed`           |
| Agendar remoção de número  | `number.remove.scheduled`     | —                                 |
| Cancelar remoção agendada  | `number.remove.canceled`      | —                                 |

## Tentativas de entrega

Se seu endpoint não responder com status `2xx` dentro de 5 segundos, o Turbo Notify refará a tentativa com backoff exponencial:

| Tentativa | Intervalo aproximado |
| :-------: | -------------------- |
| 1         | Imediata             |
| 2         | 12 segundos          |
| 3         | 24 segundos          |
| 4         | 48 segundos          |
| 5         | 96 segundos          |
| 6         | 192 segundos         |

Após esgotar as tentativas, o evento é marcado como `dead_letter` e descartado.

## Garantia de entrega e idempotência

O Turbo Notify adota o modelo **at-least-once**. Em situações excepcionais, o mesmo evento pode ser entregue mais de uma vez. Use o campo `id` para implementar idempotência e evitar processamento duplicado.

### O campo `id` como chave de idempotência

O campo `id` (ex.: `evt_abc123…`) identifica o evento de forma única e é **estável entre tentativas de entrega**. Se o mesmo `id` chegar duas vezes no seu endpoint, trata-se de uma reentrega automática pelo Turbo Notify — o evento já foi processado na primeira entrega.

Armazene os `id` recebidos e ignore eventos cujo `id` já esteja na sua base:

```js title="dedup.js"
const seen = new Set();

function handleEvent(event) {
  if (seen.has(event.id)) {
    return; // reentrega — já processado
  }
  seen.add(event.id);
  // ... processar
}
```

Em produção, persista o `id` em uma tabela ou cache com TTL de ~72 h.

### Timestamps em reentregas

O campo `timestamp` sempre reflete a hora em que o **evento ocorreu** (protocolo WhatsApp ou ação na API), nunca a hora em que o webhook foi enviado ao seu endpoint. Em reentrgas, o `timestamp` permanece **inalterado** — é o mesmo valor da tentativa original. O mesmo vale para os campos `*_at` no objeto `data` (`sent_at`, `received_at`, `delivered_at`, `read_at`, etc.).

Isso significa que, ao receber uma reentrega:
- `timestamp` e `*_at` refletem a hora do evento original.
- `X-Webhook-Attempt` é incrementado a cada tentativa — use-o para diagnóstico, não para lógica de negócio.
- `X-Webhook-Timestamp` reflete a hora do **envio HTTP atual** e é usado para validação de assinatura e proteção anti-replay; **não** é o timestamp do evento.

## Alternativa: polling

Se preferir consumir eventos sob demanda em vez de expor um endpoint público, utilize o [polling via `GET /events`](/messages/polling/). O objeto `data` é o mesmo do webhook.

## Mensagens de grupo nos webhooks outbound

Quando você envia uma mensagem para um grupo via
`POST /v1/messages` com `to.group_id`, os webhooks subsequentes
(`message.sent`, `message.delivered`, `message.read`,
`message.send.failed`) usam o mesmo shape polimórfico — `to` carrega
`group_id` + snapshot `name`, e `member` identifica a linha que enviou:

```json title="message.sent (outbound para grupo)"
{
  "id": "evt_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "type": "message.sent",
  "timestamp": "2026-05-25T10:00:05Z",
  "request_id": "req_b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5",
  "data": {
    "message_id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "direction": "outbound",
    "from":   { "number": "5511973117056", "alias": "main", "name": "Turbo Notify" },
    "to":     { "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a", "name": "TNT" },
    "member": { "number": "5511973117056", "alias": "main" },
    "content_type": "text",
    "preview": "Bom dia, equipe",
    "sent_at": "2026-05-25T10:00:05Z"
  }
}
```

- `to.group_id` é o identificador público `grp_{hex32}` — mesmo valor que você forneceu no `POST /v1/messages`.
- `member` identifica a linha Turbo Notify que enviou a mensagem ao grupo. Para tenants com múltiplos extras, permite correlacionar qual linha participou do envio.
- Para detectar mensagens de grupo em qualquer webhook (inbound ou outbound), verifique `"group_id" in data.to`.

A mesma regra vale para inbound: webhooks `message.received` de
grupo trazem `from = participante`, `to.group_id = grupo`,
`member = linha tenant que recebeu`.
