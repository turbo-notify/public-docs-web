O Turbo Notify notifica seu sistema sobre eventos (envio confirmado, entrega, leitura, mensagem recebida, reação, falha) via webhook (HTTP POST). O objeto `data` de cada evento é **idêntico** ao retornado pelo endpoint [`GET /events`](/messages/polling/).

Se quem responde é um agente de IA, a combinação comum é: o webhook entrega o evento à sua aplicação, e o agente age pelas ferramentas do [Servidor MCP](/general/mcp-server/) (por exemplo `reply_to_message`). Sem endpoint público, o agente pode ler os mesmos eventos com a ferramenta `list_events`.

## Recebimento dos eventos

Para começar a receber eventos, cadastre a URL do seu webhook no <DashboardLink path="/webhooks">Dashboard</DashboardLink>. A URL deve ser pública, acessível via HTTPS e responder com status `2xx` dentro de 10 segundos.

:::tip[Inspecione e aprenda em tempo real]
Antes de plugar o webhook na sua aplicação, abra o <ExternalLink href="https://webhook.turbonotify.com">Webhook Inspector</ExternalLink> e cadastre a URL gerada. O Inspector recebe cada entrega em tempo real (via WebSocket), exibe cabeçalhos e corpo completos, valida a assinatura HMAC interativamente e sugere a próxima chamada REST típica para cada tipo de evento (`message.received` → `GET /v1/numbers/{alias}/messages/{id}`). O `{alias}` vem do campo `number_alias` do envelope do evento (`"main"` ou o alias de um número extra).
:::

## Privacidade

Recomendamos que sua URL de webhook não exponha informações sensíveis, como chaves de acesso ou identificadores internos. Use caminhos genéricos e valide a autenticidade da requisição pelo cabeçalho de assinatura.

## Segurança

Toda requisição de webhook enviada pelo Turbo Notify inclui os cabeçalhos abaixo. Utilize a assinatura para garantir que a requisição foi realmente enviada pelo Turbo Notify e não por terceiros.

| Cabeçalho | Descrição |
|--------|-----------|
| `X-Webhook-Signature` | `sha256=<hex>`: HMAC-SHA256 de `{X-Webhook-Timestamp}.{raw_body}` com seu segredo. |
| `X-Webhook-Timestamp` | Unix epoch (segundos): utilize para rejeitar entregas com mais de ~5 minutos (proteção contra replay). |
| `X-Webhook-Attempt` | Número da tentativa atual (começa em 1, incrementa a cada reentrega). |
| `X-Webhook-Max-Attempts` | Total de tentativas que o Turbo Notify fará antes de desistir. |
| `User-Agent` | `TurboNotify-Webhook/1.0`: útil para liberar as requisições no seu firewall de aplicação (WAF). |

O segredo é definido por **você**, no <DashboardLink path="/webhooks">Dashboard</DashboardLink>, no mesmo formulário em que você cadastra a URL. O Turbo Notify não gera um segredo: escolha um valor aleatório e longo, guarde-o na sua aplicação e informe o mesmo valor nos dois lados.

Exemplo de validação da assinatura:

```python title="validacao.py"
import hmac
import hashlib

def verificar_assinatura(payload: bytes, timestamp: str, assinatura: str, segredo: str) -> bool:
    dados_assinados = f"{timestamp}.".encode() + payload
    esperado = "sha256=" + hmac.new(
        segredo.encode(),
        dados_assinados,
        hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(esperado, assinatura)

# Uso:
# timestamp = request.headers["X-Webhook-Timestamp"]
# assinatura = request.headers["X-Webhook-Signature"]
# verificar_assinatura(request.body, timestamp, assinatura, segredo)
```

```js title="validacao.js"
const crypto = require('crypto');

function verificarAssinatura(payload, timestamp, assinatura, segredo) {
  const dadosAssinados = `${timestamp}.${payload}`;
  const esperado = 'sha256=' + crypto
    .createHmac('sha256', segredo)
    .update(dadosAssinados)
    .digest('hex');
  const esperadoBuf = Buffer.from(esperado);
  const assinaturaBuf = Buffer.from(assinatura ?? '');
  if (esperadoBuf.length !== assinaturaBuf.length) return false;
  return crypto.timingSafeEqual(esperadoBuf, assinaturaBuf);
}

// Uso:
// const timestamp = req.headers['x-webhook-timestamp'];
// const assinatura = req.headers['x-webhook-signature'];
// verificarAssinatura(req.body, timestamp, assinatura, segredo);
```

## Estrutura do evento

Toda requisição de webhook segue a mesma estrutura base:

| Propriedade       | Tipo     | Descrição                                                                 |
| ----------------- | -------- | ------------------------------------------------------------------------- |
| `id`              | `string` | Identificador único do evento (`evt_…`). Use como chave de idempotência.  |
| `type`            | `string` | Tipo do evento (ex.: `message.sent`).                                     |
| `organization_id` | `string` | Identificador público da sua organização (`org_{hex32}`). Sempre presente.|
| `number_alias`    | `string` | Identificador do número Turbo Notify ao qual o evento pertence: o próprio alias, `"main"` para o número principal ou o alias de um número extra. Presente em eventos ligados a um número específico: `message.*`, `number.*`, `group.*`, todos os `contact.*` (inclusive `contact.quota.*`) e `message.quota.*` (a cota de mensagens é por número). **Omitido** em `storage.*` **e** em `media.unavailable`, os eventos que não pertencem a um número único. |
| `created_at`      | `string` | Momento de **emissão** do evento pelo Turbo Notify, distinto de `data.at` (momento da ação no WhatsApp). ISO 8601 em UTC com sufixo `Z` e precisão de segundos (ex.: `2026-06-01T13:00:05Z`). |
| `data`            | `object` | Dados específicos do evento (veja [Campos da mensagem](#campos-da-mensagem)). |

:::note[Recibos e direção]
Os eventos `message.delivered` e `message.read` representam **confirmações de leitura/entrega**. `direction` é sempre `"inbound"` (a confirmação chega do destinatário). O recibo é modelado como um evento inbound:

- **`from`** = quem **disparou o recibo** (o contato que entregou/leu). Formato de pessoa, **sem `alias`**.
- **`to`** = o **destinatário do recibo**: em conversas diretas, o seu número (com `alias`); em grupos, o **grupo** (`group_id` + `name`).

O seu número que recebeu o recibo é identificado pelo `number_alias` do envelope. Para os detalhes desse número, use `GET /v1/numbers/{alias}`.

Em **grupos**, cada outro participante gera o seu próprio par `delivered`/`read`, sempre com `from` = aquele participante e `to` = o grupo. Não confunda com `message.received`, em que `direction="inbound"` reflete uma mensagem nova vinda do contato.
:::

## Campos da mensagem

Todos os eventos `message.*` compartilham os campos abaixo em `data`:

| Campo | Tipo | Descrição |
|-------|------|-----------|
| `id` | `string \| null` | Identificador público da mensagem (`msg_{hex32}`). `null` apenas em `message.send.failed` (registro não criado). |
| `from` | `object` | Quem originou o evento. Pessoa (inbound): `{contact_id?, name?, number}`. Outbound: `{contact_id?, name?, alias, number}`. |
| `to` | `object` | Destinatário. 1:1 inbound: `{contact_id?, name?, alias, number}`, o `alias` é **sempre presente** e identifica o seu número que recebeu. 1:1 outbound: `{contact_id?, name?, number}`. Grupo: `{group_id, name?}`. |
| `preview` | `string` | Recorte do conteúdo (até 50 caracteres). Veja [Preview por tipo](#preview-por-tipo). |
| `content_type` | `string` | `text`, `image`, `audio`, `video`, `document`, `sticker`, `location`, `calendar`, `contact`, `poll`, `interactive`. Mensagens de tipo desconhecido chegam como `unsupported`. Vem como `""` (string vazia) em `message.deleted`, `message.edit.failed` e `message.delete.failed`: essas operações não repetem o tipo do conteúdo original. |
| `direction` | `string` | `"outbound"` (ação da sua organização, pela API ou pelo celular) ou `"inbound"` (ação do contato, vinda do WhatsApp). |
| `channel` | `string` | Sempre `"whatsapp"`. |
| `origin` | `string` | `"tn"` (ação originada via API do Turbo Notify) ou `"native"` (originada no canal WhatsApp). Eventos inbound (`message.received`/`delivered`/`read`) são sempre `"native"`. Sempre presente. |
| `at` | `string` | ISO 8601 em UTC com sufixo `Z` e precisão de segundos (ex.: `2026-06-01T13:00:05Z`): momento da **ação real no WhatsApp** (envio, entrega, leitura, edição, etc.). Distinto de `created_at` (momento de emissão pelo Turbo Notify). |
| `mentions` | `array` | **Opcional**: presente apenas quando a mensagem menciona alguém, e **apenas** nos eventos que carregam o corpo da mensagem: `message.received`, `message.replied`, `message.sent`, `message.edited`. Itens `{contact_id?, name?, number}` (mesmo formato do `from` inbound), na ordem dos tokens no texto, sem duplicatas. Um `@<digitos>` no `preview`/texto **só** é menção se o número constar aqui. Ausente em `delivered`/`read`/`deleted`/`reacted` e nos `*.failed`. Em `message.edited`, é o conjunto re-extraído do **novo** texto. Veja [Menções (@mentions)](/messages/send/#menções-mentions). |

> **Ordem dos campos de `from`/`to`**: sempre
> `contact_id, name, alias, number` (alias onde existir; campos opcionais
> omitidos quando `null`). O `to` de grupo é a exceção: mantém `{group_id, name?}`.
> O seu número envolvido no evento é identificado pelo `number_alias` do envelope.
> `created_at` (envelope) é o momento de **emissão** do evento; `at` (em `data`)
> é o momento da **ação no WhatsApp**: valores distintos.
>
> `name` em `from`/`to` é o push name (nome de exibição) configurado pelo
> contato no WhatsApp. O Turbo Notify nunca infere ou busca isso em uma
> agenda de contatos. Ele fica disponível quando o contato **já enviou
> pelo menos uma mensagem inbound para a sua organização** (é assim que o
> WhatsApp entrega o push name), ou quando o número de destino é ele mesmo
> um número Turbo Notify de **outra** organização com o nome já conhecido.
> Fora esses dois casos, em um `message.sent` para alguém que nunca
> apareceu em nenhuma dessas fontes, `to.name` vem **omitido**: não é um
> erro; trate a ausência como "nome ainda desconhecido", não como falha de
> entrega.

:::note[`at` outbound também é o momento real do WhatsApp]
Para eventos **outbound** (`message.sent`/`replied`/`edited`/`deleted`) e
para os eventos `number.*` de ação real, `data.at` é o
**momento genuíno da ação no WhatsApp** (o timestamp real de envio reportado pelo
WhatsApp), **não** o momento em que o Turbo Notify emitiu o evento. Por isso, nos exemplos
abaixo `data.at` é tipicamente **anterior** ao `created_at` do envelope. O evento
é emitido alguns instantes após a ação que descreve. Nos eventos de falha
(`message.*.failed` e `number.connect.failed`) não há ação concluída no
WhatsApp: `data.at` é o momento em que a falha foi detectada.
:::

Eventos `message.*.failed` adicionam um objeto `error` estruturado: **o mesmo
formato** do `status.error` retornado por `GET /v1/numbers/{alias}/messages/{id}` e
`GET /v1/numbers/{alias}/messages/{id}/status`, então o evento e a consulta dizem a mesma coisa:

| Campo | Tipo | Descrição |
|-------|------|-----------|
| `error` | `object` | Erro da falha. Presente em todos os eventos `*.failed`. |
| `error.code` | `string` | Código estável legível por máquina: faça branch neste valor (ex.: `media_fetch_failed`, `unsupported_media_format`). |
| `error.message` | `string` | Descrição legível da falha. |
| `error.hint` | `string` | Orientação acionável para corrigir, derivada do `code`. **Omitido** (chave ausente, nunca `null`) quando não há orientação para o `code`. |

### Preview por tipo

| `content_type` | Preview |
|---|---|
| `text` | Texto truncado |
| `image` | Legenda ou `[Image]` |
| `sticker` | `[Sticker]` |
| `video` | Legenda ou `[Video]` |
| `audio` | Transcrição (quando disponível) → legenda → `[Audio]` |
| `document` | Legenda → nome do arquivo → `[Document]` |
| `location` | Texto legível sem colchetes, ex.: `Av. Paulista, Sao Paulo, SP` |
| `calendar` | Sem colchetes: dia da semana e mês abreviados em inglês, horário em UTC. Ex.: `Reunião — Tue, 2 Jun 2026 14:00` |
| `contact` | `[Contact: nome]` ou `[Contact]` quando o cartão não traz nome |
| `poll` | `""` (string vazia) |
| `interactive` | Texto do corpo (`body`) da mensagem interativa, ou `[Interactive]` quando o corpo está vazio |
| `unsupported` | `""` (string vazia): tipo de mensagem não reconhecido pelo Turbo Notify |

:::note[Menções contam como 1 caractere no preview]
Cada token de menção `@<numero>` presente em `data.mentions` conta como
exatamente **1 caractere** no limite de ~50 do `preview`, e o recorte **nunca
corta um token no meio**. Uma mensagem com várias menções preserva mais texto
visível do que a contagem bruta sugeriria. Um `@<digitos>` literal que **não**
esteja em `mentions` é texto comum e conta caractere a caractere. O `preview` é
byte-idêntico em todas as superfícies (webhook, polling, `GET`, listagem).
:::

### Exemplo: `message.sent` (outbound)

```json title="webhook-payload.json"
{
  "id": "evt_b7adf529683940edcdc533081ae182c5",
  "type": "message.sent",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:00:06Z",
  "data": {
    "id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": { "name": "Turbo Notify", "alias": "main", "number": "5511973117056" },
    "to": { "name": "João Silva", "number": "5511977776666" },
    "preview": "Sua mensagem...",
    "content_type": "text",
    "direction": "outbound",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-06-01T13:00:05Z"
  }
}
```

`created_at` (`13:00:06`, emissão pelo Turbo Notify) é **distinto** de `data.at`
(`13:00:05`, confirmação de envio no WhatsApp). O evento foi emitido 1 s após
a ação.

O `number_alias` do envelope identifica o seu número envolvido no evento. Em conversas 1:1 outbound esse número coincide com `from`.

`origin` discrimina a fonte do envio outbound:
- `"tn"`: enviado via API do Turbo Notify.
- `"native"`: detectado diretamente do app WhatsApp (quando a organização digita pelo celular).

`content_type` e `preview` espelham `message.received`: `text`, `image`, `audio`, `video`, `document`, `sticker`, `location`, `calendar`, `contact`, `poll` ou `interactive`. Para o corpo completo, faça `GET /v1/numbers/{alias}/messages/{id}`.

```json title="webhook-payload.json"
  "id": "evt_2b09b39a44ffc0d3039251f995e4c284",

    "from": { "name": "João Silva", "number": "5511977776666" },
    "to": { "name": "Turbo Notify", "alias": "main", "number": "5511973117056" },
    "preview": "Olá, gostaria de saber...",
    "content_type": "text",
```

### Exemplo: `message.received` (grupo)

Quando uma mensagem chega de um **grupo WhatsApp**,
`to` traz `group_id` e o nome do grupo no momento do evento (`name`) em vez de `number`.
O seu número que participa do grupo é identificado pelo `number_alias` do envelope.
`from` continua sendo o participante que enviou: quem envia é sempre uma pessoa, nunca o grupo.
Para mensagens 1:1, `to.group_id` é omitido.

```json title="message.received (grupo)"
{
  "id": "evt_c00a44c3fc774698b0f130d40bb5f104",
  "type": "message.received",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-02T01:55:14Z",
  "data": {
    "id": "msg_e95500cc03c1492e81e46a77c1f0d420",
    "from": {
      "contact_id": "ct_45f2ece8a66a4eeaa661aeb9b8e58c77",
      "name": "Ana Souza",
      "number": "5511988887777"
    },
    "to": {
      "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a",
      "name": "TNT"
    },
    "preview": "Bom dia pessoal",
    "content_type": "text",
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "native",
    "at": "2026-06-02T01:55:14Z"
  }
}
```

- `to.group_id` é o identificador público do grupo (`grp_{hex32}`), estável por organização. JIDs brutos do WhatsApp nunca são expostos.
- O `number_alias` do envelope identifica o seu número que participa do grupo. Essencial quando a organização tem vários números extras.
- Para detectar mensagens de grupo: verifique `"group_id" in data.to`. Conversas 1:1 nunca carregam esse campo.

### Exemplo: `message.received` com menções

Quando o texto (ou a legenda) menciona alguém, o
corpo chega com os tokens já normalizados para `@<numero>` (dígitos E.164 sem
`+`) e `data.mentions` traz os contatos correspondentes, já resolvidos:

```json title="message.received (grupo, com menção)"
  "created_at": "2026-07-03T12:15:02Z",

    "from": {
      "contact_id": "ct_45f2ece8a66a4eeaa661aeb9b8e58c77",
      "name": "Ana Souza",
      "number": "5511988887777"
    },
    "to": {
      "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a",
      "name": "TNT"
    },
    "mentions": [
      {
        "contact_id": "ct_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
        "name": "João Silva",
        "number": "5511977776666"
      }
    ],
    "preview": "Oi @5511977776666, pode revisar o contrato?",
    "content_type": "text",
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "native",
    "at": "2026-07-03T12:15:01Z"

```

- `mentions` aparece **somente** nos eventos que carregam o corpo da mensagem

  **somente** quando há menções.
- Um `@<digitos>` no texto/`preview` **só** é menção se o número constar em
  `mentions`. Caso contrário é texto comum.
- O mesmo token recebido pode ser colado de volta num
  [envio com menção](/messages/send/#menções-mentions).

```json title="message.read (grupo): recibo de um participante"
  "data": {
    "id": "msg_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
    "from": { "name": "João Silva", "number": "5511977776666" },
    "to": { "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a", "name": "TNT" },
```

## Tipos de evento

O seu webhook recebe exatamente os **42 tipos de evento** documentados aqui,
e nenhum outro. Esta
página cobre os **24** eventos das famílias `message.*`, `number.*`,
`storage.*` e `media.*`. Os **18** restantes vivem em três páginas
dedicadas: 6 eventos `contact.*` (inclui `contact.quota.*`) em
[Eventos de contato](/webhooks/contact-events/), 10 eventos `group.*` em
[Eventos de ciclo de vida](/groups/lifecycle-events/), e 2 eventos
`message.quota.*` em [Eventos de cota de mensagem](/webhooks/message-quota-events/).
Todos chegam no mesmo endpoint configurado. Não é preciso registrar nada
separadamente.

### Mensagens: ciclo de envio

| Tipo                      | Quando é emitido                                                   |
| ------------------------- | ------------------------------------------------------------------ |
| `message.sent`            | Mensagem enviada com sucesso ao WhatsApp (sem citação).            |
| `message.send.failed`     | Falha no envio de uma mensagem regular (sem citação).              |
| `message.delivered`       | Recibo: o destinatário recebeu uma mensagem que você enviou.       |
| `message.read`            | Recibo: o destinatário leu uma mensagem que você enviou.           |

### Mensagens: respostas (citações)

| Tipo                      | Quando é emitido                                                   |
| ------------------------- | ------------------------------------------------------------------ |
| `message.replied`         | Resposta enviada ou recebida (qualquer `content_type`, nas duas direções). |
| `message.reply.failed`    | Falha ao enviar uma resposta (via `POST /v1/numbers/{alias}/messages/{message_id}/reply`). |

### Mensagens: recebimento e operações

| Tipo                      | Quando é emitido                                                   |
| ------------------------- | ------------------------------------------------------------------ |
| `message.received`        | Mensagem recebida de um contato (texto, mídia, sem citação).       |
| `message.edited`          | Mensagem foi editada (sua ou do contato).                          |
| `message.edit.failed`     | Falha ao editar uma mensagem.                                      |
| `message.deleted`         | Mensagem foi apagada (sua ou do contato).                          |
| `message.delete.failed`   | Falha ao apagar uma mensagem.                                      |
| `message.reacted`         | Uma reação foi adicionada ou removida (`preview` = emoji ou `""`). |
| `message.react.failed`    | Falha ao reagir a uma mensagem.                                    |

### Números: ciclo de vida

| Tipo                          | Quando é emitido                                                  |
| ----------------------------- | ----------------------------------------------------------------- |
| `number.created`              | Número extra criado.                                              |
| `number.connected`            | Número principal ou extra conectado ao WhatsApp.                  |
| `number.disconnected`         | Número ficou desconectado além da janela de reconexão automática. |
| `number.connect.failed`       | Falha no pareamento/conexão.                                      |
| `number.revoked`              | Dispositivo desvinculado pelo WhatsApp.                           |
| `number.remove.scheduled`     | Exclusão de número extra agendada (período de carência).          |
| `number.remove.canceled`      | Exclusão agendada foi cancelada.                                  |
| `number.removed`              | Número extra foi removido.                                        |

Todos os eventos `number.*` carregam os campos comuns `alias`, `number` (quando disponível) e `external_id`. `external_id` está sempre presente, como texto ou `null`: é o identificador que você deu ao número ao criá-lo ou depois, por `PATCH /v1/numbers/{alias}` (normalmente o id do seu cliente final no seu sistema). Com ele, uma plataforma que revende números encaminha o evento ao cliente certo sem precisar consultar nada. Os eventos `message.*` continuam identificando o número apenas pelo `number_alias` do envelope. O campo `name` (nome de exibição WhatsApp do número, capturado na conexão) é **opcional** em todos os eventos e **omitido quando nulo**. O `alias` `"main"` identifica o número principal; qualquer outro valor identifica um número extra. `number.connected`, `number.disconnected`, `number.connect.failed` e `number.revoked` também podem trazer `contact_id` (`ct_…`, o contato que representa o próprio número), omitido quando ainda não existe. `number.disconnected` e `number.revoked` sempre trazem `reason`, um código estável que diz o que aconteceu (veja [Motivos de uma queda](#motivos-de-uma-queda)).

Todos os eventos `number.*` também carregam `channel` (sempre `"whatsapp"`) e `origin` (sempre `"tn"`: quem informa o ciclo de vida do número é o Turbo Notify). Eventos `number.*` **não** carregam `direction`, porque o ciclo de vida do número (criação, conexão, desconexão, revogação, remoção) não é uma troca de mensagens no WhatsApp.

**Reconexão automática.** Quando a conexão de um número cai e o Turbo Notify consegue trazê-lo de volta sozinho (a conexão com o WhatsApp caiu, ou o Turbo Notify moveu a conexão durante uma manutenção, uma redistribuição de carga ou a recuperação de uma falha do lado dele), nada é enviado na hora. Se o número volta dentro da janela de reconexão automática (cerca de um minuto), **nenhum** `number.disconnected` e **nenhum** `number.connected` são enviados: para você, o número não caiu. Se não volta a tempo, um único `number.disconnected` é enviado ao fim da janela, com `at` igual ao momento em que o número ficou offline; por isso esse `at` pode ser cerca de um a dois minutos anterior ao `created_at` do envelope. O Turbo Notify continua tentando, e o `number.connected` chega quando o número volta. Uma queda que precisa de você é enviada na hora (veja os motivos abaixo).

#### Motivos de uma queda

Use `reason` para decidir o que mostrar ao seu cliente. Os valores são estáveis e escritos do ponto de vista dele.

| Evento | `reason` | O que aconteceu e o que fazer |
| ------ | -------- | ----------------------------- |
| `number.disconnected` | `connection_lost` | A conexão com o WhatsApp caiu e não voltou dentro da janela de reconexão automática. O Turbo Notify continua reconectando: você não precisa fazer nada. |
| `number.disconnected` | `service_interruption` | Uma interrupção do lado do Turbo Notify tirou o número do ar. Ele volta sozinho; se continuar desconectado, conecte de novo (`POST /v1/numbers/{alias}/connect`). |
| `number.disconnected` | `replaced_by_another_device` | Outra conexão assumiu o dispositivo vinculado deste número. Enviado na hora. |
| `number.disconnected` | `disconnected_by_request` | Alguém da sua conta desconectou ou removeu o número. Enviado na hora. |
| `number.revoked` | `logged_out_on_phone` | O dispositivo foi desconectado no celular (WhatsApp, **Dispositivos conectados**). Pareie o número de novo. |
| `number.revoked` | `replaced_by_another_device` | Outra conexão assumiu o dispositivo vinculado deste número e, por segurança, ele foi desvinculado. Pareie o número de novo. |

O mesmo código tem o mesmo significado em todos os eventos `number.*`: o tipo do evento diz a consequência (`number.disconnected`: o número continua pareado e pode voltar; `number.revoked` e `number.connect.failed`: é preciso parear de novo). Novos motivos podem ser adicionados. Trate um valor que você não conhece em `number.disconnected` como `connection_lost` e em `number.revoked` como `logged_out_on_phone`.

```json title="number.disconnected (exemplo)"
{
  "id": "evt_6f0e1d2c3b4a59687766554433221100",
  "type": "number.disconnected",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:06:21Z",
  "data": {
    "name": "Turbo Notify",
    "alias": "main",
    "number": "5511973117056",
    "external_id": null,
    "reason": "connection_lost",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-06-01T13:05:12Z"
  }
}
```

O campo `at` (em `data`) carrega o **momento da ação real no WhatsApp**, e é um valor **distinto** do `created_at` do envelope (momento de emissão pelo Turbo Notify). Os eventos de ação real **`number.connected`**, **`number.disconnected`**, **`number.revoked`** e **`number.connect.failed`** carregam `at` com esse momento genuíno do WhatsApp (tipicamente anterior ao `created_at`); os eventos gerados pelo próprio Turbo Notify (**`number.created`**, **`number.remove.scheduled`**, **`number.remove.canceled`** e **`number.removed`**) **não** carregam `at`, apenas o `created_at` do envelope (`number.remove.scheduled` traz `scheduled_at`, o momento em que a exclusão vai acontecer).

```json title="number.connected (exemplo)"
{
  "id": "evt_2dd89f2fad140cf3ba32f2ed9f289a22",
  "type": "number.connected",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:00:01Z",
  "data": {
    "name": "Turbo Notify",
    "alias": "main",
    "number": "5511973117056",
    "external_id": null,
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-06-01T13:00:00Z"
  }
}
```

`number.connect.failed` traz dois campos sobre a falha: `error`, uma
mensagem legível para os seus logs, e `reason`, um código estável para
decidir o que mostrar ao seu cliente. Os valores de `reason` são os mesmos do
campo `reason` do status, listados em
[Motivos de falha](/numbers/status/#motivos-de-falha). Trate um valor
desconhecido como `pairing_failed`.

```json title="number.connect.failed (exemplo)"
{
  "id": "evt_4bcdecc36d67daab8f863f45a288c624",
  "type": "number.connect.failed",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "vendas_sp",
  "created_at": "2026-06-01T13:03:01Z",
  "data": {
    "alias": "vendas_sp",
    "number": "5511988887777",
    "external_id": "cliente-4821",
    "error": "Pairing code expired without being used. Check that the number is registered on WhatsApp and try again.",
    "reason": "pairing_timeout",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-06-01T13:03:00Z"
  }
}
```

### Armazenamento e mídia

Eventos relacionados à integração BYO Object Storage (AWS S3, Cloudflare R2, Supabase Storage) e à disponibilidade de mídia recebida.

:::note
Estes eventos valem para qualquer provedor: o conteúdo é o mesmo, seja qual for o provedor configurado.
:::

:::caution[Mensagens recebidas com mídia: entrega só após resolução]
Para mensagens **inbound com mídia** (imagem, vídeo, áudio, documento, sticker), o webhook `message.received` só é enviado depois que a mídia tem um resultado final para a sua organização:

- **Com [BYO Storage](/general/byo-storage-setup/) ativo**: bytes salvos no seu bucket, ou falha permanente, sinalizada por `media.unavailable` (`reason`: `upload_failed` ou `storage_circuit_open`).
- **Sem BYO Storage**: o Turbo Notify **não baixa nem repassa** a mídia hospedada pelo WhatsApp. Cada mensagem recebida com mídia gera um `media.unavailable` com `reason: "no_storage"`, e o bloco de mídia em `GET /v1/numbers/{alias}/messages/{id}` vem indisponível com o mesmo `reason`.

Use `GET /v1/numbers/{alias}/messages/{id}` para acessar o bloco `image`/`video`/`audio`/`document`/`sticker` com a URL de download (quando disponível).
:::

#### Saúde do armazenamento

| Tipo                          | Quando é emitido                                                  |
| ----------------------------- | ----------------------------------------------------------------- |
| `storage.degraded`            | As verificações periódicas do seu bucket falharam várias vezes seguidas. Enquanto isso, a mídia recebida não é salva no bucket. |
| `storage.recovered`           | Primeira verificação bem-sucedida depois de um `storage.degraded`. A mídia recebida volta a ser salva no seu bucket. |

#### Disponibilidade de mídia

| Tipo                          | Quando é emitido                                                  |
| ----------------------------- | ----------------------------------------------------------------- |
| `media.unavailable`           | A mídia não pôde ser salva no seu bucket (`reason`: `no_storage`, `storage_circuit_open`, `upload_failed`). |

#### Exemplo: `storage.degraded`

## Eventos de falha

Os eventos de falha compartilham um envelope comum e diferem entre si pelo conjunto de campos extras. `id` pode ser `null` **apenas** em `message.send.failed` (quando o registro não foi criado).

### `message.send.failed` / `message.reply.failed`

```json title="message.send.failed"
{
  "id": "evt_e80780d9147341cab5a0791102f44c02",
  "type": "message.send.failed",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:00:01Z",
  "data": {
    "id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": { "alias": "main", "number": "5511973117056" },
    "to": { "number": "5511988887777" },
    "preview": "Mensagem que falhou",
    "content_type": "text",
    "direction": "outbound",
    "channel": "whatsapp",
    "origin": "tn",
    "error": {
      "code": "number_not_connected",
      "message": "The number is not connected to WhatsApp.",
      "hint": "The number was not connected to WhatsApp. Reconnect it, then send the message again."
    },
    "at": "2026-06-01T13:00:00Z"
  }
}
```

`from` e `to` estão **sempre presentes** em todo evento `message.*.failed`,
mesmo quando nenhum registro de mensagem chegou a ser criado (`id: null`).
Se a falha acontece antes de o destinatário ser identificado, `from` traz o
número e o alias que tentaram enviar. O campo `error.hint` traz a orientação
para o código, como no exemplo acima (`number_not_connected`: o número não
estava conectado, reconecte e envie de novo), e é **omitido** (não `null`)
quando não há orientação para o código.

### `message.edit.failed` / `message.delete.failed` / `message.react.failed`

Diferentemente de `message.send.failed`, essas operações falham **sobre uma mensagem que já existe**: `id` está sempre presente.

```json title="message.edit.failed"
{
  "id": "evt_833a2144b32918475ce853581a753a5f",
  "type": "message.edit.failed",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:05:01Z",
  "data": {
    "id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": { "alias": "main", "number": "5511973117056" },
    "to": { "number": "5511988887777" },
    "preview": "",
    "content_type": "",
    "direction": "outbound",
    "channel": "whatsapp",
    "origin": "tn",
    "error": {
      "code": "edit_failed",
      "message": "WhatsApp rejected the edit"
    },
    "at": "2026-06-01T13:05:00Z"
  }
}
```

O WhatsApp aceita edição apenas em mensagens recentes e ainda não apagadas. Quando ele recusa, o Turbo Notify emite `message.edit.failed` com `error.code: "edit_failed"`. Antes disso, o próprio `POST .../edit` já rejeita mensagens que não estão em estado editável, com `400 message_not_editable`. Veja [Editar e apagar](/messages/edit-delete/).

`message.delete.failed` segue exatamente a mesma forma: apenas o valor de
`type` muda; `preview` e `content_type` também vêm `""`.

`message.react.failed` difere em **um** ponto além do `type`: seu
`content_type` é sempre o literal fixo `"text"` (uma reação é sempre texto),
enquanto `edit.failed` e `delete.failed` trazem `""`.

## Mensagens de grupo nos webhooks outbound

Quando você envia uma mensagem para um grupo via
`POST /v1/numbers/{alias}/messages` com `to.group_id`, os webhooks subsequentes
(`message.sent`, `message.delivered`, `message.read`,
`message.send.failed`) usam o mesmo formato: `to` traz
`group_id` e o nome do grupo (`name`), e o `number_alias` do envelope identifica o seu número que enviou:

```json title="message.sent (outbound para grupo)"
{
  "id": "evt_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "type": "message.sent",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:00:06Z",
  "data": {
    "id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": { "name": "Turbo Notify", "alias": "main", "number": "5511973117056" },
    "to": { "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a", "name": "TNT" },
    "preview": "Bom dia, equipe",
    "content_type": "text",
    "direction": "outbound",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-06-01T13:00:05Z"
  }
}
```

- `to.group_id` é o identificador público `grp_{hex32}`. Mesmo valor fornecido no `POST /v1/numbers/{alias}/messages`.
- O `number_alias` do envelope identifica o seu número que enviou a mensagem ao grupo.
- Para detectar mensagens de grupo: verifique `"group_id" in data.to`.

## Mapeamento de operações assíncronas

Operações da API que disparam processamento assíncrono expõem o `X-Request-ID` no cabeçalho da resposta. Use `GET /v1/events?request_id=req_...` para consultar os eventos da operação e identificar o resultado pelo `id` da mensagem (`data.id`):

| Operação                   | Evento de sucesso             | Evento de falha                   |
| -------------------------- | ----------------------------- | --------------------------------- |
| Enviar mensagem            | `message.sent`                | `message.send.failed`             |
| Responder mensagem         | `message.replied`             | `message.reply.failed`            |
| Editar mensagem            | `message.edited`              | `message.edit.failed`             |
| Apagar mensagem            | `message.deleted`             | `message.delete.failed`           |

Reações e operações de número não entram nesse filtro. Para uma reação,
acompanhe `message.reacted`/`message.react.failed` pelo `data.id` da
mensagem-alvo. Para números, acompanhe `number.connected`,
`number.connect.failed`, `number.remove.scheduled` e `number.remove.canceled`
pelo `number_alias` (por exemplo `GET /v1/events?number_alias=vendas_sp`).

## Tentativas de entrega

Se seu endpoint não responder com status `2xx` dentro de 10 segundos, o Turbo Notify reagenda a entrega seguindo um cronograma no estilo Standard Webhooks, com **atraso aleatório**: o atraso real de cada tentativa é um valor aleatório entre 0 e o máximo indicado, nunca um valor fixo:

| Tentativa | Atraso antes desta tentativa |
| :-------: | ----------------------------------------- |
| 1         | Nenhum: entrega inicial                    |
| 2         | ~0 s (próximo ciclo de reentrega, ≤15 s)   |
| 3         | até 5 segundos                             |
| 4         | até 5 minutos                              |
| 5         | até 30 minutos                             |
| 6         | até 2 horas                                |

Após a 6ª tentativa falhar, o evento é marcado como `dead_letter` e nenhuma nova tentativa é feita.

:::note[Reentrega exige o plano BUSINESS ou superior]
O cronograma de reentrega acima é um recurso de plano, disponível a partir
do plano `BUSINESS`. Organizações em `SOLO` recebem **exatamente
1 tentativa**: se essa única tentativa não retornar `2xx`, o evento é
marcado como `dead_letter` imediatamente, sem nenhuma reentrega. O cabeçalho
`X-Webhook-Max-Attempts`, presente em toda tentativa de entrega, reflete
esse limite (`1` para `SOLO`; `6` para `BUSINESS`/`CUSTOM`). O plano `FREE`
não tem entrega por webhook: acompanhe os eventos por [polling](/messages/polling/).

Isso afeta apenas a **reentrega** em caso de falha. A primeira tentativa
de entrega acontece normalmente em todos os planos. Veja [Cota e
uso](/usage/quota/) para os limites e restrições de cada plano.
:::

## Garantia de entrega e idempotência

O Turbo Notify entrega cada evento **pelo menos uma vez**. Em situações excepcionais, o mesmo evento pode ser entregue mais de uma vez. Use o campo `id` para implementar idempotência e evitar processamento duplicado.

### O campo `id` como chave de idempotência

O campo `id` (ex.: `evt_3f1c9a7e2b8d4c6fa0e15b7d9c2a4e68`) identifica o evento de forma única e é **estável entre tentativas de entrega**. Se o mesmo `id` chegar duas vezes no seu endpoint, trata-se de uma reentrega automática pelo Turbo Notify. O evento já foi processado na primeira entrega.

Armazene os `id` recebidos e ignore eventos cujo `id` já esteja na sua base:

```js title="dedup.js"
const seen = new Set();

function handleEvent(event) {
  if (seen.has(event.id)) {
    return; // reentrega: já processado
  }
  seen.add(event.id);
  // ... processar
}
```

Em produção, guarde o `id` numa tabela ou num cache que o mantenha por pelo menos três dias.

### Timestamps em reentregas

O campo `created_at` (envelope) reflete o **momento de emissão do evento pelo Turbo Notify**: quando o registro do evento é criado e publicado, nunca a hora em que o webhook foi enviado ao seu endpoint. Quando presente, `at` (em `data`) reflete o **momento da ação real no WhatsApp**. Estes são **valores distintos**: um evento pode ser emitido algum tempo depois da ação que descreve (eventos gerados pelo próprio Turbo Notify não têm `at`). Em reentregas, tanto `created_at` quanto `at` permanecem **inalterados**: são os mesmos valores da tentativa original.

Isso significa que, ao receber uma reentrega:
- `created_at` é o momento de emissão; `at` (quando presente) é o momento da ação no WhatsApp, ambos fixos entre tentativas.
- `X-Webhook-Attempt` é incrementado a cada tentativa: use-o para diagnóstico, não para lógica de negócio.
- `X-Webhook-Timestamp` reflete a hora do **envio HTTP atual** e é usado para validação de assinatura e proteção anti-replay; **não** é o timestamp do evento.

## Alternativa: polling

Se preferir consumir eventos sob demanda em vez de expor um endpoint público, utilize o [polling via `GET /events`](/messages/polling/). O objeto `data` é o mesmo do webhook.
