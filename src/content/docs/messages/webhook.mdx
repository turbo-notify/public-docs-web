O Turbo Notify notifica seu sistema sobre eventos (envio confirmado, entrega, leitura, mensagem recebida, reação, falha) via webhook (HTTP POST). O objeto `data` de cada evento é **idêntico** ao retornado pelo endpoint [`GET /events`](/messages/polling/).

## Recebimento dos eventos

Para começar a receber eventos, cadastre a URL do seu webhook no <DashboardLink path="/webhooks">Dashboard</DashboardLink>. A URL deve ser pública, acessível via HTTPS e responder com status `2xx` dentro de 10 segundos.

:::tip[Inspecione e aprenda em tempo real]
Antes de plugar o webhook na sua aplicação, abra o <ExternalLink href="https://webhook.turbonotify.com">Webhook Inspector</ExternalLink> e cadastre a URL gerada. O Inspector recebe cada entrega em tempo real (via WebSocket), exibe headers/body completos, valida a assinatura HMAC interativamente e sugere a próxima chamada REST típica para cada tipo de evento (`message.received` → `GET /v1/numbers/{alias}/messages/{id}`). O `{alias}` vem do campo `number_alias` do envelope do evento (`"main"` ou o alias de um número extra).
:::

## Privacidade

Recomendamos que sua URL de webhook não exponha informações sensíveis, como chaves de acesso ou identificadores internos. Use caminhos genéricos e valide a autenticidade da requisição pelo cabeçalho de assinatura.

## Segurança

Toda requisição de webhook enviada pelo Turbo Notify inclui os cabeçalhos abaixo. Utilize a assinatura para garantir que a requisição foi realmente enviada pelo Turbo Notify e não por terceiros.

| Header | Descrição |
|--------|-----------|
| `X-Webhook-Signature` | `sha256=<hex>`: HMAC-SHA256 de `{X-Webhook-Timestamp}.{raw_body}` com seu segredo. |
| `X-Webhook-Timestamp` | Unix epoch (segundos): utilize para rejeitar entregas com mais de ~5 minutos (proteção contra replay). |
| `X-Webhook-Attempt` | Número da tentativa atual (começa em 1, incrementa a cada reentrega). |
| `X-Webhook-Max-Attempts` | Total de tentativas que o Turbo Notify fará antes de desistir. |
| `User-Agent` | `TurboNotify-Webhook/1.0`: útil para WAF allowlists. |

O segredo é definido por **você**, no <DashboardLink path="/webhooks">Dashboard</DashboardLink>, no mesmo formulário em que você cadastra a URL. O Turbo Notify não gera um segredo: escolha um valor aleatório e longo, guarde-o na sua aplicação e informe o mesmo valor nos dois lados.

Exemplo de validação da assinatura:

```python title="validacao.py"
import hmac
import hashlib

def verificar_assinatura(payload: bytes, timestamp: str, assinatura: str, segredo: str) -> bool:
    dados_assinados = f"{timestamp}.".encode() + payload
    esperado = "sha256=" + hmac.new(
        segredo.encode(),
        dados_assinados,
        hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(esperado, assinatura)

# Uso:
# timestamp = request.headers["X-Webhook-Timestamp"]
# assinatura = request.headers["X-Webhook-Signature"]
# verificar_assinatura(request.body, timestamp, assinatura, segredo)
```

```js title="validacao.js"
const crypto = require('crypto');

function verificarAssinatura(payload, timestamp, assinatura, segredo) {
  const dadosAssinados = `${timestamp}.${payload}`;
  const esperado = 'sha256=' + crypto
    .createHmac('sha256', segredo)
    .update(dadosAssinados)
    .digest('hex');
  const esperadoBuf = Buffer.from(esperado);
  const assinaturaBuf = Buffer.from(assinatura ?? '');
  if (esperadoBuf.length !== assinaturaBuf.length) return false;
  return crypto.timingSafeEqual(esperadoBuf, assinaturaBuf);
}

// Uso:
// const timestamp = req.headers['x-webhook-timestamp'];
// const assinatura = req.headers['x-webhook-signature'];
// verificarAssinatura(req.body, timestamp, assinatura, segredo);
```

## Estrutura do evento

Toda requisição de webhook segue a mesma estrutura base:

| Propriedade       | Tipo     | Descrição                                                                 |
| ----------------- | -------- | ------------------------------------------------------------------------- |
| `id`              | `string` | Identificador único do evento (`evt_…`). Use como chave de idempotência.  |
| `type`            | `string` | Tipo do evento (ex.: `message.sent`).                                     |
| `organization_id` | `string` | Identificador público da sua organização (`org_{hex32}`). Sempre presente.|
| `number_alias`    | `string` | Handle do número Turbo Notify ao qual o evento pertence: `"main"` para o número principal ou o alias de um número extra. É a **string do alias**, nunca um UUID. Presente em eventos ligados a um número específico: `message.*`, `number.*`, `group.*`, todos os `contact.*` (inclusive `contact.quota.*`) e `message.quota.*` (a quota de mensagens é por número); **omitido** em `storage.*` **e** em `media.unavailable`: os eventos que não pertencem a um número único. |
| `created_at`      | `string` | Momento de **emissão** do evento pelo Turbo Notify, distinto de `data.at` (momento da ação no WhatsApp). ISO 8601 em UTC com sufixo `Z` e precisão de segundos (ex.: `2026-06-01T13:00:05Z`). |
| `data`            | `object` | Dados específicos do evento (veja [Campos da mensagem](#campos-da-mensagem)). |

:::note[Receipts e direção]
Os eventos `message.delivered` e `message.read` representam **confirmações de leitura/entrega**. `direction` é sempre `"inbound"` (a confirmação chega do destinatário). O recibo é modelado como um evento inbound:

- **`from`** = quem **disparou o recibo** (o contato que entregou/leu). Formato de pessoa, **sem `alias`**.
- **`to`** = o **destinatário do recibo**: em conversas diretas, o seu número (com `alias`); em grupos, o **grupo** (`group_id` + `name`).

A linha Turbo Notify que recebeu o recibo é identificada pelo `number_alias` do envelope; resolva seu número/contato via `GET /v1/numbers/{alias}`.

Em **grupos**, cada outro participante gera o seu próprio par `delivered`/`read`, sempre com `from` = aquele participante e `to` = o grupo. Não confunda com `message.received`, em que `direction="inbound"` reflete uma mensagem nova vinda do contato.
:::

## Campos da mensagem

Todos os eventos `message.*` compartilham os campos abaixo em `data`:

| Campo | Tipo | Descrição |
|-------|------|-----------|
| `id` | `string \| null` | Identificador público da mensagem (`msg_{hex32}`). `null` apenas em `message.send.failed` (registro não criado). |
| `from` | `object` | Quem originou o evento. Pessoa (inbound): `{contact_id?, name?, number}`. Outbound: `{contact_id?, name?, alias, number}`. |
| `to` | `object` | Destinatário. 1:1 inbound: `{contact_id?, name?, alias, number}`, o `alias` é **sempre presente** e identifica a sua linha que recebeu. 1:1 outbound: `{contact_id?, name?, number}`. Grupo: `{group_id, name?}`. |
| `preview` | `string` | Recorte do conteúdo (até 50 chars). Veja [Preview por tipo](#preview-por-tipo). |
| `content_type` | `string` | `text`, `image`, `audio`, `video`, `document`, `sticker`, `location`, `calendar`, `contact`, `poll`, `interactive`. Mensagens de tipo desconhecido chegam como `unsupported`. Vem como `""` (string vazia) em `message.deleted`, `message.edit.failed` e `message.delete.failed`: essas operações não repetem o tipo do conteúdo original. |
| `direction` | `string` | `"outbound"` (ação da organização/API) ou `"inbound"` (ação do peer/WhatsApp). |
| `channel` | `string` | Sempre `"whatsapp"`. |
| `origin` | `string` | `"tn"` (ação originada via API do Turbo Notify) ou `"native"` (originada no canal WhatsApp). Eventos inbound (`message.received`/`delivered`/`read`) são sempre `"native"`. Sempre presente. |
| `at` | `string` | ISO 8601 em UTC com sufixo `Z` e precisão de segundos (ex.: `2026-06-01T13:00:05Z`): momento da **ação real no WhatsApp** (envio, entrega, leitura, edição, etc.). Distinto de `created_at` (momento de emissão pelo Turbo Notify). |
| `mentions` | `array` | **Opcional**: presente apenas quando a mensagem menciona alguém, e **apenas** nos eventos que carregam o body: `message.received`, `message.replied`, `message.sent`, `message.edited`. Itens `{contact_id?, name?, number}` (mesmo shape do `from` inbound), na ordem dos tokens no texto, sem duplicatas. Um `@<digitos>` no `preview`/texto **só** é menção se o número constar aqui. Ausente em `delivered`/`read`/`deleted`/`reacted` e nos `*.failed`. Em `message.edited`, é o conjunto re-extraído do **novo** texto. Veja [Menções (@mentions)](/messages/send/#menções-mentions). |

> **Ordem dos campos do objeto party** (`from`/`to`): sempre
> `contact_id, name, alias, number` (alias onde existir; campos opcionais
> omitidos quando `null`). O `to` de grupo é a exceção: mantém `{group_id, name?}`.
> A linha Turbo Notify do evento é identificada pelo `number_alias` do envelope;
> resolva seu número/contato via `GET /v1/numbers/{alias}`.
> `created_at` (envelope) é o momento de **emissão** do evento; `at` (em `data`)
> é o momento da **ação no WhatsApp**: valores distintos.
>
> `name` em `from`/`to` é o push name (nome de exibição) configurado pelo
> contato no WhatsApp. O Turbo Notify nunca infere ou busca isso em uma
> agenda de contatos. Ele fica disponível quando o contato **já enviou
> pelo menos uma mensagem inbound para a sua organização** (é assim que o
> WhatsApp entrega o push name), ou quando o número de destino é ele mesmo
> uma linha Turbo Notify de **outra** organização com o nome já conhecido.
> Fora esses dois casos, em um `message.sent` para alguém que nunca
> apareceu em nenhuma dessas fontes, `to.name` vem **omitido**: não é um
> erro; trate a ausência como "nome ainda desconhecido", não como falha de
> entrega.

:::note[`at` outbound também é o momento real do WhatsApp]
Para eventos **outbound** (`message.sent`/`replied`/`edited`/`deleted` e os
`*.failed`) e para os eventos `number.*` de ação real, `data.at` é o
**momento genuíno da ação no WhatsApp** (o timestamp real de envio reportado pelo
WhatsApp), **não** o momento em que o Turbo Notify emitiu o evento. Por isso, nos exemplos
abaixo `data.at` é tipicamente **anterior** ao `created_at` do envelope. O evento
é emitido alguns instantes após a ação que descreve.
:::

Eventos `message.*.failed` adicionam um objeto `error` estruturado: **o mesmo
shape** do `status.error` retornado por `GET /v1/numbers/{alias}/messages/{id}` e
`GET /v1/numbers/{alias}/messages/{id}/status` (coerência evento ↔ recurso):

| Campo | Tipo | Descrição |
|-------|------|-----------|
| `error` | `object` | Erro da falha. Presente em todos os eventos `*.failed`. |
| `error.code` | `string` | Código estável legível por máquina: faça branch neste valor (ex.: `media_fetch_failed`, `unsupported_media_format`). |
| `error.message` | `string` | Descrição legível da falha. |
| `error.hint` | `string` | Orientação acionável para corrigir, derivada do `code`. **Omitido** (chave ausente, nunca `null`) quando não há orientação para o `code`. |

### Preview por tipo

| `content_type` | Preview |
|---|---|
| `text` | Texto truncado |
| `image` | Legenda ou `[Image]` |
| `sticker` | `[Sticker]` |
| `video` | Legenda ou `[Video]` |
| `audio` | Transcrição (quando disponível) → legenda → `[Audio]` |
| `document` | Legenda → nome do arquivo → `[Document]` |
| `location` | Texto humanizado sem colchetes, ex: `Av. Paulista, Sao Paulo, SP` |
| `calendar` | Sem colchetes: dia da semana e mês abreviados em inglês, horário em UTC. Ex: `Reuniao — Tue, 2 Jun 2026 14:00` |
| `contact` | `[Contact: nome]` ou `[Contact]` quando o cartão não traz nome |
| `poll` | `""` (string vazia) |
| `interactive` | Texto do corpo (`body`) da mensagem interativa, ou `[Interactive]` quando o corpo está vazio |
| `unsupported` | `""` (string vazia): tipo de mensagem não reconhecido pelo Turbo Notify |

:::note[Menções contam como 1 caractere no preview]
Cada token de menção `@<numero>` presente em `data.mentions` conta como
exatamente **1 caractere** no limite de ~50 do `preview`, e o recorte **nunca
corta um token no meio**. Uma mensagem com várias menções preserva mais texto
visível do que a contagem bruta sugeriria. Um `@<digitos>` literal que **não**
esteja em `mentions` é texto comum e conta caractere a caractere. O `preview` é
byte-idêntico em todas as superfícies (webhook, polling, `GET`, listagem).
:::

### Exemplo: `message.sent` (outbound)

```json title="webhook-payload.json"
{
  "id": "evt_abc123def456789012345678",
  "type": "message.sent",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:00:06Z",
  "data": {
    "id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": { "name": "Turbo Notify", "alias": "main", "number": "5511999990001" },
    "to": { "name": "João Silva", "number": "5511999990002" },
    "preview": "Sua mensagem...",
    "content_type": "text",
    "direction": "outbound",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-06-01T13:00:05Z"
  }
}
```

`created_at` (`13:00:06`, emissão pelo Turbo Notify) é **distinto** de `data.at`
(`13:00:05`, confirmação de envio no WhatsApp). O evento foi emitido 1 s após
a ação.

O `number_alias` do envelope identifica a linha Turbo Notify do evento; resolva seu número/contato via `GET /v1/numbers/{alias}`. Em conversas 1:1 outbound essa linha coincide com `from`.

`origin` discrimina a fonte do envio outbound:
- `"tn"`: enviado via API do Turbo Notify.
- `"native"`: detectado diretamente do app WhatsApp (quando a organização digita pelo celular).

`content_type` e `preview` espelham `message.received`: `text`, `image`, `audio`, `video`, `document`, `sticker`, `location`, `calendar`, `contact`, `poll` ou `interactive`. Para o body completo, faça `GET /v1/numbers/{alias}/messages/{id}`.

```json title="webhook-payload.json"
{
  "id": "evt_def789abc234567890123456",
  "type": "message.received",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T18:32:11Z",
  "data": {
    "id": "msg_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
    "from": { "name": "João Silva", "number": "5511777777777" },
    "to": { "name": "Turbo Notify", "alias": "main", "number": "5511999990001" },
    "preview": "Olá, gostaria de saber...",
    "content_type": "text",
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "native",

```

`from.name` traz o nome de exibição configurado no WhatsApp (push name); omitido quando não definido. O `number_alias` do envelope resolve para `"main"` ou o alias do número extra que recebeu.

### Exemplo: `message.received` (grupo)

Quando uma mensagem chega de um **grupo WhatsApp**,
`to` carrega `group_id` + snapshot `name` em vez de `number`. A linha Turbo Notify
que participa do grupo é identificada pelo `number_alias` do envelope.
`from` continua sendo o participante que enviou. Pessoas sempre falam, nunca grupos.
Para mensagens 1:1, `to.group_id` é omitido.

```json title="message.received (grupo)"
{
  "id": "evt_c00a44c3fc774698b0f130d40bb5f104",
  "type": "message.received",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-02T01:55:14Z",
  "data": {
    "id": "msg_e95500cc03c1492e81e46a77c1f0d420",
    "from": {
      "contact_id": "ct_45f2ece8a66a4eeaa661aeb9b8e58c77",
      "name": "Cleverson",
      "number": "5571999258283"
    },
    "to": {
      "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a",
      "name": "TNT"
    },
    "preview": "Bom dia pessoal",
    "content_type": "text",
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "native",
    "at": "2026-06-02T01:55:14Z"
  }
}
```

- `to.group_id` é o identificador público do grupo (`grp_{hex32}`), estável por organização. JIDs brutos do WhatsApp nunca são expostos.
- O `number_alias` do envelope identifica a linha Turbo Notify que participa do grupo. Essencial quando a organização tem múltiplos números extras: resolva seu número/contato via `GET /v1/numbers/{alias}`.
- Para detectar mensagens de grupo: verifique `"group_id" in data.to`. Conversas 1:1 nunca carregam esse campo.

### Exemplo: `message.received` com menções

Quando o texto (ou caption) menciona alguém, o
body chega com os tokens já normalizados para `@<numero>` (dígitos E.164 sem
`+`) e `data.mentions` traz os contatos correspondentes, já resolvidos:

```json title="message.received (grupo, com menção)"
{
  "id": "evt_f11b55d4ed885709c1f241e51cc6f215",
  "type": "message.received",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-07-03T12:15:02Z",
  "data": {
    "id": "msg_f06611dd14d2503f92f57b88d2f1e531",
    "from": {
      "contact_id": "ct_45f2ece8a66a4eeaa661aeb9b8e58c77",
      "name": "Cleverson",
      "number": "5511988887777"
    },
    "to": {
      "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a",
      "name": "TNT"
    },
    "preview": "Oi @5511987650000, pode revisar o contrato?",
    "content_type": "text",
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "native",
    "at": "2026-07-03T12:15:01Z",
    "mentions": [
      {
        "contact_id": "ct_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
        "name": "Maria Santos",
        "number": "5511987650000"
      }
    ]
  }
}
```

- `mentions` aparece **somente** nos eventos que carregam o body
  (`message.received`, `message.replied`, `message.sent`, `message.edited`) e
  **somente** quando há menções. Uma mensagem sem menções mantém o payload
  byte-idêntico ao contrato anterior.
- Um `@<digitos>` no texto/`preview` **só** é menção se o número constar em
  `mentions`. Caso contrário é texto comum.
- O mesmo token recebido pode ser colado de volta num
  [envio com menção](/messages/send/#menções-mentions). A simetria é garantida.

o que ela continha. Não faça branch por `content_type` aqui; use o `data.id`
para localizar a mensagem no seu lado.

#### Recibos em grupo: um por participante

Quando você envia uma mensagem a um **grupo**, **cada outro participante**
gera o seu próprio `delivered` (ao receber) e `read` (ao ler). Em cada
recibo: `from` = aquele participante, `to` = o grupo. A linha da organização (dispositivo
vinculado) que observou o recibo é dada pelo `number_alias` do envelope.

```json title="message.read (grupo): recibo do participante A"
{
  "id": "evt_read_grp_A",
  "type": "message.read",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:01:15Z",
  "data": {
    "id": "msg_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
    "from": { "name": "Número A", "number": "5511973117056" },
    "to": { "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a", "name": "TNT" },
    "preview": "Olá, time!",
    "content_type": "text",
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "native",
```

- `from.number` muda a cada participante que confirma; `to` (o grupo) e o `number_alias` do envelope (o seu número) permanecem os mesmos para todos os recibos da mesma mensagem.
- Para detectar recibos de grupo: verifique `"group_id" in data.to`.

## Tipos de evento

O catálogo público é fechado. O mesmo endpoint configurado como webhook só
recebe os **42 tipos de evento** do catálogo público, sem surpresas. Esta
página cobre os **24** eventos das famílias `message.*`, `number.*`,
`storage.*` e `media.*`. Os **18** restantes vivem em três páginas
dedicadas: 6 eventos `contact.*` (inclui `contact.quota.*`) em
[Eventos de contato](/webhooks/contact-events/), 10 eventos `group.*` em
[Eventos de ciclo de vida](/groups/lifecycle-events/), e 2 eventos
`message.quota.*` em [Eventos de quota de mensagem](/webhooks/message-quota-events/).
Todos chegam no mesmo endpoint configurado. Não é preciso registrar nada
separadamente.

### Mensagens: ciclo de envio

| Tipo                      | Quando é emitido                                                   |
| ------------------------- | ------------------------------------------------------------------ |
| `message.sent`            | Mensagem enviada com sucesso ao WhatsApp (sem citação).            |
| `message.send.failed`     | Falha no envio de uma mensagem regular (sem citação).              |
| `message.delivered`       | Receipt inbound: peer entregou uma mensagem que você enviou.       |
| `message.read`            | Receipt inbound: peer leu uma mensagem que você enviou.            |

### Mensagens: replies (citações)

| Tipo                      | Quando é emitido                                                   |
| ------------------------- | ------------------------------------------------------------------ |
| `message.replied`         | Reply enviado/recebido (qualquer `content_type`, ambas direções).  |
| `message.reply.failed`    | Falha ao enviar um reply (via `POST /v1/numbers/{alias}/messages/{message_id}/reply`). |

### Mensagens: recebimento e operações

| Tipo                      | Quando é emitido                                                   |
| ------------------------- | ------------------------------------------------------------------ |
| `message.received`        | Mensagem recebida de um contato (texto, mídia, sem citação).       |
| `message.edited`          | Mensagem foi editada (sua ou do contato).                          |
| `message.edit.failed`     | Falha ao editar uma mensagem.                                      |
| `message.deleted`         | Mensagem foi deletada/revogada (sua ou do contato).                |
| `message.delete.failed`   | Falha ao deletar uma mensagem.                                     |
| `message.reacted`         | Uma reação foi adicionada ou removida (`preview` = emoji ou `""`). |
| `message.react.failed`    | Falha ao reagir a uma mensagem.                                    |

### Números: ciclo de vida

| Tipo                          | Quando é emitido                                                  |
| ----------------------------- | ----------------------------------------------------------------- |
| `number.created`              | Número extra provisionado.                                        |
| `number.connected`            | Número principal ou extra conectado ao WhatsApp.                  |
| `number.disconnected`         | Número desconectado temporariamente.                              |
| `number.connect.failed`       | Falha no pareamento/conexão.                                      |
| `number.revoked`              | Dispositivo desvinculado pelo WhatsApp.                           |
| `number.remove.scheduled`     | Exclusão de número extra agendada (período de carência).          |
| `number.remove.canceled`      | Exclusão agendada foi cancelada.                                  |
| `number.removed`              | Número extra foi removido.                                        |

Todos os eventos `number.*` carregam os campos comuns `alias` e `number` (quando disponível). O campo `name` (nome de exibição WhatsApp do número, capturado na conexão) é **opcional** em todos os eventos e **omitido quando nulo**. O `alias` `"main"` identifica o número principal; qualquer outro valor identifica um número extra.

Todos os eventos `number.*` também carregam o par de coerência `channel` (sempre `"whatsapp"`) e `origin` (sempre `"tn"`, o ciclo de vida do dispositivo é produzido pela plataforma Turbo Notify). Eventos `number.*` **não** carregam `direction`. O ciclo de vida do link (conexão, desconexão, revogação, remoção, criação) não é um fluxo de mensagem WhatsApp.

O campo `at` (em `data`) carrega o **momento da ação real no WhatsApp**, e é um valor **distinto** do `created_at` do envelope (momento de emissão pelo Turbo Notify). Os eventos de ação real **`number.connected`**, **`number.disconnected`**, **`number.revoked`** e **`number.connect.failed`** carregam `at` com esse momento genuíno do WhatsApp (tipicamente anterior ao `created_at`); os eventos sintéticos do Turbo Notify (**`number.created`**, **`number.remove.scheduled`**, **`number.remove.canceled`** e **`number.removed`**) **não** carregam `at`, apenas o `created_at` do envelope (`number.remove.scheduled` mantém `scheduled_at` como timestamp de valor de negócio, com seu nome semântico).

```json title="number.connected (exemplo)"
{
  "id": "evt_num_conn_abc123",
  "type": "number.connected",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:00:01Z",
  "data": {
    "name": "Turbo Notify",
    "alias": "main",
    "number": "5511973117056",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-06-01T13:00:00Z"
  }
}
```

### Armazenamento e mídia

Eventos relacionados à integração BYO Object Storage (AWS S3, Cloudflare R2, Supabase Storage) e à disponibilidade de mídia recebida.

:::note
Estes eventos são **agnósticos de provedor**: o payload é o mesmo independentemente do provedor configurado.
:::

:::caution[Mensagens recebidas com mídia: entrega só após resolução]
Para mensagens **inbound com mídia** (imagem, vídeo, áudio, documento, sticker), o webhook `message.received` só é enviado depois que o estado de mídia chega a um *terminal* para a sua organização:

- **Com [BYO Storage](/general/byo-storage-setup/) ativo**: bytes salvos no seu bucket, ou falha permanente sinalizada por `media.unavailable`.
- **Sem BYO Storage**: payload sai com `media` indisponível e `reason = "no_storage"`. O Turbo Notify **não baixa nem repassa** os bytes da CDN do WhatsApp.

Use `GET /v1/numbers/{alias}/messages/{id}` para acessar o bloco `image`/`video`/`audio`/`document`/`sticker` com a URL de download (quando disponível).
:::

## Eventos de falha

Os eventos de falha compartilham um envelope comum e diferem entre si pelo conjunto de campos extras. `id` pode ser `null` **apenas** em `message.send.failed` (quando o registro não foi criado).

### `message.send.failed` / `message.reply.failed`

```json title="message.send.failed"
{
  "id": "evt_send_fail_001",
  "type": "message.send.failed",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:00:01Z",
  "data": {
    "id": null,
    "from": { "alias": "main", "number": "5511973117056" },
    "to": { "number": "5511999999999" },
    "preview": "Mensagem que falhou",
    "content_type": "text",
    "direction": "outbound",
    "channel": "whatsapp",
    "origin": "tn",
    "error": {
      "code": "session_not_connected",
      "message": "WhatsApp session is not connected"
    },
    "at": "2026-06-01T13:00:00Z"
  }
}
```

`from` e `to` são **sempre obrigatórios** em todo evento `message.*.failed`:
mesmo em falhas que acontecem antes de qualquer registro ser criado como esta, em que nenhum registro de mensagem
chegou a ser criado (`id: null`). Quando o pipeline falha antes de resolver
o destinatário real, `from` é sintetizado a partir do número/alias que
tentou enviar. O campo `error.hint` é **omitido** (não `null`) quando não
há orientação acionável para o código. O exemplo acima ilustra isso
(`session_not_connected` não tem `hint`).

### `message.edit.failed` / `message.delete.failed` / `message.react.failed`

Diferentemente de `message.send.failed`, essas operações falham **sobre uma mensagem que já existe**: `id` está sempre presente.

```json title="message.edit.failed"
{
  "id": "evt_edit_fail_001",
  "type": "message.edit.failed",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:05:01Z",
  "data": {
    "id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": { "alias": "main", "number": "5511973117056" },
    "to": { "number": "5511999999999" },
    "preview": "",
    "content_type": "",
    "direction": "outbound",
    "channel": "whatsapp",
    "origin": "tn",
    "error": {
      "code": "edit_failed",
      "message": "WhatsApp rejected the edit"
    },
    "at": "2026-06-01T13:05:00Z"
  }
}
```

O WhatsApp aceita edição apenas em mensagens recentes e ainda não apagadas. Quando ele recusa, o Turbo Notify emite `message.edit.failed` com `error.code: "edit_failed"`. Antes disso, o próprio `POST .../edit` já rejeita mensagens que não estão em estado editável, com `400 message_not_editable`. Veja [Editar e deletar](/messages/edit-delete/).

`message.delete.failed` segue exatamente a mesma forma: apenas o valor de
`type` muda; `preview` e `content_type` também vêm `""`.

`message.react.failed` difere em **um** ponto além do `type`: seu
`content_type` é sempre o literal fixo `"text"` (uma reação é sempre texto),
enquanto `edit.failed` e `delete.failed` trazem `""`.

`from`/`to` são sempre obrigatórios nos 5 eventos `message.*.failed`.

## Mensagens de grupo nos webhooks outbound

Quando você envia uma mensagem para um grupo via
`POST /v1/numbers/{alias}/messages` com `to.group_id`, os webhooks subsequentes
(`message.sent`, `message.delivered`, `message.read`,
`message.send.failed`) usam o mesmo shape polimórfico, `to` carrega
`group_id` + snapshot `name`, e o `number_alias` do envelope identifica a linha que enviou:

```json title="message.sent (outbound para grupo)"
{
  "id": "evt_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "type": "message.sent",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T13:00:06Z",
  "data": {
    "id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": { "name": "Turbo Notify", "alias": "main", "number": "5511973117056" },
    "to": { "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a", "name": "TNT" },
    "preview": "Bom dia, equipe",
    "content_type": "text",
    "direction": "outbound",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-06-01T13:00:05Z"
  }
}
```

- `to.group_id` é o identificador público `grp_{hex32}`. Mesmo valor fornecido no `POST /v1/numbers/{alias}/messages`.
- O `number_alias` do envelope identifica a linha Turbo Notify que enviou a mensagem ao grupo.
- Para detectar mensagens de grupo: verifique `"group_id" in data.to`.

## Mapeamento de operações assíncronas

Operações da API que disparam processamento assíncrono expõem o `X-Request-ID` no header da resposta. Use `GET /v1/events?request_id=req_...` para consultar os eventos da operação e identificar o resultado pelo `id` da mensagem (`data.id`):

| Operação                   | Evento de sucesso             | Evento de falha                   |
| -------------------------- | ----------------------------- | --------------------------------- |
| Enviar mensagem            | `message.sent`                | `message.send.failed`             |
| Responder mensagem         | `message.replied`             | `message.reply.failed`            |
| Editar mensagem            | `message.edited`              | `message.edit.failed`             |
| Deletar mensagem           | `message.deleted`             | `message.delete.failed`           |
| Reagir a uma mensagem      | `message.reacted`             | `message.react.failed`            |
| Conectar número extra      | `number.connected`            | `number.connect.failed`           |
| Agendar remoção de número  | `number.remove.scheduled`     | —                                 |
| Cancelar remoção agendada  | `number.remove.canceled`      | —                                 |

## Tentativas de entrega

Se seu endpoint não responder com status `2xx` dentro de 10 segundos, o Turbo Notify reagenda a entrega seguindo um cronograma no estilo Standard Webhooks com **jitter total**, o atraso real de cada tentativa é um valor aleatório entre 0 e o máximo indicado, nunca um valor fixo:

| Tentativa | Atraso antes desta tentativa |
| :-------: | ----------------------------------------- |
| 1         | Nenhum: entrega inicial                    |
| 2         | ~0 s (próximo ciclo de reentrega, ≤15 s)   |
| 3         | até 5 segundos                             |
| 4         | até 5 minutos                              |
| 5         | até 30 minutos                             |
| 6         | até 2 horas                                |

Após a 6ª tentativa falhar, o evento é marcado como `dead_letter` e nenhuma nova tentativa é feita.

:::note[Reentrega exige o plano BUSINESS ou superior]
O cronograma de reentrega acima é uma feature de plano, disponível a partir
do tier `BUSINESS`. Organizações em `FREE`/`SOLO` recebem **exatamente
1 tentativa**: se essa única tentativa não retornar `2xx`, o evento é
marcado como `dead_letter` imediatamente, sem nenhuma reentrega. O header
`X-Webhook-Max-Attempts`, presente em toda tentativa de entrega, reflete
esse limite (`1` para `FREE`/`SOLO`; `6` para `BUSINESS`/`CUSTOM`).

Isso afeta apenas a **reentrega** em caso de falha. A primeira tentativa
de entrega acontece normalmente em todos os tiers. Veja [Quota e
uso](/usage/quota/) para os limites e restrições de cada plano.
:::

## Garantia de entrega e idempotência

O Turbo Notify adota o modelo **at-least-once**. Em situações excepcionais, o mesmo evento pode ser entregue mais de uma vez. Use o campo `id` para implementar idempotência e evitar processamento duplicado.

### O campo `id` como chave de idempotência

O campo `id` (ex.: `evt_abc123…`) identifica o evento de forma única e é **estável entre tentativas de entrega**. Se o mesmo `id` chegar duas vezes no seu endpoint, trata-se de uma reentrega automática pelo Turbo Notify. O evento já foi processado na primeira entrega.

Armazene os `id` recebidos e ignore eventos cujo `id` já esteja na sua base:

```js title="dedup.js"
const seen = new Set();

function handleEvent(event) {
  if (seen.has(event.id)) {
    return; // reentrega: já processado
  }
  seen.add(event.id);
  // ... processar
}
```

Em produção, persista o `id` em uma tabela ou cache com TTL de ~72 h.

### Timestamps em reentregas

O campo `created_at` (envelope) reflete o **momento de emissão do evento pelo Turbo Notify**: quando o registro do evento é criado e publicado, nunca a hora em que o webhook foi enviado ao seu endpoint. Quando presente, `at` (em `data`) reflete o **momento da ação real no WhatsApp**. Estes são **valores distintos**: um evento pode ser emitido algum tempo depois da ação que descreve (eventos sintéticos do Turbo Notify não têm `at`). Em reentregas, tanto `created_at` quanto `at` permanecem **inalterados**: são os mesmos valores da tentativa original.

Isso significa que, ao receber uma reentrega:
- `created_at` é o momento de emissão; `at` (quando presente) é o momento da ação no WhatsApp, ambos fixos entre tentativas.
- `X-Webhook-Attempt` é incrementado a cada tentativa: use-o para diagnóstico, não para lógica de negócio.
- `X-Webhook-Timestamp` reflete a hora do **envio HTTP atual** e é usado para validação de assinatura e proteção anti-replay; **não** é o timestamp do evento.

## Alternativa: polling

Se preferir consumir eventos sob demanda em vez de expor um endpoint público, utilize o [polling via `GET /events`](/messages/polling/). O objeto `data` é o mesmo do webhook.
