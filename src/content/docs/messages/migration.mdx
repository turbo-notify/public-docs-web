:::note[Atualização 2026-06-25]
As rotas planas `/v1/messages`, `/v1/contacts` e `/v1/groups` foram reintroduzidas
como forma de acesso direto ao número principal. Se você usa apenas o número principal,
estas rotas são a forma recomendada de integração.
:::

## Migração — Maio 2026 (2026-05-25): `to` polimórfico + campo `member` em grupos

**Data de vigência:** 25 de maio de 2026

Esta atualização afeta **exclusivamente mensagens de grupo** (inbound e
outbound). Mensagens 1:1 permanecem byte-idênticas — não há ação
necessária se você não usa grupos.

A linha Turbo Notify é identificada pelo `number_alias` do envelope;
resolva seu número/contato via `GET /v1/numbers/{alias}`.

:::note[O campo `member` descrito abaixo foi removido em 2026-06-19]
Esta seção documenta o estado do payload **entre 25 de maio e 19 de junho de
2026**: o campo `group` sibling foi removido e, no mesmo momento, um campo
`member` foi adicionado dentro de `data` para identificar a linha Turbo
Notify participante do grupo. Em 19 de junho de 2026 o `member` (e o
equivalente `inbox`) foi **removido** de `data` — a mesma informação passou
a viver no `number_alias` do envelope (já usado em todos os trechos "O que
fazer" desta página). Se você está integrando hoje, **ignore as menções a
`data.member`** nesta seção e use `number_alias` diretamente — veja [Visão
geral de grupos](/groups/overview/#linha-turbo-notify-number_alias-do-envelope).
:::

### Resumo das mudanças

| Área | Mudança | Tipo |
|---|---|---|
| Webhook/polling grupo inbound | `to` agora carrega `group_id` + `name` em vez de `number`/`alias` | Breaking |
| Webhook/polling grupo outbound | `to` agora carrega `group_id` + `name` em vez de `number` | Breaking |
| Campo `group` sibling | **Removido** — substituído por `to.group_id` | Breaking |
| Campo `member` | **Adicionado** como sibling top-level em mensagens de grupo — **removido novamente em 2026-06-19**, substituído pelo `number_alias` do envelope (veja nota acima) | Aditivo |
| Request `POST /v1/numbers/{alias}/messages` (grupo) | Sem mudança — já usava `to.group_id` | Sem ação |

### 1. Remoção do campo `group` sibling

O campo `group: {id, name}` que aparecia como sibling de `from`/`to` em
payloads de grupo **foi removido**. O contexto do grupo agora está dentro
do próprio campo `to`.

**Antes:**

```json
{
  "from": { "name": "Cleverson", "number": "5571999258283" },
  "to":   { "name": "Turbo Notify", "alias": "main", "number": "5511973117056" },
  "group": { "id": "grp_e442553a56b14e2695f6acfd7d651b1a", "name": "TNT" }
}
```

**Depois:**

```json
{
  "from":   { "contact_id": "ct_...", "name": "Cleverson", "number": "5571999258283" },
  "to":     { "group_id": "grp_e442553a56b14e2695f6acfd7d651b1a", "name": "TNT" },
  "member": { "alias": "main", "number": "5511973117056" }
}
```

*(O `member` acima só existiu até 19 de junho de 2026 — veja a nota logo
abaixo do resumo das mudanças. O payload atual não carrega este campo;
use o `number_alias` do envelope.)*

**O que fazer:**
- Remova qualquer leitura de `data.group` ou `data.group.id` / `data.group.name`.
- Substitua por `data.to.group_id` e `data.to.name`.
- Atualize a detecção de grupo: `"group" in data` → `"group_id" in data.to`.

### 2. Campo `to` polimórfico — shape de grupo

Para mensagens de grupo, `to` não carrega mais `number`, `alias` nem `name`
da linha Turbo Notify. Em vez disso, carrega o identificador e nome do grupo.

**Inbound de grupo:**

| Campo | Antes | Depois |
|---|---|---|
| `to.number` | telefone da linha Turbo Notify | **removido** |
| `to.alias` | alias da linha Turbo Notify (`"main"`) | **removido** |
| `to.name` | nome da linha Turbo Notify | **removido** |
| `to.contact_id` | contact_id da linha Turbo Notify | **removido** |
| `to.group_id` | ausente | `grp_{hex32}` do grupo |
| `to.name` | ausente | nome snapshot do grupo |
| `member.number` | ausente | telefone da linha Turbo Notify |
| `member.alias` | ausente | alias da linha Turbo Notify |

**O que fazer:**
- Para saber qual linha Turbo Notify recebeu a mensagem, leia o `number_alias` do envelope.
- Para obter o grupo destinatário, leia `data.to.group_id`.

### 3. Campo `member` — identificação da linha da organização (histórico — removido em 2026-06-19)

Entre 25 de maio e 19 de junho de 2026, o campo `member` era adicionado como
sibling top-level em **todos** os payloads de grupo (inbound e outbound) para
identificar a linha Turbo Notify participante do grupo — o telefone
(`number`) e alias (`alias`):

```json
"member": { "alias": "main", "number": "5511973117056" }
```

**Esse campo não existe mais.** Desde 19 de junho de 2026, a mesma
informação é dada pelo `number_alias` do envelope (fora de `data`) — resolva
o número/contato correspondente via `GET /v1/numbers/{alias}`. Não implemente
integrações novas contra `data.member`.

### 4. Detecção de grupo — padrão canônico

```js
// Antes
const isGroup = "group" in data;
const groupId = data.group?.id;
const groupName = data.group?.name;

// Depois
const isGroup = "group_id" in data.to;
const groupId = data.to.group_id;
const groupName = data.to.name;
const inboxAlias = event.number_alias; // linha da organização via envelope (number_alias)
```

### Checklist de migração (grupos)

- [ ] Remover leitura de `data.group` (campo removido)
- [ ] Substituir `data.group.id` por `data.to.group_id`
- [ ] Substituir `data.group.name` por `data.to.name`
- [ ] Atualizar detecção: `"group" in data` → `"group_id" in data.to`
- [ ] Para saber qual linha Turbo Notify recebeu/enviou: usar o `number_alias` do envelope e resolver via `GET /v1/numbers/{alias}`
- [ ] Atualizar schemas JSON com `additionalProperties: false` que incluíam `group` como campo permitido

## Migração — Abril 2026 (2026-04-21): formato de `message_id`, parties estruturados e outros

Esta versão da API introduz mudanças incompatíveis com versões anteriores. Siga este guia para atualizar sua integração.

**Data de vigência:** 21 de abril de 2026

---

## Resumo das mudanças (Abril 2026)

| Área | Mudança | Tipo |
| ---- | ------- | ---- |
| Formato do `message_id` | Agora prefixado com `msg_` | Breaking |
| `request_id` no corpo | Removido — use o header `X-Request-ID` | Breaking |
| `GET /v1/messages/{request_id}/status` | Removido — use `GET /v1/messages/{message_id}/status` | Breaking |
| Webhook `message.received` | Campo `content` removido; adicionados `preview` e `content_type` | Breaking |
| Webhook `message.edited` | Campo `new_text` removido; adicionado `new_preview` (depois renomeado para `preview` em 2026-05-06) | Breaking |
| Webhook `message.edited` (2026-05-06) | Campo `new_preview` renomeado para `preview`; payloads antigos com `new_preview` continuam sendo aceitos, mas o campo emitido hoje é sempre `preview` | Breaking |
| Typing indicator | Campo `value` renomeado para `is_typing` | Breaking |
| `POST /numbers` | Campo `phone` renomeado para `phone_number` | Breaking |
| `GET /numbers` | Shape da resposta mudou para o envelope `{data, cursor, has_more}` | Breaking |

---

## 1. Formato do `message_id`

O identificador de mensagem agora inclui o prefixo `msg_` seguido de 32 caracteres hexadecimais minúsculos.

**Antes:**

```json
{
  "message_id": "01993c5a1b24d3e9f01a2b3c4d5e6f70"
}
```

**Depois:**

```json
{
  "message_id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70"
}
```

**Validação:** `^msg_[0-9a-f]{32}$`

**O que fazer:** Atualize qualquer código que armazene ou compare `message_id` para incluir o prefixo `msg_`. Atualize validações de formato nos seus sistemas.

---

## 2. Correlação de requisição: `request_id` removido do corpo

O campo `request_id` foi removido do corpo das respostas. A correlação de requisições agora é feita exclusivamente pelo header `X-Request-ID`.

**Antes:**

```json
{
  "message_id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
  "request_id": "req_01993c5a1b24d3e9f01a2b3c4d5e6f70",
  "status": { "state": "pending", "at": "2026-04-21T10:00:00Z" }
}
```

**Depois:**

```http
202 Accepted
X-Request-ID: req_01993c5a1b24d3e9f01a2b3c4d5e6f70
```

```json
{
  "message_id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
  "status": { "state": "pending", "at": "2026-04-21T10:00:00Z" }
}
```

**O que fazer:** Leia o `X-Request-ID` do header da resposta. Para rastrear uma requisição específica nos eventos, use `GET /v1/events?request_id=req_...`.

---

## 3. Consulta de status por `request_id` removida

O endpoint `GET /v1/messages/{request_id}/status` foi removido. Use o `message_id` retornado na resposta de envio.

**Antes:**

```bash
curl "https://api.turbonotify.com/v1/messages/req_abc123/status" \
  -H "Authorization: Bearer SUA_CHAVE"
```

**Depois:**

```bash
curl "https://api.turbonotify.com/v1/messages/msg_01993c5a1b24d3e9f01a2b3c4d5e6f70/status" \
  -H "Authorization: Bearer SUA_CHAVE"
```

**O que fazer:** Armazene o `message_id` (não o `request_id`) para consultas de status futuras. Para correlacionar requisições com eventos, use a API de eventos com `request_id` no query parameter.

---

## 4. Webhook `message.received`: `content` removido

O campo `content` foi removido do payload do evento `message.received`. Em seu lugar, foram adicionados `preview` e `content_type`.

**Antes:**

```json
{
  "id": "evt_abc123",
  "type": "message.received",
  "timestamp": "2026-04-21T10:00:00Z",
  "data": {
    "message_id": "01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": "5511999999999",
    "to": "5511973117056",
    "content": "Olá, gostaria de saber sobre o pedido",
    "received_at": "2026-04-21T10:00:00Z"
  }
}
```

**Depois:**

```json
{
  "id": "evt_abc123",
  "type": "message.received",
  "timestamp": "2026-04-21T10:00:00Z",
  "data": {
    "message_id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": { "number": "5511999999999" },
    "to": { "number": "5511973117056" },
    "content_type": "text",
    "preview": "Olá, gostaria de saber sobre o pedido",
    "received_at": "2026-04-21T10:00:00Z"
  }
}
```

**O que fazer:**
- Substitua o uso de `data.content` por `data.preview` para exibição ou logging rápido.
- Para o corpo completo da mensagem, chame `GET /v1/numbers/{alias}/messages/{message_id}` dentro da janela de retenção.
- Use `data.content_type` para identificar o tipo de conteúdo recebido.
- Atualize referências a `data.from` e `data.to`: agora são objetos `{number: string}`, não strings planas.

---

## 5. Webhook `message.edited`: `new_text` removido

O campo `new_text` foi removido do payload do evento `message.edited`. Em seu lugar foi adicionado `new_preview`.

**Antes:**

```json
{
  "id": "evt_abc124",
  "type": "message.edited",
  "timestamp": "2026-04-21T10:05:00Z",
  "data": {
    "message_id": "01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "new_text": "Texto corrigido da mensagem completa.",
    "edited_at": "2026-04-21T10:05:00Z"
  }
}
```

**Depois (até 2026-05-06):**

```json
{
  "id": "evt_abc124",
  "type": "message.edited",
  "timestamp": "2026-04-21T10:05:00Z",
  "data": {
    "message_id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "new_preview": "Texto corrigido da mensagem co",
    "edited_at": "2026-04-21T10:05:00Z"
  }
}
```

**Em 2026-05-06** o campo `new_preview` foi renomeado para `preview`, para manter paridade com o `preview` dos eventos `message.sent` e `message.received`. A partir de **2026-06-01** o envelope passou a expor `organization_id` + `created_at` (em vez de `timestamp`), o `data` usa `id` (em vez de `message_id`), e o timestamp de ocorrência é o campo `at` (último, em vez de `edited_at`). O payload atual é:

```json
{
  "id": "evt_abc124",
  "type": "message.edited",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-06-01T10:05:00Z",
  "data": {
    "id": "msg_01993c5a1b24d3e9f01a2b3c4d5e6f70",
    "from": { "alias": "main", "number": "5571999258283" },
    "to": { "number": "5511988877766" },
    "preview": "Texto corrigido da mensagem co",
    "content_type": "text",
    "direction": "outbound",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-06-01T10:05:00Z"
  }
}
```

Após a edição via `POST /v1/numbers/{alias}/messages/{id}/edit`, `GET /v1/numbers/{alias}/messages/{message_id}` retorna o body já atualizado — não é mais necessário tratar o body antigo. Edições feitas diretamente no app do WhatsApp (channel-side) também passam a ser persistidas.

**O que fazer:**

1. Substitua o uso de `data.new_text` por `data.preview`.
2. Se já tinha migrado para `new_preview`, faça a substituição final por `preview`. Camadas de compatibilidade do servidor continuam aceitando payloads legados no read-side, mas o write-side só emite `preview`.
3. Para o corpo completo atualizado (qualquer edição, API ou channel-side), chame `GET /v1/numbers/{alias}/messages/{message_id}`.

## 6. Indicador de digitação: `value` renomeado para `is_typing`

O campo `value` no payload do indicador de digitação foi renomeado para `is_typing`.

**Antes:**

```json
{
  "to": "+5511999999999",
  "value": true
}
```

**Depois:**

```json
{
  "to": {"number": "+5511999999999"},
  "is_typing": true
}
```

**O que fazer:** Atualize as chamadas a `POST /v1/numbers/{alias}/typing-indicator` para usar `is_typing` no lugar de `value` e o campo `to` no formato estruturado `{"number": "..."}` (veja [Indicador de digitação](/other-features/typing-indicator/#destinatários-disponíveis) para as formas aceitas hoje).

---

## 7. `POST /numbers`: campo `phone` renomeado para `phone_number`

O campo do número de telefone ao criar um número extra foi renomeado.

**Antes:**

```json
{
  "alias": "vendas-sp",
  "phone": "+5511988887777"
}
```

**Depois:**

```json
{
  "alias": "vendas-sp",
  "phone_number": "+5511988887777"
}
```

**O que fazer:** Atualize qualquer chamada a `POST /v1/numbers` para usar `phone_number` no campo do telefone.

---

## 8. `GET /numbers`: novo formato de resposta

A resposta do endpoint de listagem de números mudou para o envelope `{data, cursor, has_more}`.

**Antes:**

```json
{
  "numbers": [
    { "alias": "vendas-sp", "phone": "+5511988887777", "status": "active" }
  ]
}
```

**Depois:**

```json
{
  "data": [
    {
      "contact_id": "ct_c7abb1f5ee9640bf86a0a20290810ae9",
      "name": "Vendas SP",
      "type": "extra",
      "alias": "vendas-sp",
      "number": "5511988887777",
      "description": null,
      "status": { "status": "connected", "at": "2026-04-01T10:00:00Z", "reason": null }
    }
  ],
  "cursor": null,
  "has_more": false
}
```

**O que fazer:**
- Acesse os números em `data` (antes: `numbers`).
- Atualize referências ao campo `phone`: nos **itens da listagem** ele virou `number`, em **dígitos E.164 sem `+`**. O nome `phone_number` vale para o corpo **e** para a resposta de `POST /v1/numbers` (outro endpoint, veja a seção anterior), mas o `+` inicial **só** é aceito no **corpo da requisição** — a **resposta** devolve dígitos puros, sem `+` (ex.: `"5511988888888"`).
- Troque `number_type` por `type` e trate `status` como **objeto** `{status, at, reason}`, não como a string `"active"`. Não existem `created_at` nem `phone_number` nos itens.
- Não implemente paginação aqui: `GET /v1/numbers` não aceita nenhum query parameter e sempre devolve todos os números da conta em uma única página — `cursor` vem sempre `null` e `has_more` sempre `false`.

O shape completo, campo a campo, está em [Listagem de números](/numbers/list/).

## Novos recursos nesta versão

Além das mudanças incompatíveis, esta versão introduz novos recursos:

| Recurso | Endpoint | Descrição |
| ------- | -------- | --------- |
| Consulta de mensagem | `GET /v1/numbers/{alias}/messages/{message_id}` | Recupere corpo completo, status e mídia por ID |
| Envio de mídia | `POST /v1/numbers/{alias}/messages` com o campo âncora da mídia em `content` (`image_url`, `video_url`, `audio_url`, `document_url` ou `sticker_url`) | Envie imagens, áudios, vídeos, documentos e figurinhas |
| BYO Object Storage | Dashboard → Configurações → Integrações | Armazenamento durável para mídia recebida e enviada |
| Polling de eventos | `GET /v1/events` | Alternativa ou complemento ao webhook para processar eventos |

O corpo do envio é `{to, quoted_message_id?, content}` e não aceita campos extras: o tipo de conteúdo é **inferido** do campo âncora presente em `content`, e mandar um `content_type` explícito retorna `422`. Veja [Envio de mensagens](/messages/send/) e [Envio de mídia](/messages/send-media/).

Consulte as páginas de cada recurso para detalhes de uso.

## Checklist de migração

- [ ] Atualizar armazenamento de `message_id` para incluir o prefixo `msg_`
- [ ] Atualizar validações de formato de `message_id` para `^msg_[0-9a-f]{32}$`
- [ ] Ler `X-Request-ID` do header em vez de `request_id` do corpo
- [ ] Substituir chamadas a `GET /v1/messages/{request_id}/status` por `GET /v1/messages/{message_id}/status`
- [ ] Atualizar handlers de `message.received` para usar `preview` e `content_type` em vez de `content`
- [ ] Atualizar referências a `from` e `to` de string para objeto `{number: string}`
- [ ] Atualizar handlers de `message.edited` para usar `preview` (anteriormente `new_text` → `new_preview` → `preview`; o nome final `preview` é o canônico desde 2026-05-06)
- [ ] Atualizar chamadas a `POST /v1/typing-indicator` para usar `is_typing`
- [ ] Atualizar chamadas a `POST /v1/numbers` para usar `phone_number`
- [ ] Atualizar código de listagem de números para ler `data[]` e os campos `type`, `number` (dígitos, sem `+`) e `status` como objeto
