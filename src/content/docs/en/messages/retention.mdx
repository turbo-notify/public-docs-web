> **Note (2026-07-04):** retention stopped being merely informational and became a read-window **actually enforced** by the API, with the number of days set by the contracted plan's tier. See the changelog [Cycle-anchored quotas](/en/changelog/2026-07-04-evaluated-cycle-quotas/).

Turbo Notify applies a per-tier read-window for querying messages through the API, balancing data privacy with your business's short/medium-term auditing needs.

## Read-window per tier

Each plan tier defines how many days, from the moment of sending/receiving, a message stays **retrievable** through the API:

| Tier       | Read window |
| ---------- | ----------:|
| `FREE`     | 7 days     |
| `SOLO`     | 30 days    |
| `BUSINESS` | 90 days    |
| `CUSTOM`   | 365 days   |

A message older than your tier's window stops existing for read purposes through the API — even though the row may still physically exist in the database (see [Physical retention vs. read-window](#physical-retention-vs-read-window) below).

## Behavior when fetching by id

`GET /v1/numbers/{alias}/messages/{id}` (and the flat route `GET /v1/messages/{id}` for the main number) returns **404** when the `id` is outside the tier's retention window — the same shape as a message that never existed, with no leak of the resource's past existence:

<ApiResponse
  status={404}
  body={{
    error: 'not_found',
  }}
/>

This also applies to sub-resources that depend on the id — `.../status`, `.../receipts`, `.../reactions` — which return 404 for the same reason once the parent message falls outside the window.

## Behavior on list

`GET /v1/numbers/{alias}/messages` (cursor list) **filters out** messages outside the tier's retention window — they simply don't appear on any page, without affecting pagination of messages that are still inside the window.

## Physical retention vs. read-window

The window above is about **API visibility** — a read-time filter layered on top of physical storage. Regardless of the contracted tier, physical storage follows a fixed **12-month** retention (database partitions dropped by age). The `CUSTOM` tier's 365-day window always sits inside that 12-month physical floor — there is no conflict between the two concepts, just two different horizons:

- **Physical retention (12 months, fixed, same for every tier):** when the data stops existing in the database, period — no tier can read past this.
- **Read-window (per tier, 7 to 365 days):** when the API stops answering queries about the message — an earlier cutoff than physical retention, set by the contracted plan.

Upgrading your tier does **not** recover messages that already passed the 12-month physical retention floor; it only recovers access to messages that were within the physical floor but outside your previous tier's read-window.

## Media durability (BYO Storage)

For messages with media (image, video, audio, document, sticker), the durability of the **bytes** is independent of the read-window above:

- **With [BYO Object Storage](/en/general/byo-storage-setup/) configured**: the bytes are copied to your bucket as soon as the message is received. They stay available for as long as your bucket retains the object — fully under your control, even after the message leaves the read-window.
- **Without BYO Storage**: only metadata (mime type, size, hash, caption) is persisted. Bytes are NOT proxied or stored by Turbo Notify. The `media.kind` field returns `"unavailable"` with a `setup_hint` envelope nudging you toward configuration.

This behavior is canonical since 2026-05-26 — there is no longer a 24h window via the WhatsApp CDN. Details in [BYO Object Storage](/en/general/byo-storage-setup/).

## Practical implications

- Query the message status as early as possible after sending — don't rely on the tier's read-window for long-term archiving.
- Configure a [webhook](/en/messages/webhook/) to receive real-time updates instead of relying exclusively on manual polling.
- Store whatever data is relevant to your business in your own system, such as the `message_id` and final status — the API is not a long-term store for your conversation history.
- Operations that depend on the original message, such as [replying](/en/messages/send/) (via `POST /v1/numbers/{alias}/messages/{message_id}/reply`), are also subject to the read-window — replying to a message outside the window fails as if the target message didn't exist.
- Per-cycle message/contact allowances are a different concept from retention — see [Usage & Quota](/en/usage/quota/).
