## Quotas vs. rate limits

Turbo Notify applies two distinct control mechanisms — don't confuse one for the other:

| | Quota | Rate limit |
| - | ----- | ---------- |
| What it measures | Total volume consumed in the billing cycle (messages, distinct contacts) | Instantaneous velocity of sends/calls |
| Window | Evaluated billing cycle (`cycle_start` → `cycle_end`) | Seconds/minutes, no cycle memory |
| Resets at | `resets_at` (cycle end) | A few seconds later (`Retry-After`) |
| Typical errors | `402 contact_quota_exceeded` · `429 messages_quota_exceeded` | `429 send_rate_spacing` · `429 rate_limit_exceeded` |
| Documented in | [Usage & Quota](/en/usage/quota/) | This page |

This page covers exclusively **velocity** limits — how fast you can send messages and call specific endpoints. For per-cycle message/contact allowances and their errors, see [Usage & Quota](/en/usage/quota/).

## Send rate (per tier)

Every message sent via the API respects a minimum interval since the previous send **on the same number** — the anti-ban spacing between sends. The interval is set by the plan's tier:

| Tier       | Minimum interval between sends | Equivalent messages/min |
| ---------- | -------------------------------:| -------------------------:|
| `FREE`     | 6s | 10 msg/min |
| `SOLO`     | 1.2s | 50 msg/min |
| `BUSINESS` | 0.6s | 100 msg/min |
| `CUSTOM`   | 0.4s | 150 msg/min |

Sending before the minimum interval since the last successful send **on that number** returns `429` with the code `send_rate_spacing` and a `Retry-After` header (in seconds — the time left until the next send is allowed):

<ApiResponse
  status={429}
  headers={{ 'Retry-After': '2' }}
  body={{
    error: 'send_rate_spacing',
  }}
/>

This limit is per **number** (main or extra) — each number has its own spacing clock, so using [extra numbers](/en/numbers/add/) increases the account's total send capacity.

## Contact refresh (per tier)

The [contact refresh](/en/contacts/refresh/) endpoint (`POST .../contacts/{contact_id}/refresh`) is more expensive than a plain read — it triggers the WhatsApp Gateway on demand — so it has its own per-minute limit, also scaling with tier:

| Tier       | Refresh/min |
| ---------- | -----------:|
| `FREE`     | 5   |
| `SOLO`     | 30  |
| `BUSINESS` | 120 |
| `CUSTOM`   | 600 |

Exceeding this limit returns `429 refresh_rate_limited` with a `Retry-After` header.

## Burst protection (operational, same across every tier)

Regardless of the contracted tier, Turbo Notify applies fixed operational limits to protect its infrastructure. These **do not** differentiate by plan:

- **`messages_per_minute`** — 10,000 sends/minute per replica (infrastructure burst protection, not a per-organization SLA).
- **`recipients_per_day`** — 2,000 distinct recipients/day per organization (fairness across accounts).

## Extra numbers

Each extra number registered on the account has its own send-spacing clock, independent of the main number. Each extra number's limits follow the same tier rules as the account.

This lets you distribute send volume across several numbers, increasing your account's total send capacity.

## Internal controls

Beyond velocity limits, Turbo Notify applies internal controls to protect its infrastructure and prevent abuse. These controls may temporarily restrict sending in situations such as:

- Abnormal traffic spikes from a single account.
- Sending patterns that could compromise service stability.
- A high rate of consecutive failures or rejections.

These controls are transparent and, in most cases, do not impact normal platform usage.

## Blocking risk

WhatsApp has its own usage rules and limits. Even while you stay within Turbo Notify's limits, excessive, unsolicited, or spam-perceived sending can result in WhatsApp blocking your number.

To avoid issues, follow the responsible-usage recommendations in [Abuse Prevention](/en/general/abuse/) and the <ExternalLink href="https://www.whatsapp.com/legal/business-policy/">WhatsApp policies</ExternalLink>.

## Related errors

| Status | Error code               | Description                                                              |
| :----: | ------------------------- | -------------------------------------------------------------------------- |
| `429`  | `send_rate_spacing`      | Sent before the tier's minimum interval between messages, on the same number. |
| `429`  | `refresh_rate_limited`   | Contact refresh limit exceeded.                                            |
| `429`  | `messages_per_minute_limit_exceeded` | Burst protection: 10,000 sends/minute per replica exceeded (see [above](#burst-protection-operational-same-across-every-tier)). |
| `429`  | `recipients_per_day_limit_exceeded`  | Burst protection: 2,000 distinct recipients/day exceeded (see [above](#burst-protection-operational-same-across-every-tier)). |
| `503`  | `service_unavailable`    | Service temporarily unavailable due to overload.                          |

For **quota** errors (`402 contact_quota_exceeded`, `429 messages_quota_exceeded`, `402 feature_not_available`), see [Usage & Quota](/en/usage/quota/#errors).

## Best practices

- Respect the `Retry-After` header when you receive a `429` status.
- Spread sending out over time instead of sending everything at once — your tier's minimum spacing already defines the sustainable pace.
- Use [extra numbers](/en/numbers/add/) to increase your send capacity.
- Monitor API response codes to quickly detect when a limit is hit.
- Configure [webhooks](/en/messages/webhook/) to track message status without repeatedly polling the API.
