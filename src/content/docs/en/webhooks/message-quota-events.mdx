Events related to the **per-number message quota**, measured against the
organization's **current billing cycle** (`cycle_start`/`cycle_end`).
Per-tier limits: `FREE`=300, `SOLO`=1.8k,
`BUSINESS`=50k, `CUSTOM`=500k **per number, per cycle**.

As of 2026-07-02 the message quota is **per number** — mirroring the
contact quota: each linked number (`main` or an extra-number alias) has its
own allowance, and an organization with N numbers gets N× the tier allowance.
These events identify the affected number via **`number_alias` in the
envelope** (not in `data`). Only messages sent **via Turbo Notify**
(`origin: "tn"`) consume the quota.

To configure the webhook URL, validate the signature, and understand the
envelope, see [Webhook: Setup & Envelope](/en/messages/webhook/).

## Events

| Event | When |
| ------ | ------ |
| `message.quota.warning` | Crossed the 80/90/95% threshold of the number's message quota |
| `message.quota.exceeded` | A send was rejected for exhaustion (HTTP 429) |

## `number_alias` in the envelope

Both events carry, immediately below `organization_id`, the `number_alias`
field: the TN number handle whose message quota was reached —
`"main"` for the primary number or an extra-number alias. The event `data`
carries the quota fields `threshold_bps` (only on `warning`), `used`, `quota`,
`cycle_start`, `cycle_end`, `resets_at`, `tier`, `channel`, `origin` —
`number_alias` rides the **envelope**, never `data`.

`used`/`quota` are measured against the organization's evaluated billing
cycle (`cycle_start`/`cycle_end`, ISO 8601 UTC); `resets_at` equals
`cycle_end`.

> Among account-wide events, `number_alias` is omitted **only** on
> `storage.*`. Every `*.quota.*` family (contacts and messages) now carries it.

## Example: `message.quota.warning`

```json
{
  "id": "evt_...",
  "type": "message.quota.warning",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:00Z",
  "data": {
    "threshold_bps": 80,
    "used": 240,
    "quota": 300,
    "cycle_start": "2026-06-01T00:00:00Z",
    "cycle_end": "2026-07-01T00:00:00Z",
    "resets_at": "2026-07-01T00:00:00Z",
    "tier": "FREE",
    "channel": "whatsapp",
    "origin": "tn"
  }
}
```

```json
    "origin": "tn"
  }

```

## Timestamps and correlation

- These are **synthetic** Turbo Notify events (they don't reflect a WhatsApp
  action): they **don't** carry `at` in `data` — only the
  envelope `created_at` (when TN emitted the event).
- `cycle_start`/`cycle_end` are the evaluated billing cycle `used`/`quota`
  were measured against. `resets_at` is a **business-value** timestamp (when
  the quota cycle resets), kept with its semantic name — equal to `cycle_end`
  at emission, not an occurrence moment.
- There's no `phone` in these events' payload. To correlate with the request
  that triggered the denial, use `GET /v1/events?request_id=req_...`.
