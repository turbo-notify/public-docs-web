List of webhook events emitted by Turbo Notify for changes related to TN
Contacts. You need to configure the URL and enable `contact.*` in the
dashboard.

## Table

| Event | When |
| ------ | ------ |
| `contact.created` | First observation of the `(organization, number, phone)` triple — contact identity is **per number**, so the same phone reaching `main` and an extra number generates **two** `contact.created` events, one per number (see [Contacts overview](/en/contacts/overview/)) |
| `contact.name_changed` | `name` diverged from the previous snapshot |
| `contact.picture_changed` | WhatsApp emitted a `PictureUpdate` or a refresh detected a new hash |
| `contact.first_messaged` | The organization sent the first outbound message to this contact (an **acquisition** signal for a new contact — observability; the quota is consumed by contacts reached in the cycle, not by this event) |
| `contact.quota.warning` | Crossed the 80/90/95% threshold of the contact quota |
| `contact.quota.exceeded` | A send was rejected for exhaustion (HTTP 402) |

## The `data` shape: contact triple + standard context fields

A `contact.*` event's `data` mirrors `message.*`'s `data`: the
**contact triple** `{id, name, number}` plus the standard context fields
(`direction`, `channel`, `origin`). `id` is the contact's own public id
(`ct_{hex32}`), just like `message.*`'s `data.id`.

```json
{
  "id": "ct_a1b2c3d4...",
  "name": "João Silva",
  "number": "5571999294756",
  "direction": "inbound",
  "channel": "whatsapp",
  "origin": "tn"
}
```

- `id` — the contact's public id (`ct_{hex32}`), the event's subject.
- `name` — the contact's WhatsApp push name.
- `number` — **full E.164**.
- `direction` — always `"inbound"` (the contact is observed/discovered via the
  WhatsApp channel). Absent on the synthetic quota events.
- `channel` — always `"whatsapp"`.
- `origin` — always `"tn"` (the TN platform processed the discovery).

> The `id` here is the **event's subject**. The `contact_id` that appears in
> a **message**'s `from`/`to` object is different — it references the
> counterpart's contact and keeps the `contact_id` key.

The full number is already exposed in every message's `from`/`to`, so masking
it on contact events only created inconsistency. `name` (push name) is still
PII that TN never logs raw — you receive it via webhook and own its
subsequent storage.

## `created_at` vs `at`

- `created_at` (envelope) — the moment TN **emitted the event**.
- `at` (in `data`) — the moment of the **real WhatsApp action**.

These are **distinct values**. The TN synthetic events (`contact.created`,
`contact.quota.warning`, `contact.quota.exceeded`) and also
`contact.picture_changed` (a picture/snapshot discovery, with no single
WhatsApp action moment) carry no `at` — only the envelope `created_at`. The
real-action events `contact.name_changed` and `contact.first_messaged` carry
`at`.

Every `contact.*` event carries `channel: "whatsapp"` and `origin: "tn"`.
Contact lifecycle events carry `direction: "inbound"`; the synthetic quota
events do **not** carry `direction`.

## `number_alias` in the envelope

**Every** `contact.*` event — both lifecycle (`contact.created`,
`contact.name_changed`, `contact.picture_changed`, `contact.first_messaged`)
and quota (`contact.quota.warning`, `contact.quota.exceeded`) — carries,
immediately below `organization_id`, the `number_alias` field: the TN number
handle the contact (or the contact quota) belongs to — `"main"` for
the primary number or an extra-number alias. Use it to route the observation
to the correct inbox.

The contact quota is now **per number** since 2026-06-22: each number has its
own distinct-contact count, so the `contact.quota.warning`/`contact.quota.exceeded`
events identify the affected number via `number_alias` in the envelope. The
quota event's `data` carries `threshold_bps` (only on `warning`), `used`,
`quota`, `cycle_start`, `cycle_end`, `resets_at`, `tier`, `channel`, `origin`.

> `used`/`quota` are measured against the organization's evaluated billing
> cycle, represented by `cycle_start`/`cycle_end` (ISO 8601 UTC). `resets_at`
> equals `cycle_end`.

> `number_alias` rides the **envelope**, never `data`. Among account-wide
> events, it's omitted only on `storage.*` (the sole event with no single
> number). Every `*.quota.*` family — both `contact.quota.*` and
> `message.quota.*` (per-number since 2026-07-02) — carries `number_alias`.

## Example: `contact.created`

Synthetic — no `at`, no `source`.

```json
{
  "id": "evt_a1b2c3d4...",
  "type": "contact.created",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:00Z",
  "data": {
    "id": "ct_a1b2...",
    "name": "João Silva",
    "number": "5571999294756",
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "tn"
  }
}
```

## Example: `contact.name_changed`

`name` is the new push name; `old_name` is the previous one.

```json
{
  "id": "evt_...",
  "type": "contact.name_changed",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:03Z",
  "data": {
    "id": "ct_a1b2...",
    "name": "João S.",
    "number": "5571999294756",
    "old_name": "João Silva",
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-05-15T12:00:00Z"
  }
}
```

`created_at` (TN emission) is **distinct** from `data.at` (the WhatsApp action
moment): here TN emitted the event 3s after the name change.

## Example: `contact.picture_changed`

```json
{
  "id": "evt_...",
  "type": "contact.picture_changed",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:02Z",
  "data": {
    "id": "ct_a1b2...",
    "name": "João Silva",
    "number": "5571999294756",
    "picture": {
      "kind": "available",
      "url": "https://<bucket>.r2.cloudflarestorage.com/contacts/.../picture.jpg?...",
      "url_expires_at": "2026-05-15T12:15:00Z",
      "hash": "abc123..."
    },
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "tn"
  }
}
```

`contact.picture_changed` does **not** carry `data.at` — it's a picture
discovery (snapshot) with no single WhatsApp action moment; use the envelope
`created_at` to know when the event was emitted.

This event also does **not** carry `picture.fetched_at`: the discovery is made
by hash comparison, and the URL's validity is already expressed by
`picture.url_expires_at`. `fetched_at` only exists when reading the contact
([`GET /v1/numbers/{alias}/contacts/{contact_id}`](/en/contacts/detail/)),
never on this webhook.

The `picture` block follows the same lifecycle as message media: when the
picture is stored in your bucket it arrives as
`kind: "available"` with a **presigned, time-limited URL**
(`url_expires_at`, ~15 min) — never a WhatsApp URL. Re-download the picture via
the GET endpoint when the URL expires. The event fires **only** when the
picture lands in your bucket, including when a contact was first observed
with no picture and it becomes available later (as soon as BYO Storage is
enabled). To read the picture on demand use
[`GET /v1/numbers/{alias}/contacts/{contact_id}/profile-picture`](/en/contacts/profile-picture/),
where `{alias}` is the `number_alias` received in this event's envelope.

## Example: `contact.first_messaged`

```json
{
  "id": "evt_...",
  "type": "contact.first_messaged",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:01Z",
  "data": {
    "id": "ct_...",
    "name": "João Silva",
    "number": "5571999294756",
    "tier": "unknown",
    "direction": "inbound",
    "channel": "whatsapp",
    "origin": "tn",
    "at": "2026-05-15T12:00:00Z"
  }
}
```

The `tier` field is **not populated** on this event: `contact.first_messaged`
always emits `"unknown"`. Don't use this field to infer the organization's
plan — the real `tier` is delivered on the
`contact.quota.warning`/`contact.quota.exceeded` events.

## Example: `contact.quota.warning`

```json
{
  "id": "evt_...",
  "type": "contact.quota.warning",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:00Z",
  "data": {
    "threshold_bps": 90,
    "used": 90,
    "quota": 100,
    "cycle_start": "2026-06-01T00:00:00Z",
    "cycle_end": "2026-07-01T00:00:00Z",
    "resets_at": "2026-07-01T00:00:00Z",
    "tier": "FREE",
    "channel": "whatsapp",
    "origin": "tn"
  }
}
```

`threshold_bps` is an integer in basis points: `80 | 90 | 95`. Quota
exhaustion is **not** signaled by this event with `threshold_bps: 100` — it's
signaled by the separate `contact.quota.exceeded` event, which does **not**
have the `threshold_bps` field. A consumer that branches on
`threshold_bps === 100` writes dead code and misses the real exhaustion
signal. Synthetic event — carries `channel`/`origin` but **no `direction`**
(not a message flow) and **no `at`**; `cycle_start`/`cycle_end` are the
evaluated billing cycle `used`/`quota` were measured against; `resets_at` is a
business-value timestamp (when the quota cycle resets, equal to `cycle_end`),
not the action moment.

## Example: `contact.quota.exceeded`

```json
{
  "id": "evt_...",
  "type": "contact.quota.exceeded",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:00Z",
  "data": {
    "used": 100,
    "quota": 100,
    "cycle_start": "2026-06-01T00:00:00Z",
    "cycle_end": "2026-07-01T00:00:00Z",
    "resets_at": "2026-07-01T00:00:00Z",
    "tier": "FREE",
    "channel": "whatsapp",
    "origin": "tn"
  }
}
```

Synthetic — carries `channel`/`origin` but **no `direction`**, **no `at`** and
**no `request_id`** in `data`; `resets_at` is kept.

## Idempotency

Every event carries a unique `id` (`evt_…`). Use `id` as your deduplication
key on your side.
