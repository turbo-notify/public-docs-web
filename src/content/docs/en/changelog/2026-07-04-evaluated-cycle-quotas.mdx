**Date:** 2026-07-04
**Status:** Applied

:::caution[Contract change]
Response and event fields change shape. Integrations reading `window_days`
(quota endpoints and `*.quota.*` webhooks) need to migrate to
`cycle_start`/`cycle_end`. New 402 gates may start rejecting requests that
were previously accepted silently.
:::

:::note[Update 2026-07-21]
Per-tier limits and the extra-number price were later revised on 2026-07-21:
the BUSINESS extra-numbers cap went from 300 to **1,000**, and an extra number
now costs **R$ 49.90/mo**. The values quoted below are preserved as a
historical record — for the current limits, see [Usage &
Quota](/en/usage/quota/).
:::

## What changed

### Quotas now measure against the evaluated billing cycle

Message and contact `used`/`quota` are now measured against the
organization's **evaluated billing cycle** — the subscription's current
billing period (from its start to its end), advanced at each renewal — no
longer a rolling 30-day window that decayed day by day. `resets_at` is now
the real cycle-renewal moment, not a value recomputed on every read.

| Retired field | New fields |
| --------------- | ------------- |
| `window_days` | `cycle_start`, `cycle_end` |

Affects:

- `GET /v1/numbers/{alias}/messages/quota` and `GET /v1/numbers/{alias}/contacts/quota`
  (and the equivalent flat routes for the main number).
- The `message.quota.warning`/`message.quota.exceeded` and
  `contact.quota.warning`/`contact.quota.exceeded` webhooks — `data` gains
  `cycle_start`/`cycle_end` in place of `window_days`.

`resets_at` stays present in every shape (endpoints and events) and always
equals `cycle_end`.

### `GET /v1/usage` gains `numbers[]` and the roll-up now sums allowances

`GET /v1/usage` and `GET /v1/usage/messages` stay top-level (account
roll-up), but each family's `quota` field is now the **sum of each linked
number's allowance** (it used to show a single number's ceiling against a
summed `used` — inconsistent). Both endpoints gain `numbers[]`: one entry per
live number with the `used`/`quota`/`remaining` breakdown for each family.

### Sending to a group now requires the BUSINESS tier or above

New `groups:messages` feature, available from the `BUSINESS` tier up.
Organizations on `FREE`/`SOLO` can still **receive** group messages and read
groups — only the outbound **send** (message or typing indicator) to a
`group_id` now returns **402 `feature_not_available`**.

### New retention read-window (per tier)

Each tier now defines how many days a message stays **retrievable** through
the API:

| Tier | Read window |
| ---- | ----------:|
| `FREE` | 7 days |
| `SOLO` | 30 days |
| `BUSINESS` | 90 days |
| `CUSTOM` | 365 days |

Messages older than the tier's window return **404** on `GET .../messages/{id}`
and are filtered out of `GET .../messages` (cursor list). The physical row
still follows the fixed partition retention (12 months) regardless of tier —
this window is only about API visibility.

### Inactive-subscription gate

Sending is now blocked with **402 `subscription_inactive`** when the
organization's subscription does not allow feature usage — including when a
**trial period has expired** with no conversion to a paid plan
(`details.status: "trial_expired"`).

### Numeric extra-numbers cap enforced

`POST /v1/numbers` now returns **402 `extra_numbers_limit_reached`** when the
organization already has the maximum number of live extra numbers for its
tier (BUSINESS 300 / CUSTOM 1,000).

### Read receipts now require the BUSINESS tier or above

New `read_receipts` feature, available from the `BUSINESS` tier up. The
detailed receipt log (`GET .../messages/{id}/receipts`, both the per-number
nested route and the main-number flat route) now returns **402
`feature_not_available`** for `FREE`/`SOLO` organizations. The message's
overall status (`GET .../messages/{id}/status`) is **not** affected by this
gate — it stays available on every tier. See [Receipts](/messages/receipts/)
(PT-BR — translation pending for this page).

### Webhook configuration now requires the SOLO tier or above

Creating a new webhook, or re-enabling a paused one, now requires the `SOLO`
tier or above — `FREE` organizations receive **402
`feature_not_available`** when attempting either action in the dashboard.
Editing the URL/secret/headers of an **already-active** webhook, or
explicitly deactivating it, stays available even after a downgrade
(grandfathered) — dispatch to an already-active webhook is unaffected by
this gate.

### Contacts-list filter renamed and fixed to the evaluated cycle

`GET /v1/numbers/{alias}/contacts` (and the main-number flat shortcut) had
a `has_messaged_in_window` filter measuring a **rolling 30-day** window
over `first_messaged_at` — diverging from the contact quota, which already
measured against the evaluated cycle. The parameter is **retired and
renamed** `contacted_in_cycle`: same semantics as the quota's `used`
figure (`is_self=false` contacts whose `last_messaged_at` falls inside the
number's evaluated billing cycle — new or returning). The old name does
**not** error — unrecognized query params are silently dropped (no strict
query validation), so `has_messaged_in_window=true` now returns the
unfiltered list.

### Webhook retries now require the BUSINESS tier or above

The exponential-backoff retry schedule (up to 6 attempts) is also a plan
feature — `FREE`/`SOLO` organizations get **exactly 1 delivery attempt** per
event; if it does not return `2xx`, the event goes straight to
`dead_letter`, with no retry. The `X-Webhook-Max-Attempts` header reflects
this limit on every delivery attempt. See [Delivery
attempts](/messages/webhook/#tentativas-de-entrega) (PT-BR — translation
pending for this section).

## Compatibility

Pre-production: the change applies immediately, with no transition layer.
Migrate any read of `window_days` to `cycle_start`/`cycle_end` and handle the
new 402 error codes (`subscription_inactive`, `feature_not_available`,
`extra_numbers_limit_reached`) in your send flows.
