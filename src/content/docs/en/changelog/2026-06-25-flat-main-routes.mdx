**Date:** 2026-06-25
**Status:** Applied

:::note[Flat routes work again]
Between 2026-06-22 and 2026-06-25, flat routes (`/v1/messages`, `/v1/contacts`,
`/v1/groups` and their sub-routes) returned **404** — see [Number-nested
routes](/en/changelog/2026-06-22-number-scoped-routes/). Starting with this
release they work again **permanently** as a shorthand for the primary number,
with a response identical to the nested form. They no longer return 404 for
being flat — only if the organization has no primary number registered.
:::

## What changed

From this version on, all primary-number operations can be performed
directly without specifying the alias in the URL:

| New flat route | Equivalent |
|---|---|
| `POST /v1/messages` | `POST /v1/numbers/main/messages` |
| `GET  /v1/messages` | `GET  /v1/numbers/main/messages` |
| `GET  /v1/messages/{id}` | `GET  /v1/numbers/main/messages/{id}` |
| `GET  /v1/contacts` | `GET  /v1/numbers/main/contacts` |
| `GET  /v1/contacts/quota` | `GET  /v1/numbers/main/contacts/quota` |
| `GET  /v1/groups` | `GET  /v1/numbers/main/groups` |
| `POST /v1/typing-indicator` | `POST /v1/numbers/main/typing-indicator` |
| *(and all sub-routes)* | |

The `/v1/numbers/main/…` form continues to work normally and produces
identical responses — the nested form is canonical; the flat form is a
permanent shortcut valid only for the primary number. For **extra numbers**,
continue using `/v1/numbers/{alias}/…` — they have no flat form.

The webhook/polling envelope of an operation performed via the flat route
carries `number_alias: "main"`, indistinguishable from an operation performed
via the nested route.

This change requires no modifications to existing integrations.
