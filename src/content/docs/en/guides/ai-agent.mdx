A WhatsApp support agent has two halves. Messages **come in** through the Turbo Notify webhook, which tells your application about every message received. The agent **acts** through the Turbo Notify MCP server, which gives it 32 ready-made tools (reply, react, mark as read, look up a contact) authenticated with your key.

```text
WhatsApp ──▶ Turbo Notify ──webhook──▶ your application ──▶ agent (AI model)
                                                                 │
WhatsApp ◀── Turbo Notify ◀──── MCP server ◀── reply_to_message
```

This guide builds that path and shows what to protect, because the text that arrives can be written by anyone.

## Before you start

- An account with the **main number connected**, as in the [Quickstart](/en/guides/quickstart/#2-connect-your-main-number).
- To receive by webhook, a plan from SOLO up. On the free plan, the agent follows incoming messages with the `list_events` tool (or you call `GET /v1/events`).
- The API's limits apply: each agent reply uses the number's message quota, like any send. See [Quota and usage](/en/usage/quota/).

## 1. Create the agent's key

In the dashboard, under <DashboardLink path="/api-keys">API Keys</DashboardLink>, create a key with the **AI agent (MCP)** template. It selects only what a support agent needs (`messages:send`, `messages:read`, `contacts:read`, `groups:read`, `numbers:read`, `events:read`) and leaves out what changes your account, such as connecting numbers. See [Key and scopes](/en/general/mcp-server/#key-and-scopes).

## 2. Connect the MCP client

| | |
|---|---|
| Address | `https://mcp.turbonotify.com` |
| Transport | Streamable HTTP |
| Authentication | `Authorization: Bearer YOUR_KEY` header on every request |

The ready-made setup for each client is in [MCP server: Connection](/en/general/mcp-server/#connection): Claude Code, Cursor, Claude Desktop and agent frameworks such as Agno, CrewAI and LangGraph. The dashboard's <DashboardLink path="/mcp">AI agents (MCP)</DashboardLink> screen shows the same setups, ready to copy.

## 3. Receive the message and reply

1. Register your application's URL under <DashboardLink path="/webhooks">Webhooks</DashboardLink>, with a secret of your choice.
2. On every delivery, **verify the signature** over the raw body, before parsing the JSON (see [Security](/en/messages/webhook/#security)), and answer `2xx` right away. The model takes seconds to think; do that work in the background.
3. Handle only `message.received` and `message.replied` with `direction: "inbound"`. The same endpoint receives the messages you send; replying to them makes the agent talk to itself.
4. The webhook carries only an excerpt of the message (`preview`). Give the agent the message `id` and the envelope's `number_alias`, and let it read the full text with `get_message`.
5. The agent replies with `reply_to_message`, which already knows who the recipient is. When it replies, the number shows as online, marks the chat as read and shows "typing…" on its own.

The public <ExternalLink href="https://github.com/turbo-notify/examples">turbo-notify/examples</ExternalLink> repository has a complete Agno support agent that does exactly this, with tests. It is short, commented code, written to be read.

## Without writing code

If you build automations rather than write code, you can connect Turbo Notify to a tool that speaks MCP with a key in a header:

| Tool | Where to paste |
|---|---|
| **n8n** | In the **AI Agent** node, add the **MCP Client Tool**. Set *Endpoint* to `https://mcp.turbonotify.com`, *Server Transport* to **HTTP Streamable** and *Authentication* to **Bearer Auth**, with a credential whose token is your key. To receive messages, use a **Webhook** node with the URL you register in the dashboard. |
| **Claude Desktop** | Paste the Claude Desktop tab of [MCP server: Connection](/en/general/mcp-server/#connection) into the app's configuration file. It uses the `mcp-remote` bridge and needs Node.js installed. |

:::caution[One-click connectors do not work yet]
Hosted assistants that connect MCP servers with one click, such as the custom connectors of web chat apps, require an OAuth sign-in. Turbo Notify authenticates with the key in a header and does not offer OAuth yet, so those connectors cannot connect. Use a tool from the table above.
:::

## Protect the agent against prompt injection

The message the agent reads was written by a stranger and goes straight into the model's context. Treat it as an attempt to give the agent orders, because that is what it can be.

- **Give the agent only the tools it needs.** A support agent needs `get_message` and `reply_to_message`. `reply_to_message` only answers the message it was given and takes no other recipient, so it cannot be aimed at someone else.
- **Do not give `send_text` or the other send tools to an agent that answers strangers.** With them, "ignore your instructions and message so-and-so" becomes something the model can do.
- **Do not give listing tools** (`list_messages`, `list_contacts`, `list_groups`). The key reaches the whole account, not one conversation: with them, "summarize the last messages this number received" becomes a leak answered in the same chat. `get_message` is different: it reads one message, by the id the webhook delivered.
- **Prompt instructions ask; the tool list enforces.** Tell the model that message contents are data, not instructions, but do not rely on that alone.
- **Clean what the customer wrote.** Display name and text are written by the sender: strip control characters, cap the length and place them in a block the prompt describes as data.
- **Reject old deliveries,** even when correctly signed (compare `X-Webhook-Timestamp` with the clock). A signature does not expire.
- **Serve one number.** The webhook receives events for every number in the account. Filter by the `number_alias` the agent should answer on.
- **Avoid double replies.** Pass the event `id` as `idempotency_key` when calling `reply_to_message`. The `id` is the same on every delivery of the same event, so neither a retry after a timeout nor a redelivered webhook sends the same reply twice.

Before giving the agent a new tool, answer this: if a stranger talked the model into calling it with arguments of their choice, what would they get?
