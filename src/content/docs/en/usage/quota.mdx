Turbo Notify meters **two independent quotas** per linked number (`main` or an
extra-number alias): outbound messages and distinct contacts contacted. As of
ADR 2026-07-02 both quotas are **per number** — each number has its own
allowance, so an organization with N numbers gets N× the tier allowance.

Only traffic sent **via Turbo Notify** (`origin: "tn"`) consumes quota;
messages sent directly from the physical phone (`origin: "native"`) don't count.

## Evaluated cycle — when the quota resets

The measurement window for both quotas is the organization's **evaluated
billing cycle** (`cycle_start` through `cycle_end` — the same
`current_period_*` window as the subscription), not a rolling 30-day window
anymore. `resets_at` always equals `cycle_end`: the quota resets at cycle
rollover, not on a moving window that decays day by day.

- **`used`**/**`quota`** are always measured against the currently open cycle.
- When the cycle closes (subscription renewal), the counters reset to zero and
  a new `[cycle_start, cycle_end)` window begins.
- `cycle_start`/`cycle_end` is the **same for every number** in the
  organization (the cycle belongs to the subscription, not the number) — only
  `used`/`quota` vary per number.

## Tier table (per number, per cycle)

| Tier       | Messages/cycle | Distinct contacts/cycle | Extra numbers (max) |
| ---------- | --------------: | -----------------------: | -------------------:|
| `FREE`     | 1,000           | 100                       | 0                    |
| `SOLO`     | 10,000          | 1,000                     | 0                    |
| `BUSINESS` | 50,000          | 5,000                     | 300                  |
| `CUSTOM`   | 500,000+        | 50,000+                   | 1,000                |

The 10:1 ratio (messages/contact) reflects the average usage of ~10 messages
per contact per cycle. Organization-level overrides (`messages_quota_override`
/ `contacts_quota_override`) replace the tier ceiling when set — applied
**per number**, the same way the tier ceiling is.

The `tier` field in the responses below is always one of the 4 values above,
in **uppercase** (`"FREE"`, `"SOLO"`, `"BUSINESS"`, `"CUSTOM"`).

## Groups and inbound messages

- A **group** send consumes **1 message-quota unit** and **zero** contact
  quota — a group is not a contact.
- **Inbound** (received) messages consume neither quota.
- Only **outbound** sends with `origin: "tn"` consume the message quota; only
  contacts reached **via Turbo Notify** consume the contact quota.

## Sending to groups requires BUSINESS or above

Sending a message or a typing indicator to a `group_id` requires the
`groups:messages` feature, available from the `BUSINESS` tier up. On
`FREE`/`SOLO` you can still **receive** group messages, list groups and read
group details — only the outbound **send** to a group is blocked:

<ApiResponse
  status={402}
  body={{
    error: 'feature_not_available',
  }}
/>

See [Groups — Overview](/en/groups/overview/) and [Group limitations](/en/groups/limitations/).

## Endpoint: account-wide usage

```http
GET /v1/usage
```

**Scope:** any authenticated API key (no specific scope).

**Cache:** `Cache-Control: max-age=60` (Redis L1, 60s TTL).

`GET /v1/usage` is the **account roll-up**: the top-level `messages`/`contacts`
sum the usage of **every number** in the organization — `quota` is the **sum of
each number's allowance** (an organization with 2 numbers on a 100/cycle tier
reports `quota: 200`). `resets_at` is the organization's evaluated
`cycle_end` (the same for every number). The response also carries
`numbers[]`: one entry per LIVE number (main + extras), with the
`used`/`quota`/`remaining` breakdown for each family — no `resets_at`/`tier`
per entry (both are already uniform at the top level).

<ApiResponse
  status={200}
  body={{
    messages: {
      used: 1234,
      quota: 10000,
      remaining: 8766,
      resets_at: '2026-07-01T00:00:00Z',
      tier: 'SOLO',
    },
    contacts: {
      used: 87,
      quota: 1000,
      remaining: 913,
      resets_at: '2026-07-01T00:00:00Z',
      tier: 'SOLO',
    },
    numbers: [
      {
        alias: 'main',
        messages: { used: 600, quota: 5000, remaining: 4400 },
        contacts: { used: 40, quota: 500, remaining: 460 },
      },
    ],
  }}
/>

### `GET /v1/usage/messages`

The same account roll-up, messages only — but it also carries its own
`numbers[]` (messages-only entries), for callers that only need this quota
without paying for the contact-quota roll-up:

<ApiResponse
  status={200}
  body={{
    messages: {
      used: 1234,
      quota: 10000,
      remaining: 8766,
      resets_at: '2026-07-01T00:00:00Z',
      tier: 'SOLO',
    },
    numbers: [
      { alias: 'main', messages: { used: 600, quota: 5000, remaining: 4400 } },
    ],
  }}
/>

## Per-number endpoints

- `GET /v1/numbers/{alias}/messages/quota` — the number's **message** quota
  (flat route for the main number: `GET /v1/messages/quota`, equivalent to
  `GET /v1/numbers/main/messages/quota`).
- `GET /v1/numbers/{alias}/contacts/quota` — the number's **contact** quota
  (flat route for the main number: `GET /v1/contacts/quota`).

Both return the same shape — the evaluated-cycle snapshot **for that number**:

<ApiResponse
  status={200}
  body={{
    used: 1234,
    quota: 10000,
    remaining: 8766,
    cycle_start: '2026-06-01T00:00:00Z',
    cycle_end: '2026-07-01T00:00:00Z',
    resets_at: '2026-07-01T00:00:00Z',
    tier: 'SOLO',
  }}
/>

`resets_at` always repeats `cycle_end` — kept for convenience for clients that
only look at one field. Unlike `GET /v1/usage`, these two endpoints expose
`cycle_start`/`cycle_end` explicitly because they are the snapshot of **one**
number, not a multi-number roll-up.

## Retention read-window

Beyond the quota, each tier defines how many days a message stays
**retrievable** through the API — messages older than that window stop
existing for reads:

| Tier       | Read window |
| ---------- | ----------:|
| `FREE`     | 7 days     |
| `SOLO`     | 30 days    |
| `BUSINESS` | 90 days    |
| `CUSTOM`   | 365 days   |

- `GET /v1/numbers/{alias}/messages/{id}` for a message older than the tier's
  window returns **404** (indistinguishable from "never existed").
- `GET /v1/numbers/{alias}/messages` (cursor list) **filters out** messages
  outside the window — they simply don't appear on any page.
- This window governs **API visibility**; the physical row still follows the
  fixed partition retention (12 months) regardless of tier — see
  [Message retention](/en/messages/retention/) for the full content/metadata
  lifecycle.

## Errors

### 402 — subscription inactive

Returned by the send pipeline when the organization's subscription does not
allow feature usage (`ACTIVE` and `TRIALING` within the trial period are the
only statuses that pass unrestricted):

<ApiResponse
  status={402}
  body={{
    error: 'subscription_inactive',
    message: 'Subscription is not active',
    details: { status: 'trial_expired' },
  }}
/>

`details.status` is one of: `trialing` (allowed, does not raise this error),
`trial_expired` (trial ended with no paid plan), `past_due`, `pending`,
`terminated`, `canceled` (past the already-paid period), or `missing` (the
organization has no subscription at all).

### 402 — feature not available on this plan

<ApiResponse
  status={402}
  body={{
    error: 'feature_not_available',
  }}
/>

Today the public gates in this family are: reactions (`reactions`, SOLO+); typing
indicator (`typing_indicator`, SOLO+ — the base gate, every call); sending a
message or typing indicator to a group (`groups:messages`, BUSINESS+ — see
[above](#sending-to-groups-requires-business-or-above)); detailed receipt
log (`read_receipts`, BUSINESS+ — see [Receipts](/en/messages/receipts/));
and creating extra numbers (`extra_numbers`, unavailable on FREE/SOLO — see
[Extra numbers](/en/numbers/add/)).

### 402 — extra-numbers limit reached

Returned by `POST /v1/numbers` when the organization already has
`max_extra_numbers` live extra numbers for its tier (BUSINESS 300 / CUSTOM
1,000; FREE/SOLO have no access to extra numbers at all):

<ApiResponse
  status={402}
  body={{
    error: 'extra_numbers_limit_reached',
    message: 'Extra numbers limit reached for the current plan (300/300).',
    details: { limit: 300, current: 300 },
  }}
/>

`details.limit` is the tier's `max_extra_numbers` ceiling; `details.current`
is the organization's current count of live extra numbers.

### 402 — contact quota exceeded

<ApiResponse
  status={402}
  body={{
    error: 'contact_quota_exceeded',
    message: 'Distinct-contacts quota exceeded for tier BUSINESS (100/100 this cycle)',
    details: { quota: 100, used: 100, resets_at: '2026-07-01T00:00:00Z', tier: 'BUSINESS' },
  }}
/>

### 429 — message quota exceeded

<ApiResponse
  status={429}
  headers={{ 'Retry-After': '1' }}
  body={{
    error: 'messages_quota_exceeded',
  }}
/>

Unlike the contact 402, this 429 does **not** carry `details` with
`used`/`quota`/`resets_at` in the body — query
`GET /v1/numbers/{alias}/messages/quota` (or `GET /v1/usage/messages`) for the
full snapshot and the real `resets_at`. The `Retry-After` header here is a
short technical value (it does not represent "how long until the quota
renews" — the quota only renews at `resets_at`, which may be days away).

### 402 vs 429 — when each appears

| | 402 (contacts) | 429 (messages) |
| - | ------------- | ------------- |
| Signal | Upgrade the plan | Cycle quota exhausted |
| `Retry-After` header | Absent | Present (not reliable for "when does the quota renew") |
| Body carries `used`/`quota`/`resets_at` | Yes (`details`) | No — query the quota endpoint |
| Resets at | `resets_at` (evaluated cycle end) or upgrade | `resets_at` (evaluated cycle end) |

## Quota webhooks

- `contact.quota.warning` at 80/90/95% (basis points).
- `contact.quota.exceeded` on exhaustion.
- `message.quota.warning` at 80/90/95%.
- `message.quota.exceeded` on exhaustion.

Both families carry `cycle_start`/`cycle_end` in `data` (replacing the retired
`window_days`). See [Message quota events](/en/webhooks/message-quota-events/),
[Contact events](/en/webhooks/contact-events/) and [Rate Limits](/en/messages/rate-limits/).
