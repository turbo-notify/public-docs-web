Eventos relacionados à **quota de mensagens por número** (janela rolling de 30 dias; limites por tier: free=1k, solo=10k, business=50k, custom=500k+ **por número**).

Desde a ADR 2026-07-02 a quota de mensagens é **por número** — espelhando a quota de contatos: cada número vinculado (`main` ou alias extra) tem sua própria franquia, e uma organization com N números tem N× a franquia do tier. Estes eventos identificam o número afetado via **`number_alias` no envelope** (não em `data`). Apenas mensagens enviadas **via Turbo Notify** (`origin: "tn"`) consomem a quota.

> **Nota (2026-05-15):** o enforcement deste quota foi ativado em 2026-05-15. Os limites já estavam documentados — a partir desta data, o código aplica os limites efetivamente. Veja [Per-Tier Message Quota Activation](/changelog/2026-05-15-message-quota-activation/) e a [auditoria em rate-limits](/messages/rate-limits/).

## Eventos

| Evento | Quando |
| ------ | ------ |
| `message.quota.warning` | Cruzou threshold 80/90/95% da quota de mensagens do número |
| `message.quota.exceeded` | Tentativa rejeitada por estouro (HTTP 429) |

## `number_alias` no envelope

Ambos os eventos carregam, logo abaixo de `organization_id`, o campo `number_alias`: o handle do número TN ("inbox") cuja quota de mensagens foi atingida — `"main"` para o número principal ou o alias de um número extra. O `data` do evento **não** muda (os campos de quota `threshold_bps`, `used`, `quota`, `window_days`, `resets_at`, `tier`, `channel`, `origin` permanecem iguais) — o `number_alias` fica no **envelope**, nunca dentro de `data`.

> Entre os eventos de conta, `number_alias` é omitido **apenas** em `storage.*`. Toda família `*.quota.*` (contatos e mensagens) passou a carregá-lo.

```json
{

  "type": "message.quota.exceeded",
  "organization_id": "org_a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "number_alias": "main",
  "created_at": "2026-05-15T12:00:00Z",
  "data": {
    "quota": 1000,
    "used": 1000,
    "resets_at": "2026-06-14T...",
    "tier": "free",
    "channel": "whatsapp",
    "origin": "tn"
  }
}
```

## Timestamps e correlação

- Estes são eventos **sintéticos** do Turbo Notify (não refletem uma ação no WhatsApp): desde 2026-06-02 **não** carregam `at` em `data` — apenas o `created_at` do envelope (momento de emissão do evento pelo TN).
- `resets_at` é um timestamp de **valor de negócio** (quando a janela de quota reinicia), mantido com seu nome semântico — não é o momento de ocorrência.
- Não há `phone` no payload destes eventos. Para correlacionar com a requisição que disparou o estouro, use `GET /v1/events?request_id=req_...`.
